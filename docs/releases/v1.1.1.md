**`v1.1.1` is `main` at `82e1dc1e`** — v1.1.0 (`36787f1b`, 2026-09-10) plus **462 commits**
(`git rev-list v1.1.0..main --count`; 365 without merges), landed as the coordinator's gated
batches **#93 through #195**. Every batch was gated on a dedicated worktree in the `esker-ci`
container — `nextest`, `fmt`, `clippy`, `doc`, `deny` — before it was fast-forwarded onto `main`.

**What makes this release different from v1.1.0 is not the percentage, it is the machine the
percentage was taken on.** v1.1.0's scoreboard was the ActiveRecord suite against the
**in-process** backend, and its own acceptance sheet said so
([`docs/acceptance/v1.1.md`](../acceptance/v1.1.md) §9: *"A 99.48% pass rate over 10,134 tests says
nothing about a real cluster of stores"*). v1.1.1's scoreboard is the same suite against a **real
topology — one placement driver, four stores, one `esker-sql` node** — running for ten and a half
hours without a stop, a wedge or a node restart.

## 3. What changed

Classified from `git log --oneline v1.1.0..main`. Each entry names the commit that carries it.

### A. PL/pgSQL and row triggers — [ADR 0113](../adr/0113-plpgsql-is-the-subset-the-suite-sends.md)

Accepted 2026-09-13; supersedes [ADR 0058](../adr/0058-a-do-block-is-two-templates-not-a-language.md)'s
"a DO block is two templates" ruling. The census and the order of work are
[`docs/plans/plpgsql-subset.md`](../plans/plpgsql-subset.md).

* **`DO $$ … $$` runs through a PL/pgSQL interpreter**, inside the statement that reached it
  (`ea72350d` reads the body, `83815c76` runs it). Declarations, `IF`, `RAISE`, `SELECT … INTO`,
  assignment, `FOR <record> IN <query> LOOP`, `EXECUTE`, `RETURN` and plain statements; one
  transaction, one buffer, one savepoint, **no autonomous write**. A variable reaches SQL as a
  typed literal in the lowered tree, never as text.
* **Row triggers fire** — `BEFORE` and `AFTER` ROW, on `INSERT`, `UPDATE` and `DELETE`, in
  PostgreSQL's place and order (`c32c77c5`). `BEFORE ROW` runs after defaults, sequences and the
  row id and before generated columns and checks; triggers of one event fire in name order, each
  handed the `NEW` the one before returned; `RETURN NULL` takes the row out of the statement
  (`INSERT 0 0`). A stored trigger that never fired is what made `persistence_test` red.
* **One catalog write is taken** — `UPDATE pg_catalog.pg_constraint SET convalidated = …`
  (`b5f47544`, ADR 0113 §6 ruled **(b)** by the user). It writes the `NOT VALID` flag a foreign key
  or a `CHECK` already stores; `check_all_foreign_keys_valid!` cannot work without it. **Every
  other catalog write stays `42501`**, including another column of the same catalog, and
  `tests/user_decided_divergences.rs` pins that.

### B. Transactions and isolation — [ADR 0114](../adr/0114-a-unique-key-being-written-waits-at-read-committed.md)

Accepted 2026-09-13, three sections, all built. Debts #90, #91, #96.

* **§1 — at READ COMMITTED a unique index entry is locked before it is read** (`f873997b`). A write
  that adds a by-value entry takes ADR 0057's row lock on the entry's key first; a lock taken after
  a wait re-runs the statement at a fresh snapshot, which finds the holder's committed entry
  (`23505`) or nothing (the insert goes through). Two sessions inserting one unique key now behave
  as PostgreSQL does instead of the second being refused `40001`. REPEATABLE READ and SERIALIZABLE
  take no lock on the entry, by decision.
* **§2 — the eager row lock is validated at the statement's read timestamp** (`fc0c9807`).
  **This is the format change; §4 is its deployment rule.** `SELECT … FOR UPDATE`'s eager lock
  (ADR 0088) was a `Check` validated at the transaction's `start_ts`, so a row another transaction
  committed after `BEGIN` was always `40001`. The user approved the format change on 2026-09-13.
  * **Wire**: `TxnMutation::Check { key, read_ts }`. **Tag 5 keeps its bytes** (`read_ts: None`);
    **tag 7** is `u8 7, bytes key, varint read_ts`. The golden gains `txn-prewrite-check-at` and
    `txn-prewrite-read-ts`.
  * **Raft log**: `TxnWrite::Check { key, read_ts }`, **kind 7**, same layout.
  * **Store**: a check validates at `read_ts.unwrap_or(start_ts)`; a range stays at `start_ts`.
* **§3 — SERIALIZABLE, and `ON CONFLICT` at REPEATABLE READ** (`101a8b5b`), decided as option (2)
  **with the arbiter rule**: a lost race on a unique key is **`40001` when the key was read before
  this transaction wrote it** and `23505` otherwise, where *read before* means an earlier read at
  SERIALIZABLE (`Txn::has_read`, asked immediately before the probe so the probe never counts) or a
  read by `ON CONFLICT`'s arbiter at either level (`conflicting_row` collects, the `INSERT` marks).
  **No format, no wire, nothing below the SQL layer.** It still answers at `COMMIT` where
  PostgreSQL answers at the `INSERT` — declared, ADR 0114 *What stays declared*.
* **#96 — a READ COMMITTED lock refused because its row moved re-runs the statement**
  (`a820f2c7`). PostgreSQL's `LockRows` locks the row's newest version; this node re-runs at a
  fresh snapshot through the one path both the first attempt and the retry share. It asks
  `changed_since_statement` only after a refusal, and re-runs only when the row explains it. **No
  format change and no client change.** The in-memory backend's cluster lock now validates as the
  store's does.

### C. Frame sizing and cutting — debts #98, #99, #100

* **#98 — a request is measured by what it encodes to** (`5493a006`). **The request had not grown;
  the estimate of it had.** `txn_payload_size` charged a flat six bytes a field, and since ADR 0114
  §2 gave a mutation a read timestamp it charged six more for a varint the encoder had been writing
  since ADR 0057 §4 — so the estimate stood six bytes above every stamped mutation, which at READ
  COMMITTED is every write a statement makes. Measured on both builds with the same probe (65,536
  mutations): `PUT` estimate 4,259,889 → 4,653,105 with the **frame 4,259,886 on both**.
  **Zero bytes changed on the wire.**
* **#99 — a batch too large for one frame is sent as several** (`cdff95cc`). A 65,536-row fixture
  load is a legal statement; PostgreSQL has no user-visible frame ceiling, so refusing it was this
  client's limitation and not the database's. The cut is by bytes, made where the request is built,
  over the objects that will actually be sent. `ResolveLock` needs no cut of its own. **Client-side
  only — no format change.**
* **#100 — one mutation wider than a frame is a named refusal that carries the key**
  (`Error::KeyTooLarge`, same commit). A caller holding a quarter of a million keys cannot find the
  offending one otherwise; the key named is the one whose own mutation would not fit, and nothing
  is sent.

### D. Types and the catalog surface

* **`regnamespace`** (oid 4089) and **`regnamespace[]`** (4090) —
  [ADR 0115](../adr/0115-regnamespace-is-an-oid-that-prints-as-a-schema.md), accepted 2026-09-13
  (`1a366f1d`). A name resolves against the statement's own catalog the way `regclass` does; an oid
  prints as the schema that has it (its digits for one no schema has, `-` for 0); a row holds the
  four bytes and no name. Measured: a stored value follows its schema through `ALTER SCHEMA …
  RENAME TO` and prints its digits once the schema is dropped. **Declared: not an index key** (§5).
* **#81 — an unknown literal beside an enum takes the enum** (`229b70e4`, `6c37caff`, `d0892316`;
  `850447a7` takes a fourth patch back out because no test could distinguish it). `CASE`, `COALESCE`,
  a set operation's arms and `GREATEST`/`LEAST` all settle a user-defined type the same way, and an
  unknown branch is read as a label — `22P02 invalid input value for enum h_mood: "nope"` instead
  of `invalid input syntax for type smallint`.
* **#101 (json half) — a deep JSON value is parsed on a stack sized for its bound** (`02493064`).
  This crate's four depth bounds are all read off **statement text**, and the scanner deliberately
  never looks inside a string literal — which is how `UNION` as a column name is counted. So
  `'[[[[…]]]]'::jsonb` was one token at depth one, bounded by nothing. A value level costs about
  2,796 bytes and 19beta1 *answers* ten thousand levels, so a constant bound inside a worker's
  stack would have traded a crash for a refusal of what PostgreSQL answers. For `jsonb`, ten
  thousand levels answer and a hundred thousand are `54001`, which is 19beta1's own pair.
  **The tsquery half is open, and it is still a crash** (§5).
* **#103 — a column default prints the cast that is in its tree, modifier and all** (`530b5e94`).
  `pg_get_expr` deparses the tree a default was stored as, so on one `interval(3)` column 19beta1
  answers three different strings for three spellings; two of the three were wrong here. The defect
  lived in the **cross product** of two corpora, each of which varied one axis and fixed the other.

### E. Sequences and constraint names

* **#93 — a serial or identity column on a table with no key takes its number** (`0d1d7b4a`). A
  table with no primary key carries an internal row id at position 0, so every declared column sits
  one later in the row than in the statement; the sequence filled the row id's slot and `id` stayed
  NULL (`23502`) for serial, bigserial and both kinds of identity. `sequences_for` now finds the
  column by name.
* **#94 / #95 — a rolled-back sequence takes its numbers with it, and a default names its sequence
  by the search path** (`b3779f12`). A relation id is given back by a rolled-back `CREATE`, and the
  sequence's non-transactional counter is keyed by that id, so the next sequence on the reused id
  carried on from the rolled-back one's numbers. No format change.
* **#97 — a sequence's counter is written only by transactions of its own** (`bd9f9e15`).
  `CREATE SEQUENCE` wrote its `START` in the statement's transaction and the drops deleted it
  there, so a transaction that made a sequence and drew from it was refused `40001` at `COMMIT`.
  `CREATE SEQUENCE` now writes no counter and a drop leaves it behind.
* **#92 — a constraint's name is chosen, found and refused by PostgreSQL's rules** (`b81c2098`).
  Four measured shapes: a nameless `CHECK` is named for the one column its expression reads; a
  taken derived name is numbered past every constraint name in the schema where a *given* one is
  refused; a table's constraints of every kind share one name space (`42710`); a `UNIQUE` or
  `PRIMARY KEY` meets a relation of its name first (`42P07`) and a constraint second; and
  `SET CONSTRAINTS` finds a name the way a relation is found.

### F. Statements

* **`INSERT … SELECT`** (`60458625` red first, `56ca733c`): the query is read to the end and
  written through the `VALUES` loop.
* **#102 / #111 — `DROP DATABASE` refuses a database other sessions are on, and counts them**
  (`20e935cc`). Four of five shapes were already right; the fifth was missing outright —
  `55006 database "X" is being accessed by other users` with `DETAIL: There is 1 other session
  using the database.` #111 is `pg_stat_activity.datname` answering per row instead of one value
  for all of them.

### G. Liveness, measurement and records

* **#84 — a single-node oracle has a physical half, so its locks expire** (`2021e563`;
  [ADR 0116](../adr/0116-a-single-node-oracle-needs-a-physical-half.md), **Proposed** in the tree,
  approved by the user 2026-09-16). A Percolator lock's only way out without its owner is the
  lease, and `is_expired` judges that in the timestamp's physical half. `CountingOracle` hands out
  consecutive integers, whose physical half is zero for the first 262,144 timestamps — so under it
  a lock left by a prewrite whose commit never landed was **immortal**, every later statement on
  that key spent the resolution budget and answered `40001`, and restarting did not help. The
  single-node `esker-sql` binary — the no-`--pd` arm, a production path — shipped exactly that
  pairing. `WallClockOracle` is promoted into `esker-client` and de-duplicated from two test copies.
* **#88 — measured, not fixed** (`149987f9`, `f8cdc7a7`, and the register row). A columnar fragment
  refuses a whole scan where the row path refuses one key. **How often**: on a hot table with a
  writer beside it, **22 of 120 scans — one in 5.5** — met a lock, with a transaction open for
  essentially the whole window; a cold table met 0 of 120. **What it costs**: on a **100,000-row**
  table the fallback is **7.29 s against a clean scan's 653 ms (+1016%)**, **84× the absolute cost**
  of the same fallback on a four-hundred-row table (86.6 ms vs 68.2 ms, +27%), at one encounter in
  30 scans. The fallback's own cost is the stable half (five round medians within 1.8%); the clean
  baseline is the half that moves (280 → 817 ms as the writer adds rows), so the *ratio* slides
  26× → 8.9× while the absolute cost does not move. **One point at one scale; no slope is claimed.**
  The fix needs a wire format change and therefore an ADR, which is not in this release.
* **#89's test half** (`cb7f816b`), **#77 closed as a record** (`29b2b001`, `bc465803` — the test it
  asked for cannot be written, and the measurement says why), **#104 registered and closed the same
  day** (`c224f0ea` — a misread of a test's 60-attempt sample size as a 1-in-60 failure rate; the
  defect was fixed 2026-09-09 under ADR 0079).

## 4. Deployment: every store is upgraded before any SQL node

**This release changes a wire format and a Raft log format** (§3 B, ADR 0114 §2), so a rolling
upgrade has an order and getting it wrong has a defined cost. The rule is ADR 0114's own
consequence and the rule `VERB_RELEASE_LOCK`'s doc already stated for the log:

> **Upgrade every store first. Upgrade `esker-sql` nodes second.**

* **A node that goes first** costs `08006` on every READ COMMITTED `SELECT … FOR UPDATE` that
  reaches an old store — the old store cannot decode **tag 7** — **having locked nothing**. The
  refusal is clean: no partial lock is left behind.
* **A leader that goes first** costs its old followers their copies of the region: they **stop at
  the entry rather than skip it** when they meet **kind 7**, so **nothing diverges**. An unknown
  tag and an unknown kind are errors on both paths, never a silently skipped record
  (`crates/esker-store/src/apply.rs`, `raft_log.rs`; invariant 2).

**Tag 5 keeps its bytes**, so a new store serves an old node's unstamped `Check` unchanged — the
compatibility only runs one way, which is why the order matters.

Nothing else in this release changes a format. #98 changed zero bytes on the wire, #99 cuts a batch
client-side, and #100, #96 and ADR 0114 §3 are above the wire entirely.

> **This order is a design property with a stated failure mode, not a measured one.** No
> mixed-version cluster was run (§6).

### The declared divergences, by family

A divergence is **declared** when a corpus line disagrees with PostgreSQL and a test says so in
words, with the reason; the harness fails on any disagreement that is *not* declared, so the list
is complete by construction ([`docs/acceptance/v1.1.md`](../acceptance/v1.1.md) §3). Merged by
family, with what moved since that sheet:

* **`postgres_fdw` is not available** — `0A000 extension "postgres_fdw" is not available`, off
  `AVAILABLE_EXTENSIONS` by ruling. A foreign-data wrapper is a second storage engine reached
  through this one. **This is the ten rows attempt 7 counts as declared** (`foreign_table_test.rb`).
* **A write to a system catalog is `42501`** — `pg_depend`, `pg_class`, and every column of
  `pg_constraint` **except** `convalidated`, which ADR 0113 §6 (b) now takes (§3 A). The catalog
  here is computed from records rather than stored as tables, so there is no row to delete and no
  honest way to pretend there is. Pinned by `tests/user_decided_divergences.rs`.
* **PL/pgSQL outside ADR 0113's subset is still `0A000`.** The "DO minimal" ruling was reversed for
  the subset the suite sends; a body outside it is refused, and the two tests that pinned `DO` as
  refused moved to where a running block is tested.
* **`reg*` is not an index key.** PostgreSQL 19 builds a primary key and an index over a
  `regnamespace` column; this node refuses all three by name, because the row codec writes no key
  bytes for the type — as for `regproc` and `regtype` — and a key that writes nothing would give
  every row the same key (ADR 0115; `tests/regnamespace.rs`). Relatedly, a real relation's
  `regclass` **does not narrow to an `oid`** (`22003`): relation ids are `u64` and an oid is four
  bytes, and answering a truncated oid would be a wrong value under a right type
  ([ADR 0097](../adr/0097-an-oid-is-four-bytes-and-a-derived-one-is-not.md)'s own boundary).
* **`SET standard_conforming_strings = off` is refused, and so is PostgreSQL 19's own.**
  `0A000 non-standard string literals are not supported`, the same code and the same sentence
  19beta1 gives. `bytea_test.rb` fails **on the oracle itself**. There is nothing to build here.
* **A deep `tsquery` is not a divergence yet — it is #101's open half, and it is a crash.** 19beta1
  answers a `tsquery` of 6,000 levels and refuses 10,000; here **ten thousand levels still kill the
  child, in parallel and serially**, so probe contention is not the explanation.
  `tests/value_depth.rs::a_deep_tsquery_is_refused_and_never_kills_the_child` is `#[ignore]`d and
  carries the state — *"a tsquery of ten thousand must be an answer or a refusal, never a dead
  child"*. This is the one open row that touches invariant 9, and it is named here rather than
  filed under "declared" because a refusal it is not.
* **Two wire-level divergences no suite test reaches — status unknown at this release, and said so
  rather than carried forward.** v1.1.0's sheet recorded them against `9d642ef0`:
  `COALESCE(1, 1.5)` answering `float8` where PostgreSQL resolves the common type of `integer` and
  `numeric` as `numeric`, and `(ARRAY[c::regtype])::regtype[]` answering an internal
  type-confusion message rather than a deliberate refusal. **Neither appears in today's accepted
  baseline** (`esker-rails-harness/wire-types-baseline.txt`, 43 entries, last rebased at run 127 on
  node `93fb44dd`, 2026-09-11) — and the census has not been re-run since, so that absence is not
  evidence they are fixed. The oid/regtype surface moved a great deal in runs 109–110, so these two
  need re-reading before either is quoted again.

Beyond the declared list, attempt 7's board carries rows that are **not the node**: three
cross-adapter files (MySQL2, Trilogy, SQLite constants), `pg_dump` and a PostgreSQL socket absent
from the machine, a pure Arel `BigDecimal` unit test, three Ruby fork segfaults and three marshal
errors. They were identical on the fake backend at run 116.

## 6. What this release cannot claim

In the manner of [`docs/acceptance/v1.1.md`](../acceptance/v1.1.md) §9: each of these is a limit of
**evidence**, not a suspicion about the code.

* **§1 is one client, one file at a time.** The harness runs 426 suite files in sequence, one
  watchdog of 1,800 s per file, 88.7 s a file. The only concurrency exercised is what an individual
  test creates for itself. **No sustained multi-client load was applied**, and nothing here is a
  throughput or a tail-latency number.
* **No faults were injected.** The pass ran ten and a half hours with **zero node restarts, zero
  wedges, zero stopped files** and a node log holding no WARN or ERROR line — which is a statement
  about a healthy cluster's ten hours, not about a cluster losing a store, a leader or a disk. The
  crash and fault behaviour this release claims is what the workspace's own tests claim.
* **Ten and a half hours is the longest thing measured.** The catalog canary's floor did not climb
  over that window and the seeded row still answered at the end. Nothing was run for a day, a week
  or under a growing store beyond what #109 measures — and **#109 measures an insert cost that
  grows 4.4× with what the store already holds**, which is the shape most likely to bite a longer run.
* **No cross-version upgrade was run.** §4's order comes from the format change's design and from
  the decode paths' own behaviour, not from a mixed-version cluster anybody started. The failure
  modes named there are the ones the code is written to produce.
* **The scoreboard is `7193e5d9` and the release is `82e1dc1e`** (§2). Fifty-seven commits — three
  of them below the SQL layer — landed after the pass that measured it, and only #98 among those
  has a real-topology observation of its own, taken on one file run alone.
* **The declared divergences of §5 are v1.1.0's sheet's, re-read rather than re-measured**, except
  where a ruling in this release moved one (`convalidated`, the PL/pgSQL subset, `regnamespace`,
  #101's two halves). **The wire census was not re-run for this release at all**, which is why §5's
  last bullet says *unknown* rather than *fixed* about two rows that have left the baseline.
