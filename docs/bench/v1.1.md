`CLAUDE.md`: *"Benchmarks are not optional but are not gates. Keep `esker-cli bench` runnable at
every phase and record numbers in `docs/bench/` so regressions are visible."* The v1.1 candidate tag
is not cut yet, and this is the record that should exist before it is.

> **Status: four bands measured on 2026-09-10 at `5e508fb3`, one band not applicable, and two
> stated environment limits** (§5). Written method-first on purpose, the same as
> [`mpp-baseline.md`](mpp-baseline.md): a measurement whose method is written afterwards is a
> measurement whose method was chosen by its results — and the first attempt to take numbers
> produced none, which is recorded below rather than retried quietly.

### The window of 2026-09-09 20:14–20:48 took no numbers, and why

Three faults, all in the runner and none in the system:

1. **`psql` is not in the CI image.** The first arm — a SQL load for
   [ADR 0102](../adr/0102-the-catalogs-read-path.md)'s numbers — exited 127 before it started. The
   image belongs to the coordinator and a lane does not rebuild it, so that measurement moved to a
   `Gate` test instead (`what_a_catalog_read_costs_with_stores_under_it`), which reaches real
   stores over a socket without needing a client binary.
2. **The binaries are at `/target`, not `./target`.** The container mounts the repo at `/work` and
   the build volume at `/target`; five bands reported `rc=127` in seconds.
3. **`esker-cli cluster start` is a foreground supervisor, not a daemon.** With that fixed, the
   script waited on it for the rest of the window and produced an empty log. The cluster itself
   came up correctly — PD on 24164 and four stores — which is visible in the container's process
   list and nowhere else.

**Nothing about the system was learned, and nothing is claimed.** The runner now starts the
cluster in the background and waits for `region ls` to answer before the first band.

## 1. What the record has to contain

Four bands on a **real cluster** — four `esker server` processes, a real placement driver, release
binaries — each reporting **p50, p99, throughput** beside the **region count** the band ran at, with
the `[box]` environment line and `env-sampler.sh` beside every round:

| band | what it is | workload |
|---|---|---|
| point write | one key, durable | `fillrandom --sync` |
| point read | one key | `readrandom` |
| range scan | seek and read a handful, thousands of times | `scanrange --batch-size 32` |
| transaction mix | 2PC, two `fsync`s | `txnput` and `txnget` |

## 2. What runs today, and the one thing that does not

**The workloads exist.** `fillrandom`, `readrandom`, `scanrange` and `txnput`/`txnget` are all in
`Workload`, and `scanrange` is exactly the short-range shape a SQL index lookup makes — its own doc
comment says why `readseq` cannot stand in for it.

**One documentation defect, found on the way**: the usage text lists
`fillseq | fillrandom | overwrite | readrandom | readmissing | readseq | txnput | txnget | tso |
allocid` and **omits `scanrange`**, which `Workload::parse` accepts. The band this record needs is
the one nobody can discover from `--help`.

**And the topology is not expressible.** `bench --remote HOST:PORT` drives **one store**:
`bench_remote.rs` and `bench_txn.rs` both build their client on
`StaticRegion::whole_key_space(BOOTSTRAP_REGION, store_id, NO_LEADER_OPINION)` — a resolver that
says the whole key space is one region on the store you named. There is no `--pd`, so a four-store
cluster cannot be measured through its placement driver, which is the topology this record is
supposed to be about.

**The change that closes it is small and its shape is known.** `esker-cli` already asks a
placement driver for a region: `region.rs`'s `PdConn` calls `PdReq::GetRegion` and gets back the
region, its leader peer id and the store addresses — everything `Route` needs. So: an adapter that
implements `RegionResolver` over that call, and a `--pd HOST:PORT` flag on `bench` that installs it
in place of `StaticRegion`. No new wire tag, no new dependency — `esker-sql` keeps its own copy for
its own reasons, and this one stays inside `esker-cli`.

**Both are closed now** (`bench --pd HOST:PORT`, and `scanrange` in the usage text). The flag
asks PD once where the stores are, connects to all of them, and resolves every key through
`PdReq::GetRegion`; `--pd` and `--remote` are refused together rather than ranked, because a run
that quietly picked one would be a number nobody could read back.

## 3. What is different from the last record, so nobody compares the wrong things

The most recent numbers of this shape are [`phase-5.md`](phase-5.md), and **they are not
comparable row for row**:

| | phase-5 | this record |
|---|---|---|
| topology | **one store**, no Raft, no placement driver | **four stores**, Raft, a real PD |
| durability | one `fsync` per write, two per transaction | the same, but now behind a Raft round as well |
| timestamps | `CountingOracle` in the benchmark process | PD's oracle, over the wire |
| routing | none — one region, one store | PD, with a region cache and retries |
| binary | `cargo build --release -p esker-cli` at `7da4762` | release at the v1.1 candidate |
| machine | Apple M4 Max, 16 cores, 128 GiB | the same machine, and it is now shared with lanes |

**Every one of those makes v1.1's numbers slower than phase-5's, and none of them is a
regression.** A record that does not say this invites exactly the wrong reading — which is why the
comparison table comes before the numbers rather than after them.

## 4. The run

`esker-coord/h1/bench-v1.1.sh`: one cluster, four bands in sequence, `env-sampler.sh` beside it, a
hard deadline per band and the group killed on `EXIT`. Every band prints its region count. The

## 5. The numbers

Taken by r1 on 2026-09-10 from `harness/bench-v11-r1.sh` — a **copy** of
`esker-coord/h1/bench-v1.1.sh` rather than an edit of it, so the method in §4 is still the method
that ran.

    commit     5e508fb3, host release build
    esker-cli   7,514,016 b · sha 283a067bb4ff4136 · inode 308622331
    esker-sql  15,624,896 b · sha 6202469c0579e108 · inode 308622379
    topology   4 stores 26800..26803, placement driver 26804, every band through `--pd`
    NUM        5,000

| band | workload | p50 | p99 | throughput | regions |
|---|---|---|---|---|---|
| point write | `fillrandom --sync` | 21,328.5 us | 31,344.0 us | 46 ops/s | 3 |
| point read | `readrandom` | 123.9 us | 271.0 us | 7,533 ops/s | 3 |
| range scan | `scanrange --batch-size 32` | — | — | **not applicable** | 3 |
| txn write | `txnput` | 58,501.6 us | 73,975.9 us | 18 ops/s | 3 |
| txn read | `txnget` | 126.9 us | 276.5 us | 7,324 ops/s | 3 |

**Reads and writes are three orders of magnitude apart, and that is the shape of the system rather
than a fault in it.** A point read is 124 us; a synchronous point write is 21 ms — 172x — because a
write is a Raft round plus an `fsync` and a read is neither. A transactional write is 58 ms, another
2.7x on top, which is Percolator's two phases and their two `fsync`s. §3's table is what these
should be read against: none of the four differences from `phase-5.md` is a regression.

**`range-scan` did not fail; it does not exist in this configuration.** The tool says so itself —
`esker bench: scanrange does not run over RawKv` — so it is recorded as not-applicable rather than
as a missing number. Whoever owns the band should say whether a RawKv cluster is the wrong place to
ask for it or whether the band needs a different driver; §2 promised this band and the promise is
not yet kept.

### NUM is 5,000, and what 20,000 would cost

§4's method says `--num 20000`. At the rates above that is, per band:

    point write   20,000 / 46 ops/s     =  ~7.2 min
    txn write     20,000 / 18 ops/s     = ~18.5 min
    point read    20,000 / 7,533 ops/s  =   ~3 s
    txn read      20,000 / 7,324 ops/s  =   ~3 s
                                          ~26 min for the two write bands alone

Longer than the 30-minute window this ran in, so NUM was cut to 5,000 **before** the run rather
than discovered halfway through it. **The latencies are per-operation and do not depend on NUM;
only the wall time does** — so the table above is a fair reading of the four bands, and a 20,000-row
record needs a ~40-minute window of its own for the write bands.

### Two environment limits, stated rather than smoothed over

**1. `env-sampler.sh` produced an empty file.** It is in the method, it was started beside the
bands, and it did not sample. Its output must not be quoted as evidence of a quiet box, because
there is none.

**2. The `[box]` lines in this run belong to the Gate step, not to the bands.**

    [box] starting a cluster:  load 9.75 3.69 3.28, free 2884 MB, available 14670 MB
    [box] catalog measurement: load 9.75 3.69 3.28, free 2998 MB, available 14794 MB

A one-minute load average of 9.75 is not a quiet box — it is a `cargo nextest` compile inside the
container, which ran immediately before the Gate step. The **bands** ran earlier, on a box with an
empty chain and no foreign container, and **no `[box]` line exists for them**, because those lines
are printed by the Gate test and the bands run on the host. §1 asks for that line beside every
round; for the bands it is not there, and the next record should make the runner print one.

### The catalog read on a real topology — ADR 0102's number

`what_a_catalog_read_costs_with_stores_under_it` (`crates/esker-sql/tests/routing_differential.rs`)
is the arm §4's first attempt moved here when `psql` turned out not to be in the CI image. On r1's
run it **panicked** before producing a curve — `INSERT INTO t VALUES (249, 249) never landed:
duplicate key value violates unique constraint` — which was the test's own retry rule refusing a
`23505` that its first attempt had caused; the rule keyed on the wording of one of the client's
three "the write's fate is unknown" shapes. Fixed in the same day's work, and the measurement now
runs:

    2000 point writes and 2000 point reads through a store-backed node
    before        catalog views 1,    repeats 0,    mean 711 us, worst  711 us
    after writes  catalog views 2001, repeats 1999, mean 729 us, worst 3323 us
    after reads   catalog views 4001, repeats 3999, mean 764 us, worst 3323 us
    buckets after reads: <100us 0 · <1ms 3638 · <10ms 363 · rest 0

**Read against run 111's own number, which is the point of the test.** Run 111 counted 4,790,406
catalog views in one `ActiveRecord` pass at a mean of under half a microsecond — against a
`MemoryBackend`, an in-process `BTreeMap` with no store, no placement driver, no Raft and no socket.
The same view over a socket and Raft is **764 us**, three orders of magnitude away. The count is
topology-independent; the cost is not, and only one of those two numbers is about the read
[ADR 0102](../adr/0102-the-catalogs-read-path.md) is about.

**Provenance, because it is not the same run as the bands:** taken on this machine at `f4a7406a`
(the commit that fixed the retry rule), not at `5e508fb3`, and on a box that was not otherwise
quiet — the two `[box]` lines above are this measurement's own. It is a first number for the band
rather than a release figure, and it should be re-taken at the tag beside the other four.
