# v1.1 — the release record, and the method written before the numbers

`CLAUDE.md`: *"Benchmarks are not optional but are not gates. Keep `esker-cli bench` runnable at
every phase and record numbers in `docs/bench/` so regressions are visible."* The v1.1 candidate tag
is not cut yet, and this is the record that should exist before it is.

> **Status: method only. No numbers yet** — and the first attempt to take them produced none,
> which is recorded here rather than retried quietly. Written method-first on purpose, the same as
> [`mpp-baseline.md`](mpp-baseline.md): a measurement whose method is written afterwards is a
> measurement whose method was chosen by its results.

### The window of 2026-09-09 20:14–20:48 took no numbers, and why

Three faults, all in the runner and none in the system:

1. **`psql` is not in the CI image.** The first arm — a SQL load for
   [ADR 0102](../adr/0102-the-catalogs-read-path.md)'s numbers — exited 127 before it started. The
   image belongs to the coordinator and a lane does not rebuild it, so that measurement moved to a
   `Gate` test instead (`what_a_catalog_read_costs_with_stores_under_it`), which reaches real
   stores over a socket without needing a client binary.
2. **The binaries are at `/target`, not `./target`.** The container mounts the repo at `/work` and
   the build volume at `/target`; five bands reported `rc=127` in seconds.
3. **`esker-cli cluster start` is a foreground supervisor, not a daemon.** With that fixed, the
   script waited on it for the rest of the window and produced an empty log. The cluster itself
   came up correctly — PD on 24164 and four stores — which is visible in the container's process
   list and nowhere else.

**Nothing about the system was learned, and nothing is claimed.** The runner now starts the
cluster in the background and waits for `region ls` to answer before the first band.

## 1. What the record has to contain

Four bands on a **real cluster** — four `esker server` processes, a real placement driver, release
binaries — each reporting **p50, p99, throughput** beside the **region count** the band ran at, with
the `[box]` environment line and `env-sampler.sh` beside every round:

| band | what it is | workload |
|---|---|---|
| point write | one key, durable | `fillrandom --sync` |
| point read | one key | `readrandom` |
| range scan | seek and read a handful, thousands of times | `scanrange --batch-size 32` |
| transaction mix | 2PC, two `fsync`s | `txnput` and `txnget` |

## 2. What runs today, and the one thing that does not

**The workloads exist.** `fillrandom`, `readrandom`, `scanrange` and `txnput`/`txnget` are all in
`Workload`, and `scanrange` is exactly the short-range shape a SQL index lookup makes — its own doc
comment says why `readseq` cannot stand in for it.

**One documentation defect, found on the way**: the usage text lists
`fillseq | fillrandom | overwrite | readrandom | readmissing | readseq | txnput | txnget | tso |
allocid` and **omits `scanrange`**, which `Workload::parse` accepts. The band this record needs is
the one nobody can discover from `--help`.

**And the topology is not expressible.** `bench --remote HOST:PORT` drives **one store**:
`bench_remote.rs` and `bench_txn.rs` both build their client on
`StaticRegion::whole_key_space(BOOTSTRAP_REGION, store_id, NO_LEADER_OPINION)` — a resolver that
says the whole key space is one region on the store you named. There is no `--pd`, so a four-store
cluster cannot be measured through its placement driver, which is the topology this record is
supposed to be about.

**The change that closes it is small and its shape is known.** `esker-cli` already asks a
placement driver for a region: `region.rs`'s `PdConn` calls `PdReq::GetRegion` and gets back the
region, its leader peer id and the store addresses — everything `Route` needs. So: an adapter that
implements `RegionResolver` over that call, and a `--pd HOST:PORT` flag on `bench` that installs it
in place of `StaticRegion`. No new wire tag, no new dependency — `esker-sql` keeps its own copy for
its own reasons, and this one stays inside `esker-cli`.

**Both are closed now** (`bench --pd HOST:PORT`, and `scanrange` in the usage text). The flag
asks PD once where the stores are, connects to all of them, and resolves every key through
`PdReq::GetRegion`; `--pd` and `--remote` are refused together rather than ranked, because a run
that quietly picked one would be a number nobody could read back.

## 3. What is different from the last record, so nobody compares the wrong things

The most recent numbers of this shape are [`phase-5.md`](phase-5.md), and **they are not
comparable row for row**:

| | phase-5 | this record |
|---|---|---|
| topology | **one store**, no Raft, no placement driver | **four stores**, Raft, a real PD |
| durability | one `fsync` per write, two per transaction | the same, but now behind a Raft round as well |
| timestamps | `CountingOracle` in the benchmark process | PD's oracle, over the wire |
| routing | none — one region, one store | PD, with a region cache and retries |
| binary | `cargo build --release -p esker-cli` at `7da4762` | release at the v1.1 candidate |
| machine | Apple M4 Max, 16 cores, 128 GiB | the same machine, and it is now shared with lanes |

**Every one of those makes v1.1's numbers slower than phase-5's, and none of them is a
regression.** A record that does not say this invites exactly the wrong reading — which is why the
comparison table comes before the numbers rather than after them.

## 4. The run

`esker-coord/h1/bench-v1.1.sh`: one cluster, four bands in sequence, `env-sampler.sh` beside it, a
hard deadline per band and the group killed on `EXIT`. Every band prints its region count. The
record is filled in from its output and the environment lines are pasted with the numbers, not
summarised away.
