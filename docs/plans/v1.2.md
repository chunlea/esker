# v1.2 — what is still open after v1.1

Status: **Proposed**, 2026-09-11. Drafted overnight while run 127 holds the cluster, so every fact
here is read from the tree or from a committed result and none is scheduled.

**Not a schedule.** Each row says what is true now, what would make it done, what it waits on, and
how big it is. Nothing here claims an order, because the two items that would decide one — run 127's
full pass rate and run 126's chaos verdict — are being measured tonight and tomorrow.

**Where the numbers come from.** `docs/acceptance/v1.1.md` is the v1.1 sheet, `docs/plans/debts-v1.1.md`
is the register, and `esker-rails-harness/results/` holds the runs. Where a row quotes a figure it
names the run, because a figure without one is what §9 of the v1.1 sheet exists to warn about.

## 1. #46 — an index on a `jsonb` column

**Now.** Refused with `0A000 an index on a column of type jsonb`, which a real server builds.
Ordering a `jsonb` column already answers — `crate::value::json::compare` decides which of two
values is larger, and that is what closed every other row of the no-equality census. The register
row is the only one left in §1 that is *not the same kind of work*, and the user moved it here.

**Why it is not the same kind of work.** A comparison decides an order between two values in hand.
An **index key** has to carry that order in its *bytes*, memcomparable, because the engine compares
keys without ever seeing a type. So the encoding must put the kind first —
`[] < null < string < number < boolean < array < object`, measured — then, inside a kind, a
`numeric` ordering for numbers (`1.0` and `1.00` are one value, and `2 < 10`), a length before
contents for arrays, and a pair count before keys for objects.

**Acceptance.** `CREATE INDEX … ON t (j)` over a `jsonb` column builds, and a range scan over it
returns rows in the order `tests/captures/pg19_jsonb_order.txt` measured — 53 cells, already
committed. The empty array is the row to watch: it sorts below every scalar and `[1]` does not, so
a kind-then-value encoding is wrong on it, and that single cell refuted the first model.

**Depends on.** Nothing in the tree. It depends on **the user**: this is a new on-disk key format
for a type this node already stores, so by the constitution it is not a lane's call. Existing
`jsonb` columns have no index to rebuild today, which makes now the cheap moment and any later one
expensive.

**Size.** Medium, and mostly encoding plus its golden. The comparison exists; the bytes do not.

## 2. #54 — a condition a join step can answer belongs on the join

**Now.** **Fixed and in hold**, `4375e520`, first at the morning gate. Measured at four hundred
relations: the comma form went **352 ms → 3.65 ms** and `pk_and_sequence_for` **200.6 ms → 10.9 ms**,
against a plain catalog scan at 2.79 ms. A bare cross product still costs 486 ms, which is the
control saying the semantics did not move.

**Acceptance.** Already met and already committed: `catalog_read_slope.rs`'s
`a_repeated_statement_stops_tracking_the_catalog` lost its `#[ignore]` and passes at 1.19 → 2.74 ms
for five times the catalog. What is **not** met is the gate — this is a planner change and only
fourteen join-shaped binaries have run on it, chosen by hand. **The crate's whole suite is the
acceptance that is missing**, and it is the gate's first job.

**Depends on.** The gate. Nothing else.

**Size.** Done, pending verification. Listed here so that v1.2 does not silently inherit it as open.

## 3. ADR 0107 step 2 — the vectors, and where one is stored

**Now.** **Step 1 landed** — `216b7a7f feat(sql): lquery is a type, so it has an array`, which is
what took `CATALOG_FORMAT_VERSION` to **37**. Step 2 is `int2vector`/`oidvector`, and b4 has it.

**The open question is the ADR's own**, and it says so under *What this ADR does not decide*:
whether `int2vector`'s **stored** form changes. Nothing in this node stores one today — they exist
only in `pg_catalog`'s computed views — so the question is cheap to answer later and answering it
now would be answering it without a measurement. The ADR's step 2 is written to start by asking
what a stored `int2vector` column round-trips as today.

**Acceptance.** The four special cases the ADR lists become dead code, and the two tests that pin
them go red on purpose — `tests/concat_operator.rs`'s `the_two_vectors_are_still_text` and
`tests/array_of_void.rs`'s `the_three_arrays_this_node_does_not_have`. Both were written naming this
ADR, which is how the work is recognised as finished rather than asserted to be.

**And one thing that must keep working through it**: `attnum = ANY(indkey)`. It is the one shape a
schema dump depends on, and it is why the quantified-array path lists the vectors by hand today.

**Depends on.** b4. The storage-form decision depends on a measurement nobody has taken.

**Size.** Medium, and the risk is not in the SQL layer: the zero-based lower bound and the
`esker-keys` encoding are invisible from above.

## 4. PD high availability on the real topology — run 128

**Now.** Built and tested in process, never on real hardware. `cluster start --pd-nodes 3` founds a
group ([ADR 0108](../adr/0108-a-cluster-starts-n-placement-drivers-and-every-client-follows-the-leader.md)),
all three placement-driver clients follow the leader through one shared policy, and
`crates/esker-cli/tests/pgwire_pd_failover.rs` measures **a statement returning 2.0 s after the
leading driver is `kill -9`ed** — which is the driver group's own election window, not the client.

**Acceptance.** `esker-coord/h1-run128-design.md`, four named kills across four clusters: PD leader
settled and young, **store** leader settled and young. The store pair is the one that answers run
124's last open question and the settled one is also **#55's first test on real hardware** — every
test of it today is in process.

**One correction that page carries**, because it changes what the run can claim: killing a PD
leader does *not* answer run 124's `184 × 08006`. Those came from killing the **store** that led
region 1; a PD kill is a different failure — no timestamp, so nothing runs at all, reads included.

**Depends on.** run 127 and run 126 finishing first, and a window. Nothing in the tree.

**Size.** Small for me, about 35 minutes of cluster for r1.

## 5. What run 127 will tell us

**Now.** Running tonight: the full Rails suite on the real topology, no chaos, about 13 hours. The
last full-topology figure of record is run 110 at **10,081 / 10,134 (99.48%)**, taken against
`ba9d8a3d`, and `main` has moved a long way since — every landing from `#111` to `#131`.

**What it is for.** Two numbers nothing else produces: **the pass rate on current main**, and
**the per-file duration**. The first says whether twenty batches of type and planner work moved the
board; the second is the input to every chaos recipe, because a file that takes four minutes cannot
be scored against a kill every sixty seconds.

**Acceptance.** There is none — it is a measurement, and the mistake to avoid is treating it as a
gate. What it *can* fail is its own instrument: `docs/acceptance/v1.1.md` §9 is the standing warning,
and run 124 is the worked example of a run that measured nothing while reporting numbers.

**Depends on.** Nothing. It is the input to the rest.

**Size.** r1's night.

## 6. The chaos recipe's remainder

**Now.** Two arms exist and one has never landed. run 126 is run 124's recipe plus the
`reconnected` positive case, with a per-kill verdict spec at `esker-coord/h1-run126-verdict.md`;
run 128 is PD HA. Neither has produced a number.

**The two things the recipe still does not say**, and they are the reason this is a row rather than
a note:

* **An upper bound on an `08006` burst after a leader kill.** run 124 measured 184 in 0.695 s with
  a largest gap of 367 ms — refused fast, not waiting. #55 is what that was, and it is fixed; what
  is *not* written down is the number a future run fails on. `h1-run128-design.md` proposes
  `[kill, kill + 4 s]` — twice an election's upper bound, since both groups run `esker_raft`'s
  defaults of `TICK_MS` 100 ms and `election_tick` 10–20 — **as a bound and not an expectation.**
  It has never been tested against a real run, and one run is what turns a proposal into a rule.
* **A load shape other than four clients.** Every durability run since 119 is `record --clients 4`.
  Four is what run 120 measured 31,700 attempts a second with, and nothing says whether the
  failures are shape-independent. A run at one client and at sixteen, against the same kills, is
  what would say.

**Acceptance.** Both numbers written into `h1-run124-design.md`'s criteria table with a run behind
them, rather than derived from a constant.

**Depends on.** run 126 and run 128.

**Size.** Small each, and they are measurements rather than code.

## 7. Catalog format 37 — the migration note that does not exist

**Now.** `CATALOG_FORMAT_VERSION` is **37** on main, bumped by ADR 0107 step 1. The reader's floors
are per record kind and are documented where they are declared — `OLDEST_TABLE_VERSION` 2,
`OLDEST_EXTENSION_VERSION` 12, and a schema record's own — and each says *why* it is not
`CATALOG_FORMAT_VERSION`: a reader newer than 12 must still accept what version 12 wrote.

**What is missing is not the code, it is the sentence a reader needs.** There is no document that
says, for a given version, what changed in the bytes and what a reader of an older tree does with
them. Thirty-seven versions of a format with no changelog is a format whose compatibility story
lives in thirty-seven comments, and `record.rs` already carries the one-paragraph version of it
("version 1 is not read … version 2 is different") because somebody needed it once.

**And it has collided twice**, which is the practical cost: two lanes have claimed the same next
number in one night. A table is what makes the next collision visible before it is committed.

**Acceptance.** `docs/adr/` or `docs/plans/` gains a table — version, what it added, which record
kind, which floor it moved — generated from the constants and the git history rather than typed, so
it cannot drift. Plus the rule that is currently folklore: **claim the number at HEAD in the same
commit that uses it, and the later committer renumbers.**

**Depends on.** Nothing.

**Size.** Small. It is a table and a paragraph, and the facts are all in the tree.

## What this list deliberately leaves out

* **Anything run 127 or run 126 has not measured yet.** Two of the seven rows above exist to
  receive those numbers; adding rows that guess at them would be adding rows to be deleted.
* **Five placement-driver members.** `docs/plans/phase-15-pd-ha.md` §7 says nothing is built or
  tested for it and that remains true; `--pd-nodes 5` will start five and nothing claims anything.
* **A membership change under load.** `cluster_pd_member_change.rs` adds and removes a member on
  three real processes with nothing running against them. Under load is a different question and
  nobody is asking it.
* **`cluster/mod.rs`'s third seam.** 814, 483 and 142 lines are all inside the guideline now; there
  is no third split that pays for itself.
