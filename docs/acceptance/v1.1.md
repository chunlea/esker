## 3. Declared divergences

A divergence is **declared** when a corpus line disagrees with PostgreSQL and the test says so in
words, with the reason. The harness fails on any disagreement that is *not* declared, so this list
is complete by construction — nothing diverges silently.

| | at `9d642ef0` | at v1 |
|---|---:|---:|
| **answers** — a value or an error differs | **345** | 427 |
| **types** — the value agrees and the column's type OID does not | **601** | 464 |

Both movements are the same story read twice. `answers` **fell** by 82 while the corpus grew by
1,932 statements, because three units deleted whole families rather than adding entries
([ADR 0084](../adr/0084-name-is-a-stored-type-and-its-tag-is-additive.md)'s `name`,
[ADR 0086](../adr/0086-a-folded-cast-keeps-the-type-it-named.md)'s folded cast,
[ADR 0087](../adr/0087-an-integer-literal-is-the-narrowest-type-that-holds-it.md)'s literal ladder).
`types` **rose** by 137 because entries **moved** into it: parity rule 4 found 52 `answers` entries
across 26 corpora whose rows had started agreeing behind a declared type, and a row that agrees on
its value and not on its OID belongs in `types` by definition.

> **The rule that produced most of this sheet's movement.**
> [ADR 0031](../adr/0031-rails-compatibility-is-measured.md) rule 2: an entry that starts agreeing
> is **deleted**, not left. Two harness rules were added this round because rule 2 cannot enforce
> itself:
>
> * **rule 4** — an `answers` entry whose *rows* agree belongs in `types`. A listed entry is never
>   compared, so a type difference in front of agreeing rows keeps a stale reason alive
>   indefinitely. 52 entries were in that state.
> * **`agrees`** — rule 2's staleness predicate was `actual == expected`, stricter than the
>   comparison every *unlisted* statement gets, which says an undeclared types column pins nothing.
>   An entry on a types-less corpus line was therefore **permanently** invisible to rule 2. Fixing
>   it reported 12 stale entries across 8 files, in corpora the unit that found it never touched.
>
> Both are in `crates/esker-sql/tests/parity_harness/mod.rs` with the incident that produced them.

### The five the user decided

These are not gaps waiting for a unit. PostgreSQL accepts every statement below — measured on
19beta1 as the superuser the suite connects as — and the refusal is the answer the user chose:

| Suite rows | Statement shape | Answer here |
|---|---|---|
| `fixtures` ×2, `referential_integrity` ×1 | `DO $$ DECLARE r record; BEGIN FOR r IN (…) LOOP EXECUTE … END $$` | `0A000` — general PL/pgSQL, refused by the standing "DO minimal" ruling ([ADR 0058](../adr/0058-a-do-block-is-two-templates-not-a-language.md)) |
| `postgresql_adapter` ×1 | `DELETE FROM pg_depend WHERE …` | refused — catalog DML |
| `persistence` ×1 | a trigger body that writes a primary key | refused — trigger bodies are status quo by ruling |

`crates/esker-sql/tests/user_decided_divergences.rs` pins them as **three** tests — one per
*statement shape* rather than one per suite row, since the five rows above are three refusals seen
from five places — and each asserts the text the node answers *today*: a declared divergence with
no test is a sentence in a document that nothing checks, and if one of these refusals ever changes
the test goes red and the ruling gets read again. Its third shape,
`UPDATE pg_catalog.pg_constraint SET convalidated = false`, is pinned there and currently reached
by no suite row at all, which is the right direction for a register to err in.

### Two wire-level divergences, recorded as decisions rather than left silent

No suite test reaches either — they were found by the wire-type census, not by the board — and both
are named here rather than buried in a baseline file (`run-107-routing.md`, "Two wire-level
divergences"):

| Statement | Node | PostgreSQL 19 |
|---|---|---|
| `COALESCE(1, 1.5)` | `float8` (701) | `numeric` (1700) |
| `(ARRAY[c::regtype])::regtype[]` | `ERROR: an oid is an integer, not Text("int4")` | `regtype[]` (2211) |

The first moved from `int8` to `float8` on the literal ladder — still wrong, differently; PostgreSQL
resolves the common type of `integer` and `numeric` as `numeric`. The second's message reads like an
internal type confusion rather than a deliberate refusal, which is the part worth fixing whatever is
decided about the type. They sit in `wire-types-baseline.txt` **so the gate can tell them from
anything newer**; if the board is the only measure they can stay, and if wire conformance is a goal
in its own right they are the next two.

> **The wire gate refused to let run 107 start, which is the point of having it.** The preflight
> exited **rc 4**: 22 baseline entries no longer mismatched and 4 mismatches were new. Each of the
> 22 was verified one by one against b4's batch, each of the 4 was triaged individually before the
> baseline was rebased 104 → 86, and the pre-rebase file is kept at
> `results/run-107/wire-baseline-before-run107.txt`. One of the four turned out not to be a node
> defect at all — the *oracle* lacks the `ltree` extension, a sampling gap in the census — and it is
> accepted so it stops re-firing rather than silently dropped.

> **`.config/nextest.toml`'s `cluster` group was asked two questions it had never been asked.**

> its own**: most of its reds happened *inside* it, because `max-threads = 1` bounds members against
> each other and against nothing else — so members now also run **last** (`priority = -20`), on a
> machine the rest of the suite has left. Verified by nextest's own `show-config test-groups`:
> `group: cluster (max threads = 1)` over 30 binaries and 124 tests. **This landed after

> observation and not a trend.

The standing rule is unchanged and was applied to all nine: *"bugs get **fixed**; \"known flake\" is
not an end state, and a timeout constant raised without a named broken assumption is not a fix."*

## 9. What this sheet cannot claim

v1's §8 was an erratum — a defect the sheet had not verified against, found the day after. This one
has no erratum: **nothing has been found that these numbers missed.** What follows is the other
half of that lesson, written before rather than after.

**A number is verified by the tests that ran, in the environment they ran in.** Three claims here
have a named limit, and each is a limit of *evidence* rather than a suspicion of the code:

* **§1 is the in-process backend.** The harness drives the real `esker-sql` binary over pgwire and
  proves the binary is the one it built, but the storage under it is in-process. A 99.48% pass rate
  over 10,134 tests says nothing about a real cluster of stores. §0's 4,148 tests are what covers
  that, and this round they include real-cluster binaries that were **not** in a serialised group
  and were losing deadlines under gate load — nine reds in §4. Every one was attributed before it
  landed, and two became fixes; none was retried into silence.
* **§0's Miri figure is the flagged form.** The flag has been unnecessary since `189d4117` by v1's
  own record, and this round did not re-run the plain form, so that record is another sheet older
  and still unchecked. It is one command.
* **§3's two wire divergences are outside every measure this sheet has.** No suite test reaches
  them; they exist here because a census went looking, and the reason they are written down as
  decisions is that the alternative — a line in a baseline file — is how a divergence stops being a
  question. The `ltree` case in the same census is the sharper version: the *oracle* was missing an
  extension, so a mismatch was measured against a gap in the measuring instrument.

**One thing this sheet actively refuses to round.** §2's budget is **147**, not the 140 that exists
