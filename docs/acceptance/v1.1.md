## 3. Declared divergences

A divergence is **declared** when a corpus line disagrees with PostgreSQL and the test says so in
words, with the reason. The harness fails on any disagreement that is *not* declared, so this list
is complete by construction — nothing diverges silently.

| | at `9d642ef0` | at v1 |
|---|---:|---:|
| **answers** — a value or an error differs | **345** | 427 |
| **types** — the value agrees and the column's type OID does not | **601** | 464 |

Both movements are the same story read twice. `answers` **fell** by 82 while the corpus grew by
1,932 statements, because three units deleted whole families rather than adding entries
([ADR 0084](../adr/0084-name-is-a-stored-type-and-its-tag-is-additive.md)'s `name`,
[ADR 0086](../adr/0086-a-folded-cast-keeps-the-type-it-named.md)'s folded cast,
[ADR 0087](../adr/0087-an-integer-literal-is-the-narrowest-type-that-holds-it.md)'s literal ladder).
`types` **rose** by 137 because entries **moved** into it: parity rule 4 found 52 `answers` entries
across 26 corpora whose rows had started agreeing behind a declared type, and a row that agrees on
its value and not on its OID belongs in `types` by definition.

> **The rule that produced most of this sheet's movement.**
> [ADR 0031](../adr/0031-rails-compatibility-is-measured.md) rule 2: an entry that starts agreeing
> is **deleted**, not left. Two harness rules were added this round because rule 2 cannot enforce
> itself:
>
> * **rule 4** — an `answers` entry whose *rows* agree belongs in `types`. A listed entry is never
>   compared, so a type difference in front of agreeing rows keeps a stale reason alive
>   indefinitely. 52 entries were in that state.
> * **`agrees`** — rule 2's staleness predicate was `actual == expected`, stricter than the
>   comparison every *unlisted* statement gets, which says an undeclared types column pins nothing.
>   An entry on a types-less corpus line was therefore **permanently** invisible to rule 2. Fixing
>   it reported 12 stale entries across 8 files, in corpora the unit that found it never touched.
>
> Both are in `crates/esker-sql/tests/parity_harness/mod.rs` with the incident that produced them.

### The fifteen the user decided

These are not gaps waiting for a unit. PostgreSQL accepts every statement below — measured on
19beta1 as the superuser the suite connects as — and the refusal is the answer the user chose.

**`postgres_fdw` moved here from `DEFERRED` on 2026-09-12.** A deferral is a decision that has
not been made, and a register cannot tell one of those from a queue; the user made it, so it is
declared. Nothing about the node changed with it: the extension is not in `AVAILABLE_EXTENSIONS`
(`crates/esker-sql/src/catalog/pg_catalog.rs`), whose seven entries are short for the reason that
list gives — *"an entry here tells a client this server has something"* — and a foreign-data
wrapper is a second storage engine reached through this one, which is a feature rather than a gap
in an existing one.

**It was already declared where a declaration is checked**, which is why this row changes a label
and nothing else: `crates/esker-sql/tests/drop_extension.rs`'s `Divergences::answers` carries
`CREATE EXTENSION IF NOT EXISTS "postgres_fdw"` with its reason and its capture line
(`pg19_extensions.txt:77`), pinned by `every_extension_answer_is_postgresql_19_s`. What was missing
was here: the register called it `DEFERRED`, and a reader could not tell that from a queue.

| Suite rows | Statement shape | Answer here |
|---|---|---|
| `foreign_table_test` ×10 | `CREATE EXTENSION "postgres_fdw"`, and the `CREATE SERVER … FOREIGN DATA WRAPPER postgres_fdw` and `IMPORT FOREIGN SCHEMA` statements behind it | `0A000 extension "postgres_fdw" is not available` — off `AVAILABLE_EXTENSIONS` by ruling |
| `fixtures` ×2, `referential_integrity` ×1 | `DO $$ DECLARE r record; BEGIN FOR r IN (…) LOOP EXECUTE … END $$` | `0A000` — general PL/pgSQL, refused by the standing "DO minimal" ruling ([ADR 0058](../adr/0058-a-do-block-is-two-templates-not-a-language.md)) |
| `postgresql_adapter` ×1 | `DELETE FROM pg_depend WHERE objid = 'ex_id_seq'::regclass AND refobjid = 'ex'::regclass AND deptype = 'a'`, the first of four writes | `42501` — catalog DML; re-read against the test on 2026-09-13, below |
| `persistence` ×1 | a trigger body that writes a primary key | refused — trigger bodies are status quo by ruling |

`crates/esker-sql/tests/user_decided_divergences.rs` pins the last three as **three** tests — one
per *statement shape* rather than one per suite row, since those five rows are three refusals seen
from five places — and each asserts the text the node answers *today*: a declared divergence with
no test is a sentence in a document that nothing checks, and if one of these refusals ever changes
the test goes red and the ruling gets read again. Its third shape,
`UPDATE pg_catalog.pg_constraint SET convalidated = false`, is pinned there and currently reached
by no suite row at all, which is the right direction for a register to err in.

**`pg_depend`, re-read against the statements that reach it (2026-09-13).** Run 127 attempt 6 —
the first real-topology pass to reach `postgresql_adapter_test.rb` — reported the same
`InsufficientPrivilege` run 116 did. The test is
`test_pk_and_sequence_for_with_collision_pg_class_oid`, and it writes four times: a `DELETE` of the
sequence's `'a'` dependency on its column, two `INSERT INTO pg_depend VALUES(…)` built from
`::regclass` literals, and a second `DELETE`. On PostgreSQL 19beta1, in one rolled-back transaction,
the superuser the suite connects as gets `DELETE 1`, `INSERT 0 1`, `INSERT 0 1`, `DELETE 1`, and a
role without superuser gets `42501 permission denied for table pg_depend` to the first two. The
node's statement tap for that test holds the first `DELETE` and then the test's own `DROP TABLE`s:
the refusal ended it, which is what `a_write_to_a_system_catalog_is_refused` pins. **It stays a
ruling rather than becoming a unit**, because `pg_depend` here is computed from the catalog's
records and has no row to delete: honouring the test needs a stored override that every reader of
dependencies consults — the join the test runs next, `pk_and_sequence_for`'s, among them — which is
a change to the catalog's consistency and not a few lines.

### A refusal that is PostgreSQL 19's own

§1 counts `bytea_test.rb` as `pass-match`, a file that *"fails identically on PostgreSQL 19"*. That
is a classification; this is the measurement under it, re-taken on 2026-09-13 because run 127
attempt 6 — the first real-topology pass to reach the file — reported it unchanged.

| Suite row | Statement | PostgreSQL 19beta1 | Answer here |
|---|---|---|---|
| `bytea` ×1 — `test_via_to_sql_with_complicating_connection` | `SET standard_conforming_strings = off`, on a second thread's connection | `0A000 non-standard string literals are not supported` (`call_bool_check_hook`, `guc.c`), and the same for `= false`, `TO 'off'` and `set_config('standard_conforming_strings', 'off', false)` | the same code and sentence: `crates/esker-sql/tests/corpus/pg19_set.txt:99`, replayed with no declared divergence by `tests/session_parameters.rs` |

**The test fails on the oracle itself.** Run against PostgreSQL 19 through the harness's
`config-pg19.yml`, it is `1 runs, 0 assertions, 0 failures, 1 errors` —
`PG::FeatureNotSupported: ERROR:  non-standard string literals are not supported`, raised in the
test's second thread. Its next statement, `SET escape_string_warning = off`, is reached on neither
server, and on 19 it would be `42704`: the parameter is gone. So this is neither a divergence nor a
gap, and there is nothing to build — a lexer that honoured `off` would be answering a setting
PostgreSQL 19 refuses.

### The new red, and the thing a pass cannot settle

`associations/eager_test.rb`'s two `EagerLoadingTooManyIdsTest` tests went 0F 0E → 0F 2E:
`XX000 request of about 17334584 bytes exceeds the 16777216-byte frame limit` over the 65,536-row
`citations` fixture. **The limit was not new** — `MAX_FRAME_SIZE` is in attempt 6's own binary, and
attempt 6 ran the file green with 737 assertions against this round's 735, exactly the two these
tests no longer reach.

> **What the pass could not settle, and did not guess at.** The overshoot is 557,368 bytes over
> about 65 thousand keys ≈ **8.5 bytes a key**. Separating *"the payload carries a new field"* from
> *"the keys got longer"* needs an isolating probe on **both** builds at unit level — not another
> ten-hour pass. The report said so and left it open as debt **#98**.

It was the estimate. `txn_payload_size` charged a flat six bytes a field, and since ADR 0114 §2 gave
a mutation a read timestamp it charged six more for a varint the encoder had been writing since
ADR 0057 §4 — so the estimate stood six bytes above every stamped mutation, which at READ COMMITTED
is every write a statement makes. Measured on both builds with one probe: `PUT` estimate
4,259,889 → 4,653,105 with the **frame 4,259,886 on both**. **Zero bytes changed on the wire**
(`5493a006`). `eager_test.rb` re-run alone on its own fresh cluster at **`872b8956`** returns
**197 runs, 737 assertions, 0F 0E** — attempt 6's numbers exactly, both tests passing by name.

> **That verification proves the file green run alone, not at file 179 of a pass that has already
> served 178 files.** No full pass has been run since, and §9's discipline applies to this section
> as much as to the ones above it.

### What this section cannot claim

* **One client, one file at a time**, 1,800 s watchdog per file. The only concurrency exercised is
  what an individual test creates. No sustained multi-client load, and no throughput or
  tail-latency figure.
* **No faults were injected.** Zero node restarts, zero wedges, zero stopped files is a statement
  about a healthy cluster's ten hours, not about one losing a store, a leader or a disk.
* **Ten and a half hours is the longest window measured**, and debt #109 — an insert whose cost
  grows **4.4×** with what the store already holds — is the shape most likely to bite a longer one.
* **The pass is `7193e5d9`; the release's last code commit is `0fc6fb18`**, 64 commits later, three of them below the SQL
  layer (#98, #99, #100 in `esker-proto`/`esker-client`; #84 in `esker-client`). Only #98 among
  them has a real-topology observation, and that one is a single file run alone. **This is §7's own
  rule applied to a later ref**, and the release notes repeat it rather than let it be inferred.
