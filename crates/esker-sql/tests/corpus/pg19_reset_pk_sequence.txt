# Resetting a primary-key sequence after fixtures load with explicit ids — as a real PostgreSQL
# 19beta1 answers it.
#
# **Run 45 ranking: 10 tests across 4 files** all failing with
# `duplicate key value violates unique constraint "posts_pkey"` / `"authors_pkey"` —
# `adapter_test.rb`, `callbacks_test.rb`, `cascaded_eager_loading_test.rb`,
# `connection_handling_test.rb`.
#
# **They are almost certainly one gap, not ten.** Those are the suite's own fixture tables. Fixtures
# are inserted with **explicit** ids, which does not advance the sequence, so the next
# ActiveRecord `create` asks for `nextval` and gets `1` — a row that already exists. Rails avoids
# this by calling `reset_pk_sequence!` after loading fixtures, and
# `postgresql/schema_statements.rb:227-251` shows exactly what that emits:
#
#     -- pk_and_sequence_for(table): a five-table catalog join, pinned verbatim below
#     SELECT MAX("id") FROM "posts"
#     SELECT seqmin FROM pg_sequence WHERE seqrelid = '"posts_id_seq"'::regclass   -- only if MAX is NULL
#     SELECT setval('"posts_id_seq"', <max>, <max ? true : false>)
#
# The first four statements of this file reproduce the failure the suite reports, and the rest pin
# the reset that removes it. So a lane fixing `setval` should expect the ranking row to disappear
# rather than shrink.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The `SELECT count(*)` at the end proves it left nothing behind and answers `0`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **Inserting explicit ids does not touch the sequence.** After `INSERT INTO posts (id, title)
#     VALUES (1,…),(2,…),(3,…)` the sequence still reads `last_value 1, is_called f`, and the next
#     defaulted insert is `23505 … DETAIL: Key (id)=(1) already exists.` — the ranking row, exactly.
#   * **`is_called` is the whole of the third argument's meaning.** `setval(seq, 3, true)` sets
#     `last_value 3, is_called t` and the next `nextval` is **4**; `setval(seq, 1, false)` sets
#     `last_value 1, is_called f` and the next `nextval` is **1**. Rails passes `true` when the table
#     has rows and `false` when `MAX(pk)` is NULL, which is why both forms are pinned here.
#   * **`setval` returns the value it set**, as `bigint`, and the two-argument form defaults
#     `is_called` to true — `setval(seq, 10)` then insert gives `11`.
#   * **`currval` is session state and fails before any `nextval` in that session**, with
#     `55000 currval of sequence "untouched_seq" is not yet defined in this session`. That is why
#     this whole corpus is captured in **one** psql session: a runner that opened a connection per
#     statement would record that error for every row and be wrong about all of them.
#   * **`lastval()` is not per-sequence** — it answers the last `nextval` of *any* sequence in the
#     session, and here it agrees with `currval` only because that was the last one touched.
#   * **The sequence's own metadata lives in `pg_sequence`, not in the sequence relation.**
#     `seqstart, seqincrement, seqmax, seqmin, seqcache, seqcycle` = `1|1|9223372036854775807|1|1|f`,
#     while `last_value`/`is_called` are read by selecting **from the sequence itself**. Two
#     different reads, and `reset_pk_sequence!` uses both.
#   * **`pg_get_serial_sequence` returns a schema-qualified `text`** — `public.posts_id_seq` — while
#     the name Rails passes to `setval` is the quoted bare name `"posts_id_seq"`. Both resolve.
#   * **A missing sequence is `42P01 relation "nosuchseq" does not exist`**, the ordinary relation
#     error, not a sequence-specific one.
#
# **THE THREE `last_value, is_called` PROBES ARE HELD BACK.** Reading a sequence *as a relation* is
# a second feature — PostgreSQL keeps `last_value`/`is_called` in the sequence itself and its
# parameters in `pg_sequence`, and this node stores one counter, the next value to hand out, from
# which `(5, false)` and `(4, true)` cannot be told apart. `setval`'s own semantics are right
# either way, which is what the inserts below measure; reporting the pair faithfully needs the flag
# stored beside the counter. The full capture is
# `esker-rails-harness/captures/pg19_reset_pk_sequence.txt`.
