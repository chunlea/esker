# Declarative partitioning — `PARTITION BY LIST`, `PARTITION OF`, and what `INSERT`/`SELECT` do
# through them — as a real PostgreSQL 19beta1 answers it.
#
# **Statements 781-786 of `postgresql_specific_schema.rb`**, verbatim as `ActiveRecord` emits them,
# interleaved with the `DROP TABLE IF EXISTS` lines it sends between them. Four of the nine refusals
# left at `3f02889` are these, which makes this the largest single unit on the board:
#
#     781  CREATE TABLE "measurements" (…) PARTITION BY LIST (city_id)        0A000
#     782  CREATE UNIQUE INDEX … ON "measurements" ("logdate", "city_id")     follow-on
#     784  CREATE TABLE "measurements_toronto" PARTITION OF measurements …    0A000
#     786  CREATE TABLE "measurements_concepcion" PARTITION OF measurements … 0A000
#
# `pg19_extension_inherits.txt` pins the *refusal* as a declared divergence; nothing pinned the
# behaviour. This does.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The two `SELECT count(*)` lines at the end prove it left nothing behind — `0` relations and `0`
# rows in `pg_partitioned_table`. As in `pg19_catalog_functions.txt`, the `\gdesc` pass runs after
# the rollback, so statements naming these tables have an **empty** declared-types column;
# catalog-only queries keep theirs, and the `pg_typeof` line pins `text` and `boolean`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **The suite's bound is an integer and the column is `character varying`.**
#     `FOR VALUES IN (1)` is accepted, coerced to the partition key's type, and printed back as
#     **`FOR VALUES IN ('1')`** — quoted. An implementation that stored the literal as written
#     diverges the moment `ActiveRecord` dumps the schema.
#   * **Four `relkind`s in one feature, and one of them is a capital letter.** The partitioned
#     table is `p`, each partition is an ordinary `r`, the partitioned index is **`I`**, and each
#     partition's own index is `i`. A `relkind IN ('r','p')` filter that forgets `I` still passes
#     every test that does not create a partitioned index.
#   * **`pg_get_indexdef` on the partitioned index says `ON ONLY public.measurements`** — the word
#     `ONLY` in the definition of the index that covers *every* partition — and it does **not**
#     change when partitions are attached, detached, or re-attached.
#   * **Statement 782 creates the index before a single partition exists, and every partition
#     created afterwards silently gets its own child index**, named `<partition>_<cols>_idx`:
#     `measurements_toronto_logdate_city_id_idx`. Two partitions produce two indexes the suite
#     never named, and it is the **child** index that a duplicate-key error names, not the parent's.
#   * **A unique index on a partitioned table must contain every partition column.** Dropping
#     `city_id` from it is `0A000 UNIQUE constraint on partitioned table must include all
#     partitioning columns`, `DETAIL: … lacks column "city_id" which is part of the partition key.`
#     `PRIMARY KEY` gives the same sentence with `PRIMARY KEY` substituted. The suite's index passes
#     only because `city_id` happens to be its second column.
#   * **Two different `23514`s, with two different messages and two different DETAIL shapes.**
#     Through the parent, a value with no partition is `no partition of relation "measurements"
#     found for row` / `DETAIL: Partition key of the failing row contains (city_id) = (99).`
#     Straight into the wrong partition it is `new row for relation "measurements_toronto" violates
#     partition constraint` / `DETAIL: Failing row contains (2, 2026-09-04, 33, 13).` — **the whole
#     row, not the key**.
#   * **`SELECT count(*) FROM ONLY "measurements"` is `0` while `FROM "measurements"` is every
#     row.** A partitioned table stores nothing itself; `ONLY` is the difference between the two,
#     and both spellings have to work.
#   * **An `UPDATE` that changes the partition key moves the row** instead of failing.
#     `tableoid::regclass` goes from `measurements_toronto` to `measurements_concepcion` and no
#     error is raised. Row movement is the default, not an opt-in.
#   * **An overlapping partition is `42P17`**, and the message names the partition it would overlap
#     — `partition "measurements_dup" would overlap partition "measurements_toronto"`.
#   * **A `DEFAULT` partition prints its bound as the bare word `DEFAULT`**, and once it exists the
#     `no partition found` error above stops being reachable.
#   * **`DETACH PARTITION` keeps the table and its rows.** The parent's `count(*)` drops by exactly
#     that partition's rows, `relispartition` becomes `f`, and `ATTACH PARTITION … FOR VALUES IN (2)`
#     puts all of it back. `DROP TABLE <partition>` is also allowed outright — the parent does not
#     protect it.
#   * **`partstrat` is a one-letter code (`l` for LIST) and `partattrs` is an `int2vector`.**
#     Neither is the word in the DDL.
#   * **RANGE bounds print `MINVALUE`/`MAXVALUE` back verbatim and are half-open**:
#     `FROM (MINVALUE) TO (10)` takes `9` and `FROM (10) TO (MAXVALUE)` takes `10`.
