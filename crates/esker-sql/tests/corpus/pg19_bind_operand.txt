# A **bind parameter as an operand of `=`** — the statements behind run 57's
# `operator does not exist: <type> = text`.
#
# 34 raises in run 57, in three spellings: `integer = text` (17), `bigint = text` (10),
# `boolean = text` (7). r1 traced them live out of the failing files with the runner's SQL hook,
# and the pattern is one line: every raise is a parameter on one side of `=` whose type this node
# resolved to `text` instead of taking it from the other side. The counter-cache
# `COALESCE(...) + $1` of `pg19_integer_plus_text.txt` is the same family, one operator along.
#
# `\bind` is what captured these: Parse/Bind/Execute with **untyped** parameters, which is where
# `ActiveRecord` is and where the resolution under test happens. `PREPARE` would type them from the
# DDL and there would be nothing to measure.
#
# Two things a probe gets wrong, and both are why this survived one:
#
# * **Every traced statement is aliased** — `INNER JOIN "categories" "group"`, `r.favorite`,
#   `rl.last_read` — and the qualifier was matched against each relation's *own* name, so an alias
#   found nothing and the parameter kept the `text` fallback. A probe written without an alias
#   passes against the bug.
# * **`(1 = $3)` has no column in it at all.** An integer literal on the left types the parameter
#   on the right, and five characters in the middle of a long statement refused the whole of it.
#   `('a' = $1)` is the other half of that rule and types nothing: two `unknown`s are both `text`
#   on a real server, which is why it still answers.
