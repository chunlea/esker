# What a real PostgreSQL 19beta1 does with a **subquery in an expression** -- phase 12 unit 1
# (`docs/plans/phase-12-subquery.md`). Every line below was put to the `esker-pg19` container
# before a line of the implementation was written, in ONE session inside `BEGIN ... ROLLBACK` with
# `ON_ERROR_ROLLBACK on`, so the shared oracle is left exactly as it was found.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# It builds its own tables. `sq_e` is empty on purpose: an empty subquery is the case every rule
# below turns on.
#
# THE FIVE THINGS THAT WOULD HAVE BEEN GOT WRONG BY READING RATHER THAN MEASURING:
#
#   1. **An empty subquery beats a NULL left-hand side.** `NULL IN (SELECT ... no rows)` is
#      **false**, not NULL -- where `NULL IN (1)` is NULL. So emptiness is decided *before* the
#      three-valued rule, and an implementation that short-circuited on a NULL operand (which is
#      exactly what `IN (list)` correctly does, because PostgreSQL's grammar has no empty list)
#      answers NULL and drops a row. Same for `NULL = ANY (empty)` = f, `NULL <> ALL (empty)` = t
#      and `NULL > ALL (empty)` = t.
#   2. **Two different messages for one mistake.** A subquery with two columns is
#      `42601 subquery must return only one column` where it is used as a *scalar*, and
#      `42601 subquery has too many columns` under `IN` and under `ANY`/`ALL`. Same SQLSTATE,
#      different sentence, and a client that greps the text sees two.
#   3. **A scalar subquery returning no rows is NULL, and returning two is `21000`** -- an error,
#      not the first row. The error is per *execution*, so it is only reachable when the rows are.
#   4. **`ANY`/`ALL` are three-valued in the same asymmetric way `IN` is, per operator**: a
#      definite match makes `ANY` true whatever NULLs are beside it (`100 = ANY (100,200,NULL)`
#      is t), a definite failure makes `ALL` false (`100 > ALL (100,200,NULL)` is f), and with
#      neither, a NULL anywhere makes it unknown (`300 > ALL (100,200,NULL)` is NULL).
#   5. **A scalar subquery in a target list is named after the subquery's own column** -- `max`,
#      `id`, `count`, or the inner `AS` -- while `EXISTS (...)` is named `exists` and `NOT EXISTS`,
#      `IN` and `= ANY` are all `?column?`. Measured with `psql`, which the corpus format cannot
#      record; `tests/subquery.rs` asserts it.
#
# And one that reads as a trap and is not: `EXISTS (SELECT 1/0 FROM sq_e)` is **false** rather than
# `22012`, because a subquery over no rows evaluates no expression.
