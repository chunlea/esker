# `array_agg`, its `ORDER BY`, and `pg_enum` — boot statement 26.
#
#     SELECT type.typname, type.OID, n.nspname,
#            array_agg(enum.enumlabel ORDER BY enum.enumsortorder) AS value
#     FROM pg_enum AS enum JOIN pg_type AS type ON (type.oid = enum.enumtypid) …
#
# is how `ActiveRecord` loads the enum types a schema has. It wanted three things at once: the
# relation `pg_enum`, the aggregate `array_agg`, and an `ORDER BY` **inside** an aggregate's
# parentheses, which this node refused by name along with every other aggregate clause.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **Over no rows `array_agg` is NULL, not an empty array.** `array_agg(id) … WHERE id > 99` is
#     NULL where `count(id)` is 0, and the two are not interchangeable: an empty array `IS NULL` is
#     false. The line below asserts the NULL and the `IS NULL` beside it.
#   * **NULLs are kept, not skipped.** Every other aggregate here drops them; this one collects
#     them, so `array_agg(n ORDER BY n)` over a column with a NULL is `{10,20,30,NULL}` — and
#     `ORDER BY n DESC` is `{NULL,30,20,10}`, because the default null placement follows the
#     direction. One rule, two answers, and an implementation that dropped NULLs loses a row.
#   * **The `ORDER BY` sorts by expressions the aggregate does not return.**
#     `array_agg(id ORDER BY g, id DESC)` is `{2,1,4,3}`, which is neither input order nor `id`
#     order — so the sort key has to travel with the value rather than be recovered from it.
#   * **`pg_enum` is empty here and on this database**, and completely so here:
#     `CREATE TYPE … AS ENUM` is `0A000`, so nothing can ever put a row in it.
