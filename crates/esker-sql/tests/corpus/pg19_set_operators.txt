# THINGS REASONING WOULD GET WRONG
#
#   * **`EXCEPT ALL` is multiset subtraction, not "the same rows without the dedup step".** The left
#     side holds `2` twice and the right holds it once, so one `2` survives; `EXCEPT` dedups first
#     and answers `1` alone. `INTERSECT ALL` is the same arithmetic from the other side — the count
#     of each value is the *minimum* of the two sides, which is why it answers `2 ; 3` here and not
#     the four rows a naive pairing would give.
#   * **`INTERSECT` binds tighter than `EXCEPT`.** `a EXCEPT b INTERSECT b` is `a EXCEPT (b
#     INTERSECT b)` and answers `1`. A left-to-right reading answers the same thing on this data by
#     accident, which is exactly why the operator's precedence has to be taken from the grammar and
#     not from an example.
#   * **The arms resolve by the same rule `UNION` uses**: `integer INTERSECT numeric` settles on
#     `numeric`, and a bare literal against a `text` column settles on `text`. So the type
#     unification is reusable; what is not is the row combination.
#   * **Both refusals name the operator**: `each EXCEPT query must have the same number of columns`
#     and `INTERSECT types integer and text cannot be matched`. This node's `SetOperationTypes`
#     hard-codes the word `UNION`, which is only correct while the other two never reach it.
#   * The table is created and dropped outside a transaction, and the drop is a second pass, so the
#     declared types survive the `\gdesc` pass that runs afterwards in a fresh session.
