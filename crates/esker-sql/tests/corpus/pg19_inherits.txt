# THINGS REASONING WOULD GET WRONG
#
#   * **Inheritance is a read rule, not just a DDL one.** `SELECT … FROM parent` returns the
#     child's rows too, and so does `UPDATE parent …` and `DELETE FROM parent …`. `ONLY parent`
#     is the spelling that excludes them. A node that copied the columns and stopped would answer
#     `1` where a real server answers `2` — a wrong answer, not a missing feature, which is why
#     the DDL cannot land without the scans.
#   * **The child inherits defaults, including the parent's sequence.** `ic`'s `id` defaults to
#     `nextval('ip_id_seq'::regclass)` — the *parent's* counter, not one of its own — so rows
#     inserted through either table draw from the same sequence and cannot collide.
#   * **It does not inherit indexes or the primary key.** `pg_index` for the child is empty, so
#     the uniqueness the parent's key promises does not hold across the pair.
#   * **A child's own columns come after the inherited ones**, whatever order they were written in.
#   * **Dropping the parent is `2BP01`**, naming the child as the dependent object.
#   * A column redeclared with a different type is `42804`, and it carries **two** `DETAIL` lines.
