# **The parentheses `pg_get_expr` adds** — one probe per expression shape, generated columns and
# defaults alike.
#
# `virtual_column_test#test_schema_dumping`, run 105. The catalog was identical on both servers and
# the node's dump was otherwise complete — every virtual column, `stored: true`, and the nested
# casts `length((name)::text)` and `upper((name)::text)` exactly as PostgreSQL prints them. The
# whole of the failure was one pair of parentheses:
#
#   expected  /t\.virtual\s+"column2",\s+type: :integer,\s+as: "\(column1 \+ 1\)", stored: true$/i
#   node      t.virtual "column2", type: :integer, as: "column1 + 1", stored: true
#
# Same family as run 102's check-constraint parenthesisation, in the opposite direction: there the
# node added a pair PostgreSQL omits, here it omitted a pair PostgreSQL adds.
#
# # The rule, and it is one function's
#
# `pg_attrdef.adbin` holds one expression and `pg_get_expr(adbin, adrelid)` prints it, for a
# generated column and for a default alike — so the rule is the same in both, and this file asks it
# in both. It is [`crate::catalog::ExprShape`], already measured for an index expression:
#
#   operator or connective   one pair        (c1 + 1)   (c1 > 0)   (c1 IS NOT NULL)
#   bare call                none            length(t)  COALESCE(c1, 0)  now()
#   value, cast, CASE        none            7          c1         (1)::bigint
#
# A **bare column** is a value and prints bare, which is the row an index expression can never
# reach — a column there is a column key, never an expression key — and the one this file adds.
#
# # THINGS REASONING WOULD GET WRONG
#
#   * **The written parentheses are not the printed ones.** `((c1 + 1))` prints `(c1 + 1)` and
#     `c1 + 1` prints `(c1 + 1)`: the deparser's pair, not the user's, which is why normalising at
#     the point the text is taken is not cosmetic.
#   * **A function call takes none, and `COALESCE` is a call** — not an operator, even though it is
#     spelled like a keyword.
#   * **The pretty form drops them again**: `pg_get_expr(adbin, adrelid, true)` is `c1 + 1`. Two
#     functions, two answers, one stored expression.
#   * **`information_schema.columns.column_default` prints the same string** as `pg_get_expr`, so
#     the rule reaches a second view — and for a *generated* column that view is NULL instead
#     (`generation_expression` carries the text), which is why the generated probes here read
#     `pg_attrdef` and not `information_schema`.
