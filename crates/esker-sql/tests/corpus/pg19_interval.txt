# `interval`, as a real PostgreSQL 19beta1 answers it — tier 2
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)'s roadmap). OID 1186,
# sixteen bytes, `typcategory` T. Stored as three independent fields — **months, days,
# microseconds** — and almost every surprise below follows from that one fact.
#
# `ActiveRecord` cares about this type before it cares about the values: its **third** boot
# statement is `SET intervalstyle = iso_8601`, so the style below is not a curiosity, it is the
# one Rails reads its answers in.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table, dropping whatever a previous run left, so a replay of `cut -f1` is
# byte-identical. The table is deliberately *not* dropped at the end: `sesscap.py` asks `\gdesc`
# for the declared types after the session closes, and a dropped table makes that column empty.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **Equality is not identity of representation.** `'1 mon' = '30 days'` is **`t`**, `'1 year'
#     = '360 days'` is **`t`**, and `'1 mon 1 day' = '31 days'` is **`t`** — comparison converts a
#     month to 30 days and a day to 24 hours. Storage does not: `'1 mon 1 day'` prints as
#     `1 mon 1 day` forever, and `'400 days'` never becomes `1 year 1 mon 5 days`. So two intervals
#     can be equal and print differently, and an implementation that normalised on the way in
#     would print the wrong text for every one of them.
#   * **Signs are per field.** `'1 day' - '12 hours'` is **`1 day -12:00:00`**, a value with a
#     positive day and a negative time, and it is equal to `'12:00:00'`. Nothing normalises it.
#   * **Four output styles, and the one Rails asks for is not the default.** Measured, all four,
#     on one value: `postgres` `1 year 2 mons 3 days 04:05:06`; `iso_8601` `P1Y2M3DT4H5M6S`;
#     `sql_standard` `+1-2 +3 +4:05:06`; `postgres_verbose`
#     `@ 1 year 2 mons 3 days 4 hours 5 mins 6 secs`. And `-1 day` prints **`-1 days`** in the
#     default style — plural where the positive is singular — `P-1D` in ISO, and `@ 1 day ago` in
#     verbose.
#   * **Months carry into years; days do not carry into months.** `'1 year 13 months'` is
#     `2 years 1 mon`, but `'400 days'` stays `400 days` and `'25 hours'` stays `25:00:00`. Only
#     `justify_days`/`justify_hours`/`justify_interval` do the rest, and they are functions
#     precisely because the type does not.
#   * **A fractional unit cascades into the next one down**: `1.5 months` is `1 mon 15 days`,
#     `1.5 days` is `1 day 12:00:00`, `1.5 hours` is `01:30:00`.
#   * **The typmod is a bitmask, and it is the fourth encoding in this corpus.** Measured out of
#     `pg_attribute`: `interval(3)` is `2147418115`, `interval day` is `589823`,
#     `interval day to hour` is `67698687`, `interval year to month` is `458751`. It is a field
#     mask in the high bits with the precision in the low ones — *not* a plain number — and
#     asking `format_type` for a number that is not one is `XX000 invalid INTERVAL typmod: 0x3`,
#     an internal-error class. Compare `varchar`'s length+4, `timestamp`'s bare precision and
#     `numeric`'s `(p << 16) | s` + 4.
#   * **Two range SQLSTATEs, and a third for syntax.** `'178956971 years'` is
#     `22008 interval out of range` — the whole value overflows; `'2147483648 months'` is
#     **`22015 interval field value out of range`** — one *field* overflows, and `22015` appears
#     nowhere else in this corpus. Bad text is `22007`. Three codes for three failures.
#   * **`interval(p)` trims trailing zeros where `numeric(p,s)` pads them.** `'1.5 seconds'` at
#     `interval(3)` is `00:00:01.5`, not `00:00:01.500`. The declared precision is a maximum here
#     and an exact width there.
#   * **`interval(9)` is not an error** — `'interval(9)'::regtype` is 1186 — the same silent
#     tolerance `timestamp(9)` and `time(7)` have.
#
# THE STYLE TAIL IS TRIMMED, AND THIS SAYS SO
#
# The capture ends with the same SELECT under four `IntervalStyle` settings. Three of those four
# lines are gone from this copy: the statement text is identical in all four, the harness keys a
# divergence by that text, and the last one — after `RESET` — *agrees*, so the same key would have
# to be both listed and not. The `SET` statements are kept, because they are answered; what is
# dropped is the three readings under a style this node does not print in. `tests/interval.rs`
# declares the gap as `STYLE`, and `captures/pg19_interval.txt` in the harness has all four.
