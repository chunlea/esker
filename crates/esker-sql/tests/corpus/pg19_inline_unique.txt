# Inline `UNIQUE` table constraints — statement 779 of `postgresql_specific_schema.rb`, which
# declares four of them in one `CREATE TABLE`: a plain one, `DEFERRABLE INITIALLY IMMEDIATE`,
# `DEFERRABLE INITIALLY DEFERRED`, and `NULLS NOT DISTINCT`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`NULLS NOT DISTINCT` means the table holds at most one row with a NULL there.** Every later
#     `INSERT` that simply *omits* the column collides with the first — `23505 … Key
#     (position_4)=(null) already exists`, with `null` lower-case and in parentheses. Four of the
#     inserts below fail for a column they never mention.
#   * **`DEFERRABLE INITIALLY IMMEDIATE` is not deferred at all.** It checks at the statement, like
#     any other unique constraint; the only difference is what the catalog says and what
#     `pg_get_constraintdef` prints. `INITIALLY DEFERRED` is the one that really waits — both rows
#     go in and the violation is raised by `COMMIT`, which rolls the whole transaction back.
#   * **`pg_get_constraintdef` drops `INITIALLY IMMEDIATE` and keeps `DEFERRABLE`**, so the text
#     that comes out is not the text that went in.
#   * **The clause sits on opposite sides in the two renderings**: a constraint prints
#     `UNIQUE NULLS NOT DISTINCT (position_4)` and its index prints
#     `… USING btree (position_4) NULLS NOT DISTINCT`.
#   * **`CREATE UNIQUE INDEX` is not a constraint.** It builds an index identical to the one a
#     `UNIQUE (a)` builds and gets **no** `pg_constraint` row — the count below stays at one
#     after a second unique index appears. A node that read every unique index as a constraint
#     would report one the schema never declared.
