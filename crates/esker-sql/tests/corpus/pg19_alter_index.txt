# `ALTER INDEX` — 18 tests over 7 files, and one shape.
#
# `ActiveRecord` sends **only `RENAME TO`**, from two places: `rename_index` renames any index
# (`postgresql/schema_statements.rb:590`), and `rename_table` follows a table rename with the
# primary key's index (`:467`) because PostgreSQL does not rename it for you. The MySQL adapter's
# `ALTER INDEX … VISIBLE` is a different adapter's statement and is not sent here.
#
# Captured against `esker-pg19` on 127.0.0.1:55432.
#
# THINGS REASONING WOULD GET WRONG
#
#   * **Renaming an index renames its constraint.** `ALTER INDEX ai_pkey RENAME TO ai2_pkey` moves
#     `pg_constraint.conname` too, and so does renaming the index a `UNIQUE` constraint owns. They
#     are one name in two catalogs, not two names — which is the same fact `DROP CONSTRAINT` uses
#     from the other side.
#   * **A name already taken is `42P07`, not `42P01` or `42710`** — `relation "…" already exists`,
#     because an index shares its namespace with tables and sequences.
#   * **A missing index is `42P01 relation "…" does not exist`**, the *relation* message rather than
#     an index-specific one, and `IF EXISTS` turns it into a `NOTICE … skipping` that succeeds.
#   * **`ALTER INDEX` accepts a table.** `ALTER INDEX ai RENAME TO ai_renamed` renames the *table*
#     `ai` without complaint: the statement is the generic rename wearing another keyword. Nothing
#     the suite sends does this, and a node that refuses it is diverging on a shape no client uses.
#   * **`SET (fillfactor = …)` and `SET TABLESPACE` both succeed and change nothing observable
#     here**, while `ALTER COLUMN n SET STATISTICS` on an ordinary column is `0A000` with a HINT
#     pointing at the table's column. None of the three is sent by the suite.
#   * `pg_indexes.indexname` is a `name` and `pg_constraint.contype` a `"char"`.
