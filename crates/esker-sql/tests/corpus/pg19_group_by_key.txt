# `must appear in the GROUP BY clause` — run 57's third row, 6 tests over 2 files.
#
# **The coordinator's hypothesis, and the capture says yes**: PostgreSQL accepts a bare column when
# the `GROUP BY` contains that table's **primary key**. It is a *functional dependency* — grouping
# by a key means one row per group of that table, so every other column of it has exactly one value
# and needs no aggregate. `ActiveRecord` writes it constantly, because `group(:id)` on a relation
# selecting `*` is the shape every one of these tests has.
#
# Things reasoning would get wrong:
#
# * **It is per table, not per query.** `GROUP BY f.id` frees every column of `f` and none of `a`,
#   even in the same select list — measured, and an implementation that treated "some key is
#   grouped" as a licence would accept a genuinely ambiguous query.
# * **`HAVING` sees the same rule**: `GROUP BY f.id HAVING f.name = 'one'` runs, where
#   `GROUP BY f.name HAVING f.name = 'one'` runs for the ordinary reason. Only the first needs the
#   dependency.
# * **The message names the column the way the query did** — `"a.credit_limit"` when the table has
#   an alias and `"gb_firms.rating"` when it does not — and the class is `42803`.
#
# The capture runs inside `BEGIN … ROLLBACK`; error probes sit in `SAVEPOINT`/`ROLLBACK TO`, and
# the `SELECT count(*)` after the `ROLLBACK` proves it left nothing behind.
#
# Rows start with a literal `'r'` because `sesscap.py` drops output rows that begin with a space.#
# ---- run 104: the clause the dependency was NOT applied to ----
#
# `ORDER BY` was missing, and it is the clause `ActiveRecord` actually reaches this through.
# `Company.includes(:comments).order(:rating).ids` sends `GROUP BY "companies"."id" ORDER BY
# "companies"."rating"`, where the ordered column is nowhere else in the statement — not in the
# select list, not in the `HAVING` — so a widening that walked only those two freed nothing and the
# node answered `42803` for a query PostgreSQL answers with fifteen rows
# (`calculations_test#test_ids_with_includes_and_non_primary_key_order`).
#
# Four more things the ORDER BY section pins, each measured rather than reasoned:
#
# * **a positional grouping key frees the table too**: `GROUP BY 2` where position 2 is the key.
#   Position 1 is the leading `'r'` every row here projects, which is a trap of this file's own
#   making — the first attempt at this probe wrote `GROUP BY 1`, grouped by a constant, and got a
#   `42803` naming `gb_firms.id` that looked like a finding about positions;
# * **a composite key frees its table only when every column of it is grouped**: `GROUP BY a` over
#   `PRIMARY KEY (a, b)` leaves `extra` bare, in the select list and in the `ORDER BY` alike;
# * **a `UNIQUE NOT NULL` column determines nothing.** `GROUP BY u` is `42803` about `extra` even
#   though one row per group is just as true — PostgreSQL's `check_functional_grouping` reads the
#   *primary key* and nothing else, so a node that generalised to "any unique constraint" would
#   accept queries a real server refuses;
# * **the other table's column stays bare** in `ORDER BY` as it is in the select list, which is the
#   per-table rule this file already had, in the one clause that had not been asked.
