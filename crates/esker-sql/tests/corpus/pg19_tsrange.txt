# `tsrange` — the five range values `range_test.rb` inserts, and how they come back.
#
# **Run 50 ranking: `the type tsrange is not supported`, 46 tests in one file**
# (`adapters/postgresql/range_test.rb`). That file declares eight range columns; `tsrange` is the one
# the board names because it is the first the node refuses, and `t.tsrange :ts_ranges, array: true`
# means the array form is in the same table.
#
# The five rows below are the file's own fixtures (`insert_range(id: 101…105)`), in its order:
# closed `[a,b]`, half-open `[a,b)`, unbounded-above `[a,]`, infinite, and empty.
#
# Things reasoning would get wrong:
#
# * **A timestamp range is NOT canonicalised.** `int4range '[1,10]'` comes back `[1,11)` because the
#   subtype is discrete; `tsrange '[a,b]'` comes back exactly `["a","b"]`, because a timestamp has no
#   successor function. Both are in the rows below, side by side, because an implementation that
#   canonicalises everything or nothing is wrong either way.
# * **The bound characters are data.** `[`, `]`, `(`, `)` and the empty slot after a comma survive the
#   round trip and `lower_inc`/`upper_inc`/`lower_inf`/`upper_inf` read them back.
# * **`'empty'` is a value, not NULL**, and it is not the same as `NULL`: `isempty` is `t` for one and
#   the whole value is NULL for the other. `range_test.rb` asserts both, separately.
# * **The text output depends on `DateStyle`**, the way `pg19_date.txt` records for `date` — and AR
#   sets `intervalstyle` but not `DateStyle`, so the server default is what it reads.
# * **`test_escaped_tsrange` uses year -1000**, which PostgreSQL renders `1000-01-01 … BC`. A parser
#   that assumes four digits and no suffix fails that test and nothing else.
# * **There are TWO range arrays in that file, not one**, and this capture only had the first until
#   run 58: `t.tsrange :ts_ranges, array: true` (`:33`) and **`t.tstzrange :tstz_ranges, array:
#   true`** (`:35`). Run 58 is why the second is here — `tsrange`, `tstzrange` and `tsrange[]` all
#   landed and the file's 46 tests moved intact onto `the type tstzrange[] is not supported`, one
#   type along. An array type has to be built per element type; three of the four is still zero
#   tests passing.
# * **An array of `tstzrange` carries the time-zone dependency twice over.** Each element renders
#   through the session's `TimeZone`, so the *same stored array* prints differently in two sessions —
#   the rows below take one array in `UTC` and again in `Pacific/Auckland` and they differ, while the
#   `tsrange[]` beside it does not move. Anything that compares an array's text across sessions is
#   comparing the wrong thing.
#
# The whole capture runs inside `BEGIN … ROLLBACK`; error probes sit in `SAVEPOINT`/`ROLLBACK TO`,
# and the `SELECT count(*)` after the `ROLLBACK` proves it left nothing behind. `\gdesc` runs in a
# second session after that rollback, so statements naming `tsr` have an **empty** declared-types
# column; the `pg_typeof` lines pin the types instead.
#
# Rows start with a literal `'r'` because `sesscap.py` drops output rows that begin with a space.

# ---- BOUNDS MAY BE QUOTED, and the suite always quotes them (run 68) ----
#
# Every literal above sends its bounds bare — `[2010-01-01 14:30, 2011-01-01 14:30]` — and that is
# NOT how `range_test.rb` writes them. It writes `[''2012-01-02'', ''2012-01-04'']`, which reaches the
# server as `['2012-01-02', '2012-01-04']`: the bounds are quoted *inside* the range literal. This
# capture missed that for ten rounds, and run 68 is where it cost something — b4's user-defined range
# types landed, `floatrange` and `stringrange` both work, and the file's 46 tests did not move because
# every one of its inserts was refused with `invalid input syntax for type date: "'2012-01-02'"`,
# the quotes passed through to the element parser.
#
# Quoting inside a range literal is not optional to support: PostgreSQL's own OUTPUT quotes any bound
# containing a space, comma, quote, backslash or bracket — the `tsrange` rows above come back as
# `["2010-01-01 14:30:00","2011-01-01 14:30:00"]` — so a parser that cannot read quoted bounds cannot
# read what the same server just printed.
