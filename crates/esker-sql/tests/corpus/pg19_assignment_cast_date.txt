# A `date` column assigned a `timestamp with time zone` — the assignment cast `insert_all` relies on.
#
# **Run 51 ranking #4: `column "…" is of type date but expression is of type timestamp with time
# zone`, 57 tests over 2 files** — 58 of the 59 raises are `insert_all_test.rb`, one is
# `instrumentation_test.rb`. No test writes that cast. The statement was traced out of the failing
# file with the runner's SQL hook and it is AR filling the timestamp columns of `books`:
#
#     INSERT INTO "books" ("name","author_id","created_at","updated_at","updated_on")
#     VALUES ('New Book', 1, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP)
#     ON CONFLICT ("id") DO UPDATE SET updated_at=…
#
# `books.updated_on` is `t.date` (`test/schema/schema.rb:157`) while `created_at`/`updated_at` are
# `datetime`, and `insert_all` writes `CURRENT_TIMESTAMP` — a `timestamptz` — into all three. It is
# the same expression landing in two different column types, and PostgreSQL accepts it because there
# is an **assignment** cast from `timestamptz` to `date`.
#
# Things reasoning would get wrong:
#
# * **Assignment context is not expression context.** `INSERT INTO t (d) VALUES (CURRENT_TIMESTAMP)`
#   is fine; `SELECT … WHERE d = CURRENT_TIMESTAMP` is **not**, and neither is a comparison in an
#   `ON CONFLICT` predicate. `pg_cast.castcontext` is `'a'` for this pair — allowed when assigning to
#   a column, not when combining values. An implementation with one cast table for both contexts is
#   wrong in one direction or the other.
# * **The result depends on the session `TimeZone`.** `timestamptz` -> `date` is "which calendar day
#   is that instant, here", so the same instant is two different dates in two time zones. The rows
#   below take the same value in `UTC` and in `Pacific/Auckland` and they differ. The conversion
#   happens **once, at assignment**: the row inserted under `Pacific/Auckland` reads back as the same
#   date after `SET TimeZone = 'UTC'`, because what was stored is a date and not an instant.
# * **The reverse direction is `'i'`, implicit** — `date` -> `timestamp` and `date` -> `timestamptz`
#   need no cast at all, which is why the asymmetry cannot be modelled as one "compatible" relation.
# * **`ON CONFLICT … DO UPDATE SET` is assignment context too**, including `excluded.<col>`.
# * **What has no assignment cast raises `42804` and names both types**, which is the message shape a
#   refusal has to match.
#
# **Re-captured from r1's `captures/pg19_assignment_cast_date.txt`** with two changes, both about
# replaying it rather than about the oracle.
#
# **Five statements printed today's date and now compare against `CURRENT_DATE` instead.** A corpus
# is replayed on a day that is not the day it was captured — r1's rows say `2026-09-04` and the node
# under test answered `2026-08-30` — so a statement whose answer *is* "today" fails for a reason
# that has nothing to do with the feature. `updated_on = CURRENT_DATE` asks the same question and
# keeps asking it tomorrow. The two time-zone probes are untouched because they pin a **fixed**
# instant, which is exactly why they can print their dates.
#
# And the `pg_cast` probes, `CURRENT_TIMESTAMP::date` and the whole `Pacific/Auckland` section are
# in `SAVEPOINT`s — three things this node refuses, each of which would otherwise hide the feature
# behind it. The Auckland section is guarded **as a block** rather than statement by statement, so
# its `tz probe` row is rolled back on both sides and the counts after it agree. That is about this node and not the oracle:
# `pg_cast` is not a relation here, and run bare one `0A000` aborted the replay and took the
# forty-three statements after it — which are the whole feature. Every answer is byte-identical to
# r1's.
#
# **One line of r1's prose is contradicted by its own row**, and the row is the truth: the header
# says `WHERE d = CURRENT_TIMESTAMP` "is not" fine, and the capture shows it answering **0 rows**.
# `date` -> `timestamptz` is an *implicit* cast, so the comparison is legal and simply false — the
# date is promoted to midnight and the instant is later. What expression context lacks is the cast
# in the *other* direction, which is the one this unit is about.
#
# The whole capture runs inside `BEGIN … ROLLBACK`; error probes sit in `SAVEPOINT`/`ROLLBACK TO`,
# and the `SELECT count(*)` after the `ROLLBACK` proves it left nothing behind.
#
