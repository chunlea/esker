# What PostgreSQL 19 answers to every full-text statement the ActiveRecord suite sends.
#
# **Run 79 ranking: `the type TSVECTOR is not supported`, 52 tests over 2 files — the head of the
# board since run 60, and now more than four times the next row.** The two files want quite
# different things and only one of them is about full text:
#
# * `adapters/postgresql/full_text_test.rb` (3 tests) declares `t.tsvector "text_vector"`, writes
#   the literal `'text' 'vector'`, reads it back, updates it to `'new' 'text' 'vector'`, and dumps
#   the schema expecting `t.tsvector "text_vector"`. No operators, no functions, no index.
# * `adapters/postgresql/schema_test.rb` (48 tests, none of them about full text) dies in a shared
#   setup that builds two schemas each holding `things` with a `name_vector tsvector` column, then
#   **two GIN indexes**: one over the plain column and one over the expression
#   `(to_tsvector('english', coalesce(things.name, '')))`. One unsupported column type is costing 48
#   tests that never mention full text.
#
# So the corpus below is in three parts: the declaration and round-trip path, the index path, and
# the operator/function surface a `tsvector` implementation has to answer for even though these two
# files do not reach all of it.
#
# Things reasoning would get wrong:
#
# * **`tsvector` is not a string, and its normalised form is not the input.** `'text' 'vector'` is
#   already lexeme form and round-trips unchanged, which is what `full_text_test` asserts; but
#   `to_tsvector('english', 'The Fat Cats')` normalises, stems and drops stop words, and the output
#   ordering is by lexeme, not by input position. A round-trip test that writes lexeme form and one
#   that writes prose are testing different things.
# * **Position and weight are part of the value.** `to_tsvector` records positions (`'cat':3`), and
#   `setweight` attaches A-D; `strip()` removes both. Two tsvectors that print differently can hold
#   the same lexemes, so equality is over the whole value including positions.
# * **`@@` is not symmetric in type.** `tsvector @@ tsquery` and `tsquery @@ tsvector` both exist,
#   and `text @@ text` exists too via implicit `to_tsvector`/`to_tsquery` — with the *default* text
#   search configuration, not `english`. The rows below pin `default_text_search_config` so the
#   difference is visible rather than assumed.
# * **`||` over tsvector concatenates and renumbers.** Positions in the right operand are shifted by
#   the maximum position of the left, so `a || b` is not `b || a`.
# * **A GIN index over an expression is not the same object as one over a column**, and
#   `pg_index.indexprs` is where the expression lives — `indkey` reads 0 for it. The suite's
#   `schema_test` builds both kinds on the same table, so an implementation that supports only the
#   column form still fails the file.
# * **`tsquery` rejects what `tsvector` accepts.** A bare word is a valid tsvector and a valid
#   tsquery; `'a b'` is a two-lexeme tsvector but a **syntax error** as a tsquery.
#
# The whole capture is one `BEGIN … ROLLBACK`. Its tables live and die inside that block, so the
# `\gdesc` pass — which runs in a SECOND session after the rollback — cannot see them: queries that
# name `tsv` or `things` carry rows but an empty types column, exactly as `pg19_tsrange.txt` does.
# The expression and catalog rows carry both. Savepoints wrap every probe expected to raise, so one
# error cannot abort the block and turn every later answer into `25P02`. The `SELECT count(*)` lines
# after the `ROLLBACK` prove nothing persisted.
