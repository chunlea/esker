# What an aggregate's result **type** is, as PostgreSQL 19beta1 declares it.
#
# `array_agg` is the one this file is for: its result is the array type of its argument, and this
# node declared `text` for every one of them — right rows, wrong type, in three corpora at once
# (`tests/array.rs`, `tests/array_subquery.rs`, `tests/values_relation.rs`). The rest of the
# aggregate surface is captured beside it so that fixing one cannot quietly move another.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# Captured in one session inside `BEGIN … ROLLBACK`, in this order.
#
# THINGS REASONING WOULD GET WRONG
#
#   * **An untyped argument is `42725`, not `text[]`.** `array_agg('lit')` and `array_agg(NULL)`
#     are "function array_agg(unknown) is not unique" — PostgreSQL has one `array_agg` per element
#     type and an `unknown` matches all of them. Answering `text[]` there would be answering where
#     a real server raises.
#   * **Zero rows is NULL and the declared type is unchanged**: `array_agg(i4)` over no rows is
#     NULL and still declares `integer[]`. The type is the *argument's*, decided before a row is
#     read, which is why an empty group cannot make it `text`.
#   * `DISTINCT`, `ORDER BY` and an expression argument change nothing: `array_agg(i4 + 1)` is
#     `integer[]` because `i4 + 1` is an `integer`.
#   * **`array_agg(i4)[1]` is a syntax error on a real server too** — subscripting a function call
#     needs parentheses — so it is `42601` here and that is parity, not a gap.
#   * `sum` widens and `avg` does not follow it: `sum(int8)` is `numeric` where `avg(int8)` is
#     `numeric` too, but `sum(int4)` is `bigint` where `avg(int4)` is `numeric`.
#   * **An untyped argument is `42725` for three of the six and `text` for the other three.**
#     `sum('lit')`, `avg('lit')` and `array_agg('lit')` are "is not unique" — one candidate per
#     input type, and an `unknown` matches all of them — while `min('lit')` answers `lit`,
#     `max(NULL)` answers NULL and `count('lit')` answers 1. Six measurements, not one rule.
#   * **`(array_agg(i))[1]` is the spelling that works**: the parentheses are PostgreSQL's grammar,
#     not a style, and without them `[` is `42601` — a statement a real server refuses.
