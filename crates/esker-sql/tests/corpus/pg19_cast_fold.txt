# The cast matrix's pairs written as **literals** — PostgreSQL 19beta1.
#
# The twin of `pg19_cast_matrix.txt`, which probes every pair with a column. Here the operand is a
# constant, so the answer comes from `parse::lower`'s fold rather than from `exec::cursor`'s
# `Expr::Cast` arm, and the two files together are what says a conversion cannot be right in one
# caller and wrong in the other. Both have been, in both directions.
#
# Things reasoning would get wrong:
#
#   * **A float into an integer rounds half to EVEN and a `numeric` rounds half AWAY from zero.**
#     `2.5::float8::int4` is 2 and `2.5::numeric::int4` is 3, in one statement each.
#   * **A `"char"` is a signed byte.** `chr(200)::"char"::int4` is -61, not 195.
#   * **`200::int4::"char"` is `22003`**, not the byte 200: only -128..127 is a `"char"`.
#   * **A `bytea` and an integer are the same bytes, big-endian**, padded on the left with zeros
#     to the *target's* width — so `'\xff'::bytea::int2` is 255 and `'\xffff'::bytea::int2` is -1,
#     and one byte too many is `22003` rather than a truncation.
#   * **`65::int4::bytea` is `\x00000041`**, the number's four bytes, not `\x3635` — which is what
#     the ASCII of the digits `6` and `5` would give, and what a text round trip does give.
