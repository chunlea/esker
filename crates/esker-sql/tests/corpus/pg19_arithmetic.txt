# The facts a reading of the operators would get wrong, all measured here:
#
#   * `-2 ^ 2` is **4**, not -4: unary minus binds tighter than `^`. And `2 ^ 3 ^ 2` is 64, so `^`
#     is left-associative — the opposite of the mathematical convention.
#   * **`NULL::int4 / 0` is NULL, not `22012`.** Strictness comes first: an operator with a NULL
#     operand is never evaluated, so the divisor is never looked at. An implementation that checks
#     for a zero divisor before checking for NULL raises where PostgreSQL returns a row.
#   * **`%` does not exist for `double precision`** — `42883`, not a modulo. Only the integers and
#     `numeric` have one.
#   * **A float divided by zero raises `22012`**; it does not yield `Infinity`. And a float
#     overflow raises `22003 value out of range: overflow` rather than saturating.
#   * **`^` yields `double precision` whatever it is given** — `2::int4 ^ 3::int4` is a float.
#   * Integer division truncates **toward zero** (`-7 / 2` is -3, not -4) and `%` takes the sign of
#     the **dividend** (`-7 % 3` is -1).
#   * Overflow is at the **declared width**: `32767::int2 + 1` is `22003 smallint out of range`,
#     and so are `abs((-32768)::int2)`, `-((-2147483648)::int4)` and `int4 min / -1`.
#   * `int4 + float4` is **double precision**, not `real`: there is no mixed operator, so both
#     sides go to `float8`. `float4 + float4` really is `real`.
#   * `'a' + 1` is `22P02`, not `42883`: the unknown literal is resolved to `integer` first and
#     then fails to parse. `true + 1` is the `42883`.
