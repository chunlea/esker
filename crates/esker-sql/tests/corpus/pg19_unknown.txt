# What a real PostgreSQL 19beta1 does with an **untyped literal** -- the quoted string it calls
# `unknown` -- in a comparison. This is the specification for the wrong answer
# `docs/plans/phase-9-rails.md` §6 recorded and `tests/in_list.rs` inherited: `SELECT 1 = '1'`
# answered `f` here where a real server says `t`.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THE RULE, which is three cases and not one:
#
#   1. **One side unknown, the other typed** -- the unknown is *read as that type*, by that type's
#      own input function. `1 = '1'` is `t`; `1 = '01'`, `1 = ' 1'` and `1 = '+1'` are all `t`,
#      because that is what `int4in` accepts. A string that will not read is the input function's
#      own error, not a comparison that answers false: `1 = 'x'` is `22P02`, `1 = '1.5'` is
#      `22P02`, and a timestamp raises `22007` rather than `22P02`.
#   2. **Both sides unknown** -- both become `text`, and this is the case that tells the rules
#      apart. `'1' = '01'` is **`f`** where `1 = '01'` is `t`: with nothing to type them against
#      there is no integer anywhere in the expression, and `'1'` and `'01'` are two different
#      strings.
#   3. **An explicit type is not unknown any more.** `1 = '1'::text` is `42883 operator does not
#      exist: integer = text` -- the cast makes the right side `text` before resolution runs, and
#      there is no `integer = text` to call. The same statement without the cast is `t`.
#
# AND THE TRAP, which is `IN`:
#
#   an `IN` list is typed as a **whole**, not pairwise against the operand. `'01' IN ('1', 1)` is
#   **`t`** -- the `1` gives every unknown in the expression the type `integer`, including the
#   operand, so it is `1 IN (1, 1)`. `'01' IN ('1')` with the `1` removed is `f`, because then
#   nothing is typed and it is two strings. An implementation that reconciled each item against
#   the operand left to right would answer `f` for the first, and it would be a wrong answer
#   rather than a refusal. The coercion also happens at **plan time**: `1 IN (NULL, 'x')` is
#   `22P02` and not NULL, though the NULL alone could have decided it.
#
# TWO THINGS THIS NODE CANNOT REPRODUCE, both measured here and declared in
# `tests/unknown_literal.rs`:
#
#   * `pg_typeof(1)` is **`integer`**, not `bigint` -- a bare integer constant is `int4`, so
#     `1 = '2147483648'` is `22003 value "2147483648" is out of range for type integer`. This
#     node's bare constant is `int8` and answers `f`. It closes when `int4` exists.
#   * `pg_typeof(1.5)` is **`numeric`**. This node has no `numeric` and a decimal literal is a
#     `double precision` everywhere, `SELECT 1.5` included -- so `0.1 = '0.1000000000000000000001'`
#     is `f` on a real server and `t` here. ADR 0031's numeric backlog.
CREATE TABLE unk (id int8 PRIMARY KEY, n text, d float8, b bool)		-
INSERT INTO unk VALUES (1, 'one', 1.5, true)		-

# --- function's own error, never a `false`
