# Inline `UNIQUE` table constraints — `NULLS [NOT] DISTINCT` and `DEFERRABLE` — as a real
# PostgreSQL 19beta1 answers them.
#
# **Statement 779 of `postgresql_specific_schema.rb`**, verbatim as `ActiveRecord` emits it, and the
# second thing rung 4 stops on once the plpgsql function at 762 lands. `pg19_nulls_not_distinct.txt`
# already pins the **index** form and the `ALTER TABLE … ADD CONSTRAINT` form; the suite sends
# neither. It sends four `CONSTRAINT … UNIQUE` clauses *inside* `CREATE TABLE`, three of them
# `DEFERRABLE`, and `DEFERRABLE` appears nowhere in the corpus except `pg19_foreign_key.txt`.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`.** Error probes sit in `SAVEPOINT` /
# `ROLLBACK TO` so one refusal does not turn every line after it into `25P02`. The two
# `SELECT count(*)` lines at the end prove it left nothing behind, and both answer `0`.
#
# **The price of that rule, stated rather than hidden:** `sesscap.py` fills the declared-types
# column from a `\gdesc` pass in a *second* session, which runs after the `ROLLBACK` — so every
# statement naming `test_unique_constraints` has an **empty** types column. Statements that read
# only `pg_constraint` or `information_schema` still have theirs, and the `pg_typeof` line near the
# end pins `boolean`, `boolean`, `text` for the three columns an implementation has to produce.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`DEFERRABLE` does not change *whether* a row is refused — it changes *which statement*
#     carries the refusal.** The `INITIALLY DEFERRED` constraint accepts the offending `INSERT`
#     with no error at all, the row is really there (`count(*)` answers `2`), and the `23505`
#     arrives on the **`SET CONSTRAINTS … IMMEDIATE`** that follows. Same SQLSTATE, same DETAIL,
#     different statement. An implementation that checks uniqueness at `INSERT` time gets the right
#     answer at the wrong moment, and the suite's three constraints exist precisely to tell those
#     apart.
#   * **`SET CONSTRAINTS ALL DEFERRED` does not defer a non-deferrable constraint.** `ALL` means
#     all *deferrable* ones. The plain `UNIQUE (position_1)` still raises at `INSERT` with `ALL
#     DEFERRED` in force — while naming that same constraint explicitly is **`42809 constraint
#     "…" is not deferrable`**, an error rather than a no-op. Two spellings of the same request,
#     one silent and one refused.
#   * **`DEFERRABLE INITIALLY IMMEDIATE` is still deferrable at runtime.** `SET CONSTRAINTS … 
#     DEFERRED` on it succeeds, and the violation then moves to the `SET CONSTRAINTS … IMMEDIATE`
#     exactly as for the `INITIALLY DEFERRED` one. `INITIALLY` sets the starting mode, not the
#     capability.
#   * **`pg_get_constraintdef` drops `INITIALLY IMMEDIATE` and keeps `INITIALLY DEFERRED`.**
#     `UNIQUE ("position_2") DEFERRABLE INITIALLY IMMEDIATE` comes back as
#     `UNIQUE (position_2) DEFERRABLE`. This is the "keep only what differs from the default" rule
#     the `DESC` index and `NULLS DISTINCT` both met — and it is what `ActiveRecord`'s schema
#     dumper reads, so printing the input back verbatim is a divergence.
#   * **`NULLS NOT DISTINCT` prints between `UNIQUE` and the column list**, and explicit
#     `NULLS DISTINCT` prints as **nothing**: `UNIQUE NULLS NOT DISTINCT (position_4)` versus
#     `UNIQUE (position_3)`. Combined with `DEFERRABLE` the order is
#     `UNIQUE NULLS NOT DISTINCT (position_2) DEFERRABLE INITIALLY DEFERRED`.
#   * **`bigserial primary key` catalogues THREE constraints, and one of them is not a key.**
#     Beside the `p` and the `u` rows there is `test_unique_constraints_id_not_null` with
#     `contype = 'n'` and `pg_get_constraintdef` = **`NOT NULL id`** — a `pg_constraint` row for a
#     `NOT NULL`, which older PostgreSQL did not have. And `information_schema.table_constraints`
#     reports that same row as **`CHECK`**, not `NOT NULL`: the two catalogs disagree by design, and
#     an implementation that makes them agree breaks whichever one the client is reading.
#   * **The two ways to violate `NULLS NOT DISTINCT` have different messages.** A second NULL
#     inserted is `duplicate key value … DETAIL: Key (position_4)=(null) already exists.`; the same
#     table with two NULLs already in it refuses the `ALTER TABLE … ADD CONSTRAINT` with
#     `could not create unique index "u_nnd_deferred" DETAIL: Key (position_2)=(null) is
#     duplicated.` — **"is duplicated", not "already exists"**, and a different message text before
#     the DETAIL. Both are `23505`.
#   * **The NULL prints as `null`** — lower case, unquoted, no `NULL` keyword — and **`UPDATE` into
#     a NULL is checked too**, which is the half an implementation that only hooks `INSERT` misses.
#   * **`indnullsnotdistinct` lives on the index and `condeferrable`/`condeferred` live on the
#     constraint.** One feature, two catalogs, and `conindid` is the only thing joining them. The
#     backing index takes the constraint's own name.
#   * **A column named in a key that does not exist is `42703 column "nosuchcol" named in key does
#     not exist`** — not `42P01`, and the message says "named in key" rather than the usual
#     "does not exist" phrasing for a column reference.
#   * **`is_deferrable` and `initially_deferred` are `YES`/`NO` strings of type
#     `character varying(3)`**, not booleans.
