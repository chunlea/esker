# **How `pg_get_expr` prints a numeric constant**, measured in every position that reads one.
#
# `docs/plans/debts-v1.1.md` #22: `exec::ddl::deparse_literal` prints a number bare whatever its
# type, and PostgreSQL does not. The row moved off #12 when b4's `int4` ladder landed — the node
# now knows `1` is an `int4` and `1::bigint` an `int8`, so the information the printer needs is
# there and the printer does not use it. This file is what it should do instead.
#
# **Three forms, and which one is used is a property of the *node*, not of the value.**
#
#   * **bare `N`** — a constant whose type is the one the literal form defaults to. An integer
#     literal defaults to `integer` and a decimal literal to `numeric`, so `1` prints `1` and
#     `1.5` prints `1.5`, and `1::integer` and `1.5::numeric` print the same because the cast names
#     the type it already had;
#   * **`(N)::type`** — a **cast node** over such a constant, whether a user wrote it or coercion
#     inserted it. Written: `1::bigint` is `(1)::bigint`. Inserted: `nm > 1` is
#     `(nm > (1)::numeric)` and `greatest(i8, 1)` is `GREATEST(i8, (1)::bigint)`, because the
#     comparison and the function pick a common type and the literal is coerced up to it;
#   * **`'N'::type`** — a **bare constant whose type is not the default**, which is what the scanner
#     produces for an integer too wide for `integer` and what constant-folding produces for a
#     signed one: `9223372036854775807` is `'9223372036854775807'::bigint`, `-1` is
#     `'-1'::integer`, and `99999999999999999999999999` is `'…'::numeric`.
#
# The three compose exactly as the tree does. `-1::bigint` is `(- (1)::bigint)`, because `::` binds
# tighter than unary minus, so it is an operator over a cast and not a signed constant; and
# `(-1)::bigint` is `('-1'::integer)::bigint`, a cast over a folded signed constant. Neither is
# reasoning — both are rows below.
#
# **`i8 > 1` prints `(i8 > 1)`.** No coercion happens: PostgreSQL has an `int8 > int4` operator, so
# the literal stays an `integer` constant of the default type and prints bare. The same statement
# against `numeric` or `double precision` has no such operator and the literal *is* coerced, which
# is why `nm > 1` and `f8 > 1` show a cast and `i8 > 1` and `i2 > 1` do not. A rule about the
# *column's* width would get all four wrong.
#
# **The same rule in four readers**, which is the other half of why this file exists: a generated
# column (`pg_get_expr(adbin)`), a `DEFAULT` (the same row read the same way), an index key
# (`pg_get_expr(indexprs)`) and a `CHECK` (`pg_get_constraintdef`) all print
# `(i8 + (1)::bigint)`-shaped text from the same deparser.
#
# **A `DEFAULT` stores the expression as written and *not* the assignment cast to the column.**
# `f8 double precision DEFAULT 1.5` prints `1.5` — a `numeric` constant of the default type — while
# `DEFAULT 1.5::double precision` prints `(1.5)::double precision`. So the column's type is not a
# clue about what its default prints as, and `pg_attrdef` is the expression rather than the value
# the column will take.
#
# Captured against esker-pg19 (PostgreSQL 19beta1) with
# `sesscap.py captures-src/pg19_numeric_literal_deparse.txt.in`, inside one `BEGIN ... ROLLBACK`,
# and verified idempotent by replaying `cut -f1` of the result through the same recorder.
