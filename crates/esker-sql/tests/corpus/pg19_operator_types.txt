# Comparing two columns of different types — as PostgreSQL 19beta1 answers it.
#
# Run 46's ranking rows `operator does not exist: bigint = text` (119 tests, 29 files) and
# `integer = text` (50, 14) are **that message being right**: a comparison between an integer and a
# text is `42883` on a real server too. The rows came through `PG::Connection#exec_params`, and a
# bind gets its type from the context it sits in, which `0badfe7` fixed.
#
# What this file is for is the **other direction**, found while confirming that: this node answered
# `WHERE id = title` with *no rows* where a real server refuses the statement. Answering where
# PostgreSQL raises is ADR 0031's worst class — a query that silently finds nothing is a bug a
# suite reports as a wrong count, not as an error.
#
# Captured in one session inside `BEGIN … ROLLBACK`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **The message names the two types in the order they were written.** `id = s` is
#     `bigint = text` and `s = id` is `text = bigint`; they are two different operators that both
#     do not exist, and a node that normalised the pair would name one of them wrongly.
#   * **`character varying` is spelled out**, not `varchar`: `id = v` is
#     `bigint = character varying`.
#   * **A cast on the *other* side is what makes it work**, and only one of the two: `id = s::text`
#     is the same refusal, while `id::text = s` answers. The cast has to bring the operands
#     together, not push them apart.
#   * **`IN` carries it**: `id IN (s)` is `bigint = text`, the operator the list would have used.
#   * `id = n` (bigint against integer) and `s = v` (text against character varying) both answer —
#     those pairs are one family, and only a cross-family pair is `42883`.

# **An `unknown` stops being one the moment it passes through a constructor**, and that is the
# other half of the rule above. `id = '1'` works because the literal takes the column's type;
# `id = (SELECT '1')`, `id = CASE WHEN true THEN '1' ELSE '2' END`, `id = COALESCE('1','2')` and
# `id = ANY(ARRAY['1','2'])` are each `42883 operator does not exist: bigint = text`, because a
# scalar subquery, a `CASE`, a `COALESCE` and an `ARRAY[]` are **values of a settled type** and
# the coercion does not reach through them. `pg_typeof` says so directly: each of the first three
# is `text` and the fourth is `text[]`.
#
# The same four with one typed branch all answer, which is what makes this a rule about *unknown*
# and not a ban on constructors — and `COALESCE(NULL, '1')` is `text` too, because a NULL carries
# no type either, so a `COALESCE` of a NULL and an unknown is all-unknown.
