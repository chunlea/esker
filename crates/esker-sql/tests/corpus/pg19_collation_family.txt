# **Which expressions PostgreSQL will not derive a collation for, and which contexts ask.**
#
# `docs/plans/debts-v1.1.md` #19 recorded one row of this: a real server refuses
# `GENERATED ALWAYS AS (upper('a')) STORED` with `42P22 could not determine which collation to use
# for upper() function`, and this node builds the column. The brief was to measure the **family**
# before deciding anything, and the family has two independent halves.
#
# ## Half one: which operations need a collation
#
# An operation that *uses* a collation is refused when every input is a literal; one that does not
# use one is accepted. The message names the operation, and the three names are its own:
#
#   REFUSED  upper('a')  lower('a')  upper('a'::text)  upper(1::text)   -> "upper()/lower() function"
#   REFUSED  ('a' < 'b')  ('a' = 'b')  replace('abc','b','x')           -> "string comparison"
#   REFUSED  ('ab' LIKE 'a%')                                           -> "LIKE"
#
#   accepted  'a'   ('a')::text   (1 + 2)
#   accepted  length('a')  octet_length('a')  md5('a')  substr('abc',1,2)  btrim(' a ')
#   accepted  ('a' || 'b')   COALESCE('a','b')   CASE WHEN true THEN 'a' ELSE 'b' END
#   accepted  upper(t)  upper(u)  (t || 'x')  (t < 'b')      -- a COLUMN settles it
#
# `replace` is in the first group and `substr` in the second, which is the pair worth keeping: both
# are string functions and only one compares. Concatenation needs no collation at all. Neither of
# those is derivable from a name — they are rows here.
#
# ## Half two: only a **column** settles it, and only in some contexts
#
# An explicit `COLLATE` on a literal does **not** make a stored expression acceptable, wherever it
# is written — measured one placement at a time:
#
#   REFUSED  upper('a' COLLATE "C")        upper('a'::text COLLATE "C")
#   REFUSED  upper('a') COLLATE "C"        (('a' COLLATE "C") < 'b')
#   accepted upper(t COLLATE "C")          -- prints back as `upper((t COLLATE "C"))`
#
# And the same expression is refused or answered according to **where it is written**:
#
#   SELECT upper('a')                          answers `A`
#   DEFAULT upper('a')                         accepted, and prints `upper('a'::text)`
#   DEFAULT ('a' < 'b')                        accepted, and prints `('a'::text < 'b'::text)`
#   GENERATED ALWAYS AS (upper('a')) STORED    42P22
#   CREATE INDEX ON t ((upper('a')))           accepted -- the rows below say so
#   CHECK (upper('a') = 'A')                   accepted -- and so do they
#
# **Corrected 2026-09-10, and the rows below were right all along.** The two lines above said
# `42P22` and this header's own capture says `-`: `CREATE INDEX g1co_ix1 ON g1co ((upper('a')))`
# and `ALTER TABLE g1co ADD CONSTRAINT g1co_ck1 CHECK (upper('a') = 'A')` are both **accepted** by
# 19beta1, and re-measuring built the index and the constraint. **One context asks, not three.**
#
# The reading that came with the wrong table is refuted by it: *"a generated column, an index key
# and a check constraint are values that get compared, and a comparison is what needs the
# collation"* -- an index key and a `CHECK` are compared and do not ask. It was marked as a reading
# rather than a measurement, and it is struck rather than deleted, because a corpus that hides its
# wrong readings teaches nothing.
#
# ## Half three: there are two mechanisms, and an empty table cannot tell them apart
#
# The first pass ran every probe against a table with **no rows**. Asking the same statements with
# one row in it separates them:
#
#                                        empty table   one row
#   SELECT u < v          (C vs POSIX)   accepted      42P22 string comparison
#   GENERATED AS (u < v)  (C vs POSIX)   accepted      42P22 string comparison
#   GENERATED AS (upper('a'))            42P22         42P22 upper()/lower() function
#
# * a conflict between two **implicit** collations is an **evaluation-time** error -- it fires when
#   a row reaches the operator, in a query and in a generated column alike, and never on an empty
#   table;
# * a generated column's expression needing a collation **derivable from a column** is a **DDL**
#   check -- it fires with or without rows, and only there.
#
# Reading the first as the second is how "three contexts" happened. See
# [ADR 0096](../../../../docs/adr/0096-a-collation-is-derived-from-a-column-or-from-nothing.md).
#
# **Two read-backs go through `replace(..., '|', '!')`, and debt #20 is why.** A corpus row is
# `statement TAB types TAB rows` with columns split on `'|'` and no escape, so a *value* holding a
# pipe is parsed as extra columns: `('a'::text || 'b'::text)` came back as five fields against
# three and the row "disagreed" while reading identically in the report. Second time that has cost
# a round — `pg19_deparse_parens.txt` has the same wrapper for the same reason — which is what the
# register's #20 is for.
#
# **Every probe the *node* might refuse is guarded too, not only the ones PostgreSQL refuses.**
# A capture is taken against PostgreSQL, so a row it accepts looks safe — and three of these are
# rows this node declines, which abort the replay's transaction and swallow whatever follows
# (parity rule 3 reports it). `collation_name` is the sharpest case: PostgreSQL answers `C` and
# this node has no such column, so nothing about the capture suggested a savepoint was needed.
# In a corpus whose subject *is* a gap, guard every probe.
#
# Captured against esker-pg19 (PostgreSQL 19beta1) with
# `sesscap.py captures-src/pg19_collation_family.txt.in`, inside one `BEGIN ... ROLLBACK`, every
# expected refusal guarded by its own `SAVEPOINT`/`ROLLBACK TO` — the first pass had one refusal
