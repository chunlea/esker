# What a real PostgreSQL 19beta1 does with an aggregate -- the specification unit 1 of
# `docs/plans/phase-9-rails.md` was written from, and the evidence ADR 0031 argues over.
#
# Nothing here was written from the documentation or from memory. Every line was put to the
# running `esker-pg19` container on 2026-08-31 over the fixture below, with `\set VERBOSITY
# verbose` for the refusals, and what is recorded is what came back.
#
#   query <tab> types <tab> rows        the result, and the types `\gdesc` declared for it
#   query <tab> !SQLSTATE message       PostgreSQL refused it; DETAIL and HINT follow the message
#
# In the `rows` column ` ; ` separates rows, `|` separates columns, `\N` is SQL NULL, and a lone
# `-` is **no rows at all** -- which is a different answer from one row of NULL and the whole of
# what the empty-input rules are about.
#
# The `types` column is what a client's `RowDescription` says, so it is where the one divergence
# this node cannot close shows up: PostgreSQL types `sum(bigint)` and `avg(bigint)` as `numeric`
# and there is no `numeric` in this crate (ADR 0031).
#
# THE SIX A READER WOULD HAVE GOT WRONG, and the reason this file exists rather than a paragraph:
#
#   * `min(boolean)` and `max(boolean)` DO NOT EXIST. They are `42883`, not an ordering of `f` and
#     `t` -- so refusing them is parity and implementing them would be the divergence.
#   * an ungrouped aggregate with a `HAVING` that is false returns NO ROWS, where the same query
#     without the `HAVING` returns one row of zero. `HAVING` filters the one implicit group.
#   * `GROUP BY` may name an output alias (`GROUP BY gg`) and `HAVING` may NOT (`HAVING c > 0` is
#     `42703 column "c" does not exist`). The two clauses do not share a name scope.
#   * `sum(bigint)` over two `9223372036854775807`s is `18446744073709551614`. PostgreSQL's sum is
#     `numeric` and cannot overflow; ours is `int8` and errors instead, which is ADR 0031's
#     declared divergence and the row this file exists to keep honest.
#   * `GROUP BY ()` is the **grand total**, not a grouped query: over an empty table it still
#     returns one row of zero, where `GROUP BY g` over the same table returns none.
#   * the wrong *number* of arguments and the wrong *types* get different `DETAIL` sentences, and
#     the number-of-arguments one names the types anyway: `count(n, g)` is
#     `function count(bigint, text) does not exist`.
#
# The fixture, replayed by `tests/aggregate_parity.rs` before the first query:
#
#   CREATE TABLE agg (id int8 PRIMARY KEY, g text, n int8, f float8, b bool, ts timestamptz, y bytea);
#   INSERT INTO agg VALUES
#     (1, 'a',  10,   1.5,   true,  '2024-01-01 00:00:00+00', '\x01'),
#     (2, 'a',  20,   2.5,   false, '2024-06-01 12:00:00+00', '\x02'),
#     (3, 'b',  NULL, NULL,  NULL,  NULL,                     NULL),
#     (4, 'b',  -5,   0.5,   true,  '2023-01-01 00:00:00+00', '\xff'),
#     (5, NULL, 7,    'NaN', false, '2025-01-01 00:00:00+00', '\x00');

#   CREATE TABLE big (id int8 PRIMARY KEY, n int8);
#   INSERT INTO big VALUES (1, 9223372036854775807), (2, 9223372036854775807);
#
