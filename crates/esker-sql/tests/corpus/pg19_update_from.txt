# `UPDATE … FROM` with a self-alias — as a real PostgreSQL 19beta1 answers it.
#
# What a **joined** `update_all` sends. `ActiveRecord` cannot put a join on an `UPDATE`, so for a
# relation carrying one it does not wrap the selection in a subquery the way `delete_all` does
# (`pg19_write_in_subquery.txt`) — it aliases the target, puts the join in a `FROM`, and ties the
# two together in the `WHERE`. Verbatim from `sql.active_record`, with the bind written out:
#
#     UPDATE "vl_comments" "__active_record_update_alias" SET "body" = $1
#       FROM "vl_comments" INNER JOIN "vl_posts" ON "vl_posts"."id" = "vl_comments"."vl_post_id"
#       WHERE "vl_comments"."id" = "__active_record_update_alias"."id"
#
# It is in the same 9 test files as the subquery form, and `pg19_write_in_subquery.txt` declares it
# as a divergence until this file is answered.
#
# Captured in one session against the `esker-pg19` container, inside `BEGIN … ROLLBACK`, error
# probes in `SAVEPOINT` / `ROLLBACK TO`. The final `SELECT count(*)` proves it left nothing behind.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **A target row the join matches MANY times is updated ONCE.** Three matching `FROM` rows and
#     `SET hits = a.hits + 1` leaves `hits` at **1**, not 3, and the tag is `UPDATE 1`. PostgreSQL
#     documents which of the matching rows is used as *not readily predictable*; what it does not
#     leave open is how many times the target is written. An implementation that loops over the
#     join output writes it once per match and answers 3.
#   * **The `FROM` entry is a separate scan, and it sees the rows as they were.**
#     `SET body = c.body || '!'` over `FROM vl_comments c` appends to the **pre-statement** value
#     for every row, so three rows holding `joined` all become `joined!` — not `joined!!`, and not
#     one row's new value leaking into the next. Pinned twice, because `||` is a shape of its own
#     this node refuses by name: `SET hits = c.hits + 1 FROM vl_comments c WHERE c.id =
#     (a.id % 3) + 1` reads each row through the *next* one, so a node whose `FROM` scan saw its
#     own writes would answer `1, 1, 2` where a real server answers `1, 1, 1`.
#   * **An alias replaces the target's name, it does not add one.** With `UPDATE vl_comments a`,
#     `vl_comments.id` is `42P01 invalid reference to FROM-clause entry` with a HINT naming the
#     alias — even though the table is right there. That is exactly what frees the name for the
#     `FROM` entry that shares it, which is the whole mechanism of the Rails statement.
#   * **A `SET` target is never qualified**, and the error is about a *column* rather than a
#     relation: `SET a.body = 'q'` is `42703 column "a" of relation "vl_comments" does not exist`,
#     because `a.body` is read as the column `a` and a field of it.
#   * **An unaliased target and a `FROM` entry of the same table are fine** as long as the entry
#     has an alias of its own: `UPDATE vl_comments SET … FROM vl_comments c WHERE c.id =
#     vl_comments.id` updates one row. It is the *name* that has to be unambiguous, not the table.
#   * **A bare column that both sides have is `42702`**, not the target's: `WHERE id = 1` over a
#     target and a `FROM` entry of the same table is ambiguous.
#   * `RETURNING` names **both sides** — `RETURNING a.id, a.body, p.title` — because by then the
#     target row and its `FROM` row are one row.
#   * `DELETE … USING` is the same mechanism spelled for the other verb, and is here so that the
#     day it is needed its answer is already measured.
