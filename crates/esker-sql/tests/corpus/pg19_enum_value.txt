# An **enum as a column value** — storing one, reading it back, and ordering by it — as a real
# PostgreSQL 19beta1 answers it.
#
# ADR 0050 decided the shape: the label's **ordinal** is what is stored, `user_type` on the column
# carries the type's identity, and the label is rendered through the catalog on the way out. This
# capture is what that has to reproduce. It is `activerecord/test/cases/adapters/postgresql/
# enum_test.rb`'s `setup` and the statements its 19 tests send, plus the ordering probes that are
# the whole reason the ordinal is the storage.
#
# Captured in one session with `scratchpad/sesscap.py`, wrapped in `BEGIN … ROLLBACK`, error probes
# in `SAVEPOINT` / `ROLLBACK TO`. The `SELECT count(*)` at the end proves it left nothing behind and
# answers `0`. The `\gdesc` pass runs after the rollback, so a statement naming `mood` has an
# **empty** declared-types column; `pg_typeof` is used as a *value* wherever the type matters.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **Declaration order is sort order, and it is not the alphabet.** `mood` is
#     `('sad','ok','happy')`, so `ORDER BY current_mood` gives `sad, ok, happy` and
#     `'happy'::mood < 'ok'::mood` is **`f`** — happy is 3 and ok is 2. A node storing the label as
#     text answers `happy, ok, sad` and `t`, and both look plausible in isolation. This is the one
#     fact the whole unit exists for.
#   * **`min` and `max` follow the ordinal too**: `sad` and `happy`, not the alphabetical
#     `happy` and `sad`.
#   * **NULLs sort last ascending and first descending**, as for any type — `ORDER BY x DESC` puts
#     the NULL row first, which is easy to read as a bug in the enum ordering and is not.
#   * **An enum does not compare with `text`.** `current_mood = 'sad'::text` is
#     **`42883 operator does not exist: mood = text`** with the "add explicit type casts" HINT,
#     while `current_mood::text = 'sad'` is `t` and the *unquoted* `current_mood = 'sad'` works —
#     an `unknown` literal is coerced to the enum, a `text` one is not. Three spellings, three
#     different resolutions.
#   * **A bad label is `22P02 invalid input value for enum mood: "angry"`** — the input-syntax
#     class, not `42704` and not a `CHECK` violation — and it is the *same* error from an `INSERT`,
#     an `UPDATE` and a bare cast. The message names the type and quotes the label.
#   * **`DROP TYPE` with a dependent column is `2BP01`**, and the DETAIL names *the column and its
#     table* — `column current_mood of table postgresql_enums depends on type mood` — with the
#     `DROP ... CASCADE` HINT.
#   * **`ALTER TABLE … ADD COLUMN <enum> DEFAULT 'happy'` backfills every existing row**, and the
#     default reads back from `pg_get_expr` and from `information_schema.columns.column_default`
#     as **`'happy'::mood`** — the label quoted and cast, not the bare word.
#   * **`information_schema.columns` reports `data_type = 'USER-DEFINED'` and `udt_name = 'mood'`**,
#     which is exactly what `timestamp_test.rb:202` asserts; `format_type` says just `mood`.
#   * **An empty enum is legal and so is a column of it.** `CREATE TYPE emptymood AS ENUM ()` then
#     `CREATE TABLE e2 (c emptymood)` both succeed; the column can hold NULL and every literal is
#     `22P02`.
#   * **The five statements that name the type in an expression are in `SAVEPOINT`s** rather than run
#     bare, and that is about *this* node rather than the oracle: PostgreSQL answers all four, and
#     a cast **to** a user-defined type is not built here — so run bare, one `0A000` would abort the
#     replay's transaction and take the thirty-seven statements after it, which are the bad-label
#     probes, the `2BP01`, the default backfill, the index and the empty enum. A savepoint is what
#     keeps a declared gap from hiding the rest of the file.
#   * **`create_enum` does not send `CREATE TYPE`.** `ActiveRecord`'s helper sends a
#     `DO $$ … IF NOT EXISTS … THEN CREATE TYPE … END IF … $$` block, captured at the end of this
#     file. It is `0A000 DO` on this node, so `enum_test.rb`'s 19 tests stay blocked on the `DO`
#     block whatever this unit does — the tests reachable by a bare `CREATE TYPE` are
#     `timestamp_test.rb`'s, which uses raw `execute`.

# **`pg_enum` is a view over the type records**, added with the unit that projected it. Three
# things are asked here that one enum cannot answer: that the rows of two types do not run
# together, that a type declared with **no labels** contributes none rather than one empty row,
# and that `enumsortorder` is a `real` starting at **1** — not the label's index, and a float
# because `ALTER TYPE … ADD VALUE … BEFORE` puts a new label *between* two numbers on a real
# server. This node appends only, so its numbers are 1, 2, 3.
CREATE TYPE tense AS ENUM ('past', 'present', 'future')		-
SELECT 'r', t.typname, e.enumlabel, e.enumsortorder FROM pg_enum e JOIN pg_type t ON t.oid = e.enumtypid WHERE t.typname IN ('mood','tense','emptymood') ORDER BY t.typname, e.enumsortorder	text,name,name,real	r|mood|sad|1 ; r|mood|ok|2 ; r|mood|happy|3 ; r|tense|past|1 ; r|tense|present|2 ; r|tense|future|3
