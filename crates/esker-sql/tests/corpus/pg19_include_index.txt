# `CREATE INDEX … INCLUDE` — non-key payload columns — as a real PostgreSQL 19beta1 answers it.
#
# **Statement 787 of `postgresql_specific_schema.rb`**, verbatim as `ActiveRecord` emits it:
#
#     CREATE INDEX "company_include_index" ON "companies" ("firm_id", "type")
#       INCLUDE ("name", "account_id")
#
# Nothing in the corpus covered `INCLUDE`. `pg19_index_constraint.txt` covers `DESC`, partial and
# expression indexes; this is the one index clause it does not have.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The `SELECT count(*)` at the end proves it left nothing behind and answers `0`. The `\gdesc` pass
# runs after the rollback, so statements naming `companies` have an **empty** declared-types column;
# the `pg_typeof` line pins `smallint` for both attribute counts.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **The included columns are IN `indkey`, and only a count separates them from the key.** The
#     suite's index has `indnatts = 4`, `indnkeyatts = 2`, and `indkey = "2 3 4 5"` — all four
#     attributes, in one vector. An implementation that reads `indkey` to reconstruct an index
#     reports a four-column index unless it also reads `indnkeyatts`, and `ActiveRecord`'s schema
#     dumper reads `indkey`.
#   * **`indnkeyatts` and `indnatts` are `smallint`**, not `integer`.
#   * **Uniqueness applies to the key columns only.** `CREATE UNIQUE INDEX … ("firm_id") INCLUDE
#     ("name")` refuses a second row with the same `firm_id` and a *different* `name`, and the
#     DETAIL names only `Key (firm_id)=(1)`. The payload is stored, never compared.
#   * **An included column may repeat a key column.** `("firm_id") INCLUDE ("firm_id")` is
#     **accepted** — `indnatts = 2`, `indnkeyatts = 1`, `indkey = "2 2"`, the same attnum twice, and
#     `pg_get_indexdef` prints it back as written. Not an error, not deduplicated.
#   * **Three different mistakes on an included column give three different SQLSTATEs**, and two of
#     them are `42P17` rather than a syntax error:
#       - `INCLUDE ("name" DESC)`               → `42P17 including column does not support ASC/DESC options`
#       - `INCLUDE ("name" varchar_pattern_ops)` → `42P17 including column does not support an operator class`
#       - `INCLUDE ("nosuchcol")`                → `42703 column "nosuchcol" does not exist`
#     Note the last is the plain column-not-found wording — **not** the `column "…" named in key does
#     not exist` phrasing `pg19_unique_constraint.txt` records for a key column.
#   * **Most access methods refuse included columns, with `0A000` and the AM's name in the
#     sentence.** `hash` is `access method "hash" does not support included columns`; `brin` gives
#     the same sentence. btree accepts.
#   * **`pg_get_indexdef` puts `INCLUDE (…)` after the key list and before the predicate**:
#     `USING btree (firm_id) INCLUDE (name) WHERE (account_id IS NOT NULL)`. `pg_indexes.indexdef`
#     carries the same string.
#   * **A `UNIQUE` *constraint* takes `INCLUDE` too**, and `pg_get_constraintdef` prints it:
#     `UNIQUE (account_id) INCLUDE (name)` — so the clause has to be understood in two grammars,
#     not one.
