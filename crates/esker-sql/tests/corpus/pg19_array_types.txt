# **`pg_type` has a row for every array, including the ten no `ColumnType` stands for.**
#
# `type_lookup_test#test_array_delimiters_are_looked_up_correctly` is two lines of Ruby:
#
#   box_array = @connection.send(:type_map).lookup(1020)
#   int_array = @connection.send(:type_map).lookup(1007)
#   assert_equal ";", box_array.delimiter
#   assert_equal ",", int_array.delimiter
#
# and this node had 1007 and not 1020, so the lookup returned a bare `ActiveModel::Type::Value`
# and the test died on `undefined method 'delimiter'` — a symptom of a missing catalog row and not
# of the delimiter logic.
#
# `_box` is the only array in the suite whose delimiter is a **semicolon**, and the reason is in the
# type: a box prints as `(1,1),(0,0)`, so `{(1,1),(0,0);(3,3),(2,2)}` is two boxes where the same
# string with commas would be four points. It is the one type that tells "the adapter reads
# `typdelim`" apart from "the adapter assumes a comma".
#
# # Why a row exists for a type this node cannot store
#
# A `pg_type` row is a fact about the **catalog**, not a column type. Ten base types here have a
# `typarray` on a real server and no array type in this crate (ADR 0047: an array is a constructor
# over a scalar, and only the elements a column can hold have one) — the six geometric shapes,
# `regclass`, the two vectors and `lquery`. Leaving their rows out made `typarray` a pointer at
# nothing, which is what the adapter follows:
#
#   * it registers `box` **by name**, so 603 enters its type map;
#   * it then asks for every type whose `typelem` is a known oid, which is where 1020 comes from;
#   * `register_with_subtype` registers an array only when its element is already there — so both
#     rows are needed and neither alone is enough.
#
# Every column below is measured. `typinput` is `array_in` for all of them, which is how
# `ActiveRecord` decides a type is an array at all; `typtype` is `b`, because an array is a *base*
# type and not a category of its own; `typlen` is -1 and `typcategory` is `A`; `typarray` is 0,
# because there is no array of an array. The only column that is not the same for all of them is
# `typdelim`.
#
# Every value is cast to `text` or `int8` in the probes, so that what is compared is the value and
# not the declared type: `typname` is `name` on a real server, `typdelim` and `typtype` are
# `"char"`, `typinput` is `regproc` and an `oid` is `oid`, and this node has none of those four
# (declared in `tests/pg_catalog.rs`). The b4 type unit is where that closes.
#
# # THINGS REASONING WOULD GET WRONG
#
#   * **`typelem` is not only an array's.** A real server sets it on the fixed-length types that
#     are internally an array of something — `point` and `line` are two `float8`s, `lseg` and `box`
#     two `point`s, `int2vector` `int2`s, `oidvector` `oid`s — and leaves it `0` on `path`,
#     `polygon` and `circle`, which are variable-length. So it is a list and not a rule about
#     shapes, and it means those six turn up in the adapter's *array* query, where `ActiveRecord`
#     has already sorted them by name.
#   * **The delimiter is on both rows of the pair**: `box` and `_box`, and nothing else in the
#     catalog. Asking `WHERE typdelim <> ','` is the only way to be sure of that, and it is the
#     query that settles it.
#   * **Every range shares one `typinput`.** It is `range_in`, not `int4range_in`: the input
#     function belongs to the range machinery and reads the subtype out of `pg_range`. This crate
#     had the rule for its two *user-defined* ranges and a name each for the six built-in ones.
#   * **The extension types are not in this file.** A real server allocates `ltree`'s and
#     `lquery`'s oids per database — 120217 and 120271 in the container this was taken from — while
#     this node pins them at 16404 and 16406. Their array rows exist here and cannot be compared by
#     oid.
# The two rows the adapter reads, which is the whole of the failing test.
#   * **An oid that names one of these rows prints its name, and that took three places.**
#     `pg_type.typarray` is the link, the row itself is what the link points at, and
#     `1020::regtype` is a *third* reader — it answered the oid's own digits until it went through
#     the same lookup. `format_type(1020, NULL)` is a fourth. Both are in this file.
#   * **Zero is `InvalidOid` and not a `typarray` to search for.** Every type with no array answers
#     `0`, so a reverse lookup that does not special-case it names an array of the first such type:
#     `0::regtype` answered `tsrange[][]` for one probe's worth of time. It is `-` on a real
#     server, through both functions.
# The two rows the adapter reads, which is the whole of the failing test.
