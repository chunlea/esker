# A column `DEFAULT` is an **arbitrary expression**, evaluated per row — statement 738's ten.
#
# This node had two rules of its own and PostgreSQL has neither: a default had to be a *constant*
# (so `0::bigint` and `1 + 1` were refused) and a function default was refused as *possibly
# volatile* (so `concat`, `convert_to`, `CURRENT_DATE` and `random` were too). PostgreSQL applies
# no volatility test and no constant test at all.
#
# **What it does forbid is exactly three things**, and all three are below with their messages: a
# column reference, a subquery, and a set-returning function. An unknown function is not a fourth
# rule — it is the ordinary `42883`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **A default is stored as a parse tree and printed back deparsed**, so the text that comes out
#     is not the text that went in: `random() * 100` prints
#     `(random() * (100)::double precision)`, `0::bigint` prints `(0)::bigint`, and
#     `convert_to('A', 'UTF8')` prints `convert_to('A'::text, 'UTF8'::name)`. Every implicit cast
#     the parser inserted is visible in the output.
#   * **`CURRENT_DATE` prints as itself**, uncast and unparenthesised, where the function calls
#     around it gain both — the same rule `CURRENT_TIMESTAMP` already follows.
#   * **A volatile default really is per row**: `random() * 100` is a different number for each,
#     which is what makes the constant-folding this node used to attempt wrong rather than merely
#     narrow.
