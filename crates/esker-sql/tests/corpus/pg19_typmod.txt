# The **typmod**: `varchar(n)`, `character(n)` and `timestamp(p)` — tier 1's last unit
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)). One mechanism, three
# types, which is why they arrive together: a length or a precision is a property of the *column*,
# where PostgreSQL keeps it (`pg_attribute.atttypmod`), and not of the type.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THE THREE DO DIFFERENT THINGS WITH THEIR NUMBER, and that is the whole of the unit:
#
#   * **`varchar(n)` refuses.** Too long is `22001 value too long for type character varying(5)`,
#     on `INSERT` and on `UPDATE` alike, and trailing spaces are significant — `v = 'abc '` finds
#     nothing where `v = 'abc'` finds the row.
#   * **`character(n)` pads.** `'x'` in a `char(3)` is stored and printed as `x  `, and comparison
#     ignores trailing blanks: `c = 'x'`, `c = 'x  '` and `c = 'x    '` all match the same row.
#     Those two facts are the same fact — a value padded to `n` on the way in makes plain byte
#     comparison *be* the blank-insensitive one, which is what lets an index key hold it without
#     breaking "equal values encode identically".
#   * **`timestamp(p)` rounds**, and the rounding carries: `.999999` at `timestamp(3)` becomes the
#     next whole second, `08:30:16`.
#
# AND `character` WITH NO NUMBER IS `character(1)`, not "unlimited" — `\gdesc` says `character(1)`
# and a second character is `22001`. That is the opposite of `character varying`, where a bare
# spelling means no limit at all, and it is why `char(n)` could not land in the unit that landed
# bare `varchar`: there is no useful no-typmod form of it to land first.
#
# ONE MORE, MEASURED: `min`/`max` over a `character(n)` come back as **`bpchar`**, where over a
# `character varying` they come back as `text`. The string family does not decay uniformly.
#
# TWO THINGS THE ROUNDING DOES THAT NOBODY WOULD GUESS, both at the bottom of this file:
#
#   * **`timestamp(p)` rounds half away from zero, not half to even.** `.0005` at `timestamp(3)`
#     is `.001` and `.0025` is `.003` — a tie goes *up* in both, where the microsecond rounding in
#     the timestamp *parser* breaks a tie to the even neighbour. One type, two rounding rules, and
#     they are in different functions for a reason: this one is `AdjustTimestampForTypmod`.
#   * **And "away from zero" is away from PostgreSQL's epoch, not from the earlier instant.** A
#     timestamp before 2000-01-01 is a negative microsecond count internally, and PostgreSQL
#     negates it, rounds the magnitude, and negates back. So `1970-01-01 00:00:00.0005` at
#     `timestamp(3)` rounds **down**, to `1970-01-01 00:00:00`, where the same fraction in 2020
#     rounds up. Ties on the two sides of the year 2000 go opposite ways in wall-clock terms.
#
# AND A DECLARED LENGTH HAS BOTH ENDS, in the short vocabulary: `varchar(0)` is `22023 length for
# type varchar must be at least 1` — zero is not a legal length, which is the one a reader would
# guess wrong — and `10485761` is `cannot exceed 10485760`. Note `varchar` and `char` here where
# the `22001` above says `character varying(5)` and `character(3)`: PostgreSQL uses two
# vocabularies for one type and this file carries both rather than inferring either.
#
