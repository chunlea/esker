# `integer` / `int4`, as a real PostgreSQL 19beta1 answers it — tier 1's first type
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)).
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# WHAT MAKES IT A TYPE AND NOT AN ALIAS: the range. Both ends are here, and both directions past
# them. A mapping onto `int8` would answer every one of the `22003` lines with a stored row.
#
# THE TRAP: **`22003` has two messages and they are not interchangeable.**
#
#   * a *constant* out of range — `VALUES (4, 2147483648)`, `SET n = 2147483648` — is a bare
#     `integer out of range`, with the value **not** quoted;
#   * a *string* out of range — `WHERE n = '2147483648'` — is `value "2147483648" is out of range
#     for type integer`, with it quoted.
#
# One is the assignment noticing the constant will not fit and the other is `int4in` failing, and
# an implementation that routed both through one of them would be right about the SQLSTATE and
# wrong about the sentence. `'x'` distinguishes the same two paths under `22P02`, where the message
# happens to agree.
#
# `serial` is here because it is not a type: column `s` is an `integer` that fills itself, and
# `\gdesc` calls it `integer`. That is the whole of what ADR 0033 reverses.

CREATE TABLE i4 (id integer PRIMARY KEY, n int, w int8, s serial)		-
