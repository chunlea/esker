# THINGS REASONING WOULD GET WRONG
#
#   * **`information_schema.table_constraints` does not list an `EXCLUDE` constraint at all.** This
#     table has three of them and the view returns two rows — the `PRIMARY KEY` and the
#     `bigserial`'s not-null, the latter typed **`CHECK`**. Anything that reads exclusion
#     constraints has to read `pg_constraint`, where `contype = 'x'`.
#   * **`USING gist` is load-bearing, not decoration.** `EXCLUDE (r WITH &&)` with no `USING`
#     defaults to **btree** and is then refused: `42809 operator &&(anyrange,anyrange) is not a
#     member of operator family "range_ops"`. Spelling `USING btree` explicitly gives the identical
#     error, which is how you can tell what the default was.
#   * **A scalar column cannot be excluded without `btree_gist`.** `EXCLUDE USING gist (id WITH =)`
#     on a `bigint` is `42704 data type bigint has no default operator class for access method
#     "gist"` with a HINT. The suite sidesteps this by excluding on a `daterange(...)` **expression**
#     rather than on a column — that choice is what makes the statement work without an extension.
#   * **`daterange` is half-open, so the suite's adjacent ranges do not conflict.**
#     `[2026-01-01,2026-02-01)` and `[2026-02-01,2026-03-01)` are `&&` **false**, and both rows
#     insert. An implementation that treats a range as closed refuses a row PostgreSQL admits.
#   * **An empty range overlaps nothing, including itself.**
#     `isempty(daterange('2026-01-01','2026-01-01'))` is `t` and `&&` against a range containing it
#     is `f`.
#   * **`daterange(NULL, x)` is an *unbounded* range, not NULL.** It prints `(,2026-02-01)`, and
#     `daterange(NULL,NULL)` overlaps everything.
#   * **The partial `WHERE` is what makes NULLs legal — and it makes duplicates legal too.** Two
#     rows of `(NULL, NULL)` and **two identical rows** of `('2026-01-10', NULL)` all insert,
#     because `end_date IS NOT NULL` fails and the row is not in the index. Without the `WHERE`
#     those are four conflicts.
#   * **The SQLSTATE is `23P01`, not `23505`**, and the DETAIL prints **both** keys as rendered
#     ranges: `Key (daterange(start_date, end_date))=([2026-01-15,2026-02-15)) conflicts with
#     existing key (daterange(start_date, end_date))=([2026-01-01,2026-02-01)).`
#   * **`pg_get_constraintdef` and `pg_get_indexdef` parenthesise the same `WHERE` differently, and
#     neither matches the input.** Written `WHERE (start_date IS NOT NULL AND end_date IS NOT NULL)`,
#     it comes back **triple**-parenthesised from `pg_get_constraintdef`
#     (`WHERE (((start_date IS NOT NULL) AND (end_date IS NOT NULL)))`) and **double** from
#     `pg_get_indexdef`. Three spellings of one predicate.
#   * **The backing index is a plain `CREATE INDEX` and the operator is not in it.**
#     `pg_get_indexdef` gives `CREATE INDEX … USING gist (daterange(start_date, end_date)) WHERE …`
#     — no `UNIQUE`, no `WITH &&`. `indisunique` is `f` and `indisexclusion` is `t`; the `&&` lives
#     only in `pg_constraint`.
#   * **`DEFERRABLE INITIALLY IMMEDIATE` prints as bare `DEFERRABLE`**, the same "keep only what
#     differs from the default" rule `pg19_unique_constraint.txt` records — and deferral behaves the
#     same way here: the row inserts, `count(*)` sees it, and the `23P01` arrives on
#     `SET CONSTRAINTS … IMMEDIATE`.
#   * **`UPDATE` is checked, and only when the new range really overlaps.** Moving `end_date`
#     forward to `2026-02-20` is accepted; moving `start_date` back to `2026-01-15` is `23P01`.
