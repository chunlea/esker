# `ALTER TABLE … ALTER COLUMN … SET DEFAULT`, against PostgreSQL 19beta1 — statement 755 of
# `postgresql_specific_schema.rb`, and the statement that makes the one before it mean anything.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`SET DEFAULT nextval(…)` replaces the `bigserial`'s own default; it does not add one.**
#     `pg_attrdef` holds **one** row for the column throughout — `nextval('sd_id_seq'::regclass)`
#     before and `nextval('sdseq'::regclass)` after — and the next `INSERT` draws from the *new*
#     sequence, which is how `101` gets into a column whose original counter was at 1.
#   * **That is what makes the original sequence droppable.** `DROP SEQUENCE sd_id_seq` is `2BP01`
#     while it is the column's default and a plain success one statement later, without `CASCADE`.
#     The suite drops it on the next line, and a node that left the old default in place would
#     answer `2BP01` there — PostgreSQL's own correct answer to a state it should not be in.
#   * **`DROP DEFAULT` is idempotent** and removes the `pg_attrdef` row; the column then takes
#     NULL, not the value it had been defaulting to.
#   * **A `bigserial` is not an identity column**: `attidentity` is empty for every column here,
#     including the one a sequence fills.
#   * The refusals are four different codes: `42703` for the column, `42P01` for the table *and*
#     for a sequence `nextval` cannot find, `22P02` for a literal the type will not take, and
#     `0A000` for a column reference — the same three-rule test any other `DEFAULT` gets.
