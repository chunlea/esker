# **`pg_proc.provolatile` for every function name this node resolves**, as a real PostgreSQL
# 19beta1 answers it.
#
# NOT types, NOT answers: one column of `pg_proc`, for the 79 names in
# `plan::CatalogFunc::from_name` and `plan::ScalarFunc::from_name` together. It is the evidence
# behind `plan::CatalogFuncCall::is_immutable`, which decides whether a call may be an **index
# key** or a **generated column**, and behind the census in
# `tests/index_expression_volatility.rs`.
#
# Why the whole table at once rather than the name in front of me. `is_immutable` was a list that
# grew one function per defect -- the text-search family, then the JSON accessors, then `||` over
# text -- and each time the reasoning that added one name would have added the others. #25's
# corpus then refused `replace(t, 'a', 'b')` in a generated column, `42P17 functions in index
# expression must be marked IMMUTABLE`, for a call PostgreSQL says is `i`. So this is the list
# measured against the oracle in one pass instead of a twelfth name.
#
# `i` immutable, `s` stable, `v` volatile. A name with more than one row has overloads, and they
# do not always agree: `date_trunc(text, timestamp)` is `i` where `date_trunc(text, timestamptz)`
# is `s`, and `length(bytea, name)` is `s` where every one-argument `length` is `i` -- the same
# name, immutable or not depending on the *argument type*, which is what makes the two-column
# answer below necessary and a name-keyed table wrong.
#
# Eight of the 79 have no row: `greatest`, `least`, `current_date`, `localtime` and
# `localtimestamp` are grammar productions rather than `pg_proc` entries, and `akeys`, `avals` and
# `hstore` need the extension, so they are captured separately below.
#

#      WHERE p.proname IN (<the 79 names>)
