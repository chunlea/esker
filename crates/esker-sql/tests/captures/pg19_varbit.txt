# **`varbit` is the other spelling of `bit varying`** — PostgreSQL 19beta1, 2026-09-09.
# `ON_ERROR_ROLLBACK on`, one `BEGIN … ROLLBACK`, fixture in the first statement.
#
# Group 6 of r1's wire-108 baseline: six probes, all of them
# `0A000 the type VARBIT is not supported`. The type was here all along — `ColumnType::VarBit`,
# oid 1562, with `_varbit` 1563 beside it — and `sqlparser` gives the two spellings two
# `DataType` variants, `BitVarying` for the two words and `VarBit` for the one. Only the first was
# read, so `'101'::bit varying` answered and `'101'::varbit` did not, and with it every statement
# that reaches the type through that spelling.
#
# ## THINGS REASONING WOULD GET WRONG
#
#   * **The printed name of both spellings is `bit varying`.** `pg_typeof('101'::varbit)`,
#     `'varbit'::regtype` and `'varbit(5)'::regtype` all answer `bit varying`; `varbit` survives
#     only as `pg_type.typname`. So nothing downstream has to know which spelling was written.
#
#   * **A cast truncates and an assignment refuses.** `'10101'::varbit(3)` is `101` — no error —
#     and `INSERT INTO t(b varbit(3)) VALUES ('10101')` is `22001 bit string too long for type
#     bit varying(3)`. Same value, same type, two answers.
#
#   * **`min` and `max` do not exist over a bit string**: `42883 function min(bit varying) does
#     not exist`. This node agrees, which is worth saying out loud — it is the one place in the
#     wire baseline where being *more* permissive would have been the easy mistake.
#
#   * **The input function reads a base prefix.** `'xff'::varbit` is `11111111` and
#     `'b101'::varbit` is `101` — `x`/`X` is hex, four bits a digit, `b`/`B` is binary — and a
#     prefix on its own is the empty bit string. That is a *different door* from the `X'…'` and
#     `B'…'` literals, and it is why `'xyz'::varbit` blames the **second** character:
#     `22P02 "y" is not a valid hexadecimal digit`.
#
#   * **`substring` over a bit string answers a bit string**, a plain `bit` whichever of the two it
#     was given.
#
#   * **The bitwise operators answer `bit`, not `bit varying`**, even over two `bit varying`
#     operands: `pg_typeof('101'::varbit & '110'::varbit)` is `bit`. `||` is the exception and
#     keeps `bit varying`.
#
#   * **A bit string converts with `int4` and `int8` and with no other number, and only `bit`
#     does.** The census, rather than one target at a time:
#
#         SELECT castsource::regtype, casttarget::regtype, castcontext, castmethod
#           FROM pg_cast WHERE castsource IN (1560,1562) OR casttarget IN (1560,1562);
#
#     Eight rows, and they are the whole of it — `bit::int2`, `bit::numeric`, `bit::bool` and
#     every `varbit` number pair are `42846`. The conversion is two's complement: `n` shorter than
#     the source keeps the **low** `n` bits (`300::int4::bit(8)` is `00101100`) and `n` longer
#     **sign-extends** (`(-1)::int4::bit(40)` is forty ones, where `5::int4::bit(40)` is
#     zero-padded). The other way the bits are the **low** `n` of the target and the rest are zero,
#     so `'1'*32::bit(32)::int4` is `-1` and `'1'*40::bit(40)::int8` is a *positive*
#     `1099511627775`; more bits than the target holds is `22003`, not a truncation.
#
# ## The measurements
#
