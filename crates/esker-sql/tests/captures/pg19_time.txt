# `time` without time zone, as a real PostgreSQL 19beta1 answers it — tier 2's second type
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)'s roadmap). Eight bytes,
# OID 1083, a microsecond count since midnight, and `timetz` (1266, twelve bytes) beside it,
# which is a different type and is here only where the two meet.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table, dropping whatever a previous run left, so a replay of `cut -f1` is
# byte-identical. The table is deliberately *not* dropped at the end: `sesscap.py` asks `\gdesc`
# for the declared types after the session closes, and a dropped table makes that column empty.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`24:00:00` is a value.** The range is closed at both ends — `00:00:00` through
#     `24:00:00` — so a "time of day" that cannot be a time of day is storable, and `24:00:01` is
#     the first thing past it. `23:59:60` is *also* accepted and normalises to `24:00:00`, and
#     `23:59:59.9999999` **rounds up into it**. Three ways to reach a twenty-fifth hour.
#   * **`24:00:00 + 1 second` is `00:00:01`.** Adding an interval wraps modulo a day rather than
#     overflowing or erroring — so `time` arithmetic is a ring, and the only operation that leaves
#     it is subtraction.
#   * **Three SQLSTATEs for three kinds of wrong**, and a plausible implementation routes all of
#     them through one: `'25:00:00'` and `'12:60:00'` are `22008 date/time field value out of
#     range`; `'-01:00:00'` and `'not a time'` are `22007 invalid input syntax for type time` —
#     a *negative* time is a syntax error, not a range error, which is the one nobody guesses; and
#     `time + time` is `42725 operator is not unique`, with a `DETAIL` of "Could not choose a best
#     candidate operator" rather than the `42883` every other missing operator gives.
#   * **`allballs` is a time and is not a date.** `'allballs'::time` is `00:00:00`; the same
#     literal against `date` is `22007`. The special-word table is per type.
#   * **`sum` and `avg` over a `time` exist and answer `interval`** — `sum` of `12:00` and `13:30`
#     is `25:30:00`, a value no `time` column could hold. This is the exact opposite of `date`,
#     where both are `42883`, and the two types are one tier apart. An implementation that decided
#     the aggregate set per *category* rather than per type would get one of them wrong.
#   * **`time * 2` is an `interval`, `time - time` is an `interval`, and `time + date` is a
#     `timestamp`.** No arithmetic on a `time` answers a `time` except `+ interval`.
#   * **`time::timestamp` is `42846`** even though `date + time` builds one. A cast and an operator
#     are not the same reachability.
#   * **An over-large precision clamps in silence.** `time(7)` is `time(6)` and `'time(9)'::regtype`
#     is 1083 with no complaint, where a `varchar` length past its bound raises `22023`. Same
#     asymmetry `timestamp(9)` has.
#   * **`time(p)` rounds half away from zero**: `.5` at `time(0)` is `12:34:57` and `.9999` at
#     `time(3)` is `12:34:57`. But an *unqualified* `time` truncating a seventh digit rounds to
#     even: `.1234565` is `.123456`. Two rounding rules in one type, as `timestamp` has.
#   * **`extract` answers `numeric` and `date_part` answers `double precision`**, the same split
#     `date` has.
