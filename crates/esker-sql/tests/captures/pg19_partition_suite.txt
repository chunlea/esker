# What the Rails suite *does* with a partitioned table once the schema has loaded — as a real
# PostgreSQL 19beta1 answers it.
#
# `pg19_partition.txt` pinned the DDL of statements 781-786. This pins the statements the **test
# cases** send afterwards, found by grepping `activerecord-8.1.3.1`'s own suite:
#
#     test/cases/adapters/postgresql/partitions_test.rb     create + `table_exists?` + `drop_table`
#     test/cases/adapters/postgresql/schema_test.rb         partitioned index, `indexes()`,
#                                                           `index_name_exists?`, `remove_index`,
#                                                           and the three schema-dumper tests
#     test/cases/insert_all_test.rb:766                     `upsert_all` through a partitioned table
#     test/schema/postgresql_specific_schema.rb:192         `force: true`, which is a DROP first
#
# Every catalog query here is **`ActiveRecord`'s own**, copied out of
# `connection_adapters/postgresql/schema_statements.rb` with its `relkind` filters intact — that is
# the point of half of them.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The `SELECT count(*)` at the end proves it left nothing behind and answers `0`. `\gdesc` runs
# **inline**, in the same session, so every statement here has its declared types pinned — unlike
# `pg19_partition.txt`, whose describe pass ran after the rollback.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`DROP TABLE` of a partitioned parent succeeds and takes every partition with it — no
#     `CASCADE`.** `DROP TABLE IF EXISTS "measurements"` with two partitions holding rows leaves
#     `0` relations matching `measurements%`: the partitions and their indexes go too. This is the
#     statement `create_table(:measurements, force: true)` sends on every schema reload, so a node
#     that refused it could never load the suite's schema twice.
#     `CASCADE` changes nothing about it: `DROP TABLE "measurements" CASCADE` leaves the same `0`.
#     The keyword is not what makes the partitions go — the partitioning is.
#   * **And `INHERITS` is the opposite, in the same session.** `DROP TABLE "ip"` with an inheriting
#     child is `2BP01 cannot drop table ip because other objects depend on it`, `DETAIL: table ic
#     depends on table ip`, `HINT: Use DROP ... CASCADE …`. The two share `pg_inherits` and an edge
#     and differ here completely — one rule for both is wrong for one of them.
#   * **`DROP INDEX` on the partitioned index takes every partition's own index with it.** After
#     dropping `index_measurements_on_logdate_and_city_id`, *zero* relations match
#     `%logdate_city_id%` — the children the suite never named are removed by the drop of the
#     parent it did name. `remove_index` is what `schema_test.rb` sends.
#   * **`pg_get_partkeydef` on a *partition* is NULL**, not its parent's key. So the schema dumper
#     writes `options: "PARTITION BY LIST (city_id)"` for `measurements` and nothing for
#     `measurements_toronto` — and since `table_options` asks `inherited_table_names` **first**,
#     and `pg_inherits` does have a row for a partition, `ActiveRecord` dumps a partition as
#     **`INHERITS (measurements)`**. Measured: that query answers `measurements`.
#   * **A `PRIMARY KEY` on a partitioned table is the unique-index rule again**, and the partition
#     gets **its own** `pk_part_1_pkey`: a duplicate row is `23505 … violates unique constraint
#     "pk_part_1_pkey"`, naming the child. `PRIMARY KEY ("b")` on a table partitioned by `a` is
#     `0A000 PRIMARY KEY constraint on partitioned table must include all partitioning columns`,
#     `DETAIL: … lacks column "a" which is part of the partition key.`
#   * **PostgreSQL 19 gives a `NOT NULL` its own `pg_constraint` row**, `contype = 'n'`, named
#     `<table>_<column>_not_null` and printed `NOT NULL a` — and **a partition inherits those rows**
#     while getting a primary-key row of its own. Three rows on the parent, three on the partition,
#     and only one of the three is the key.
#   * **`upsert_all` works straight through the parent.** `ON CONFLICT ("logdate","city_id") DO
#     UPDATE` updates the row in whichever partition holds it — the conflict target is the
#     partitioned index's key and the arbiter is the partition's own index.
#   * **A partitioned table with no partitions at all is ordinary in every way that is asked
#     here**: `relkind` `p`, `relhassubclass` `f`, visible to `relkind IN ('r','v','m','p','f')`,
#     and `DROP TABLE IF EXISTS` takes it. That is `partitions_test.rb` in full.
#   * `pg_get_indexdef` for a **partition's** index has no `ON ONLY` — only the parent's does — and
#     `indexes('measurements')` answers exactly **one** row where the two partitions have one each
#     of their own, because the query filters on `t.relname`.
