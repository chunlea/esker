#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it

#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`COALESCE` is not a function and does not fail like one.** With no arguments it is
#     **`42601 syntax error at or near ")"`** — a parse error, not `42883 function does not exist`.
#     It is a syntactic construct in the grammar, so an implementation that registers it in a
#     function table gets the arity error wrong.
#   * **It has its own type-mismatch error naming itself**: `COALESCE(1, 'x'::text)` is
#     **`42804 COALESCE types integer and text cannot be matched`**. But `COALESCE(1,
#     'notanumber')` — with an *unknown* literal rather than a typed one — is
#     `22P02 invalid input syntax for type integer`, because the literal is coerced to the first
#     argument's type instead of being compared to it. Same pair of arguments, two different
#     failures depending on whether the second one carries a type.
#   * **The result type is the unification of the arguments, not the first one's.**
#     `COALESCE(NULL::int4, 0)` is `integer`, `COALESCE(NULL::text, 'x')` is `text`, and
#     **`COALESCE(1, 2.5)` is `numeric`** — the integer is promoted.
#   * **`COALESCE(sum(x), 0)` over an empty set is `0`, not NULL** — the aggregate answers NULL and
#     `COALESCE` catches it. That is exactly what `counter_cache.rb` relies on, and it is why the
#     `sum(...) IS NULL` row is pinned beside it.
#   * **`current_database()` returns `name`, not `text`** — the same type as `current_schema()`, and
#     it joins directly against `pg_database.datname` in three of the adapter's four queries.
#   * **`COALESCE` preserves that type through**: `COALESCE(NULL, current_database())` is still
#     `name`.
