# **`length` is four names and four overload sets** — PostgreSQL 19beta1, 2026-09-10,
# `127.0.0.1:55432`, one `BEGIN … ROLLBACK` with a `SAVEPOINT`/`ROLLBACK TO` per probe.
#
# Found beside wire v3 family F3b, where a test reached for `length('101'::bit(3) || '01'::bit(2))`
# and got `42883`. It was written down as "a missing function". It is not.
#
# ## `pg_proc`, all of it
#
#     bit_length   (bit)        int4      length      (bit)        int4
#     bit_length   (bytea)      int4      length      (bytea)      int4
#     bit_length   (text)       int4      length      (bytea, name) int4
#     char_length  (character)  int4      length      (character)  int4
#     char_length  (text)       int4      length      (lseg)       **float8**
#     octet_length (bit)        int4      length      (path)       **float8**
#     octet_length (bytea)      int4      length      (text)       int4
#     octet_length (character)  int4      length      (tsvector)   int4
#     octet_length (text)       int4
#
# ## What each name counts
#
#                     length          char_length   octet_length   bit_length
#     text/character  characters      characters    bytes          bytes x 8
#     bit / varbit    **bits**        -             bytes          bits
#     bytea           bytes           -             bytes          bytes x 8
#     tsvector        **lexemes**     -             -              -
#     lseg / path     **float8**      -             -              -
#
# `char_length` and `character_length` are the **same two** overloads under two spellings, and a
# `42883` names the spelling the caller wrote — which is why they are two variants here.
#
# ## Over the wire v3 probe list's 100 spellings
#
# `length` answers **eleven**: `"char"`, `bit`, `bytea`, `character`, `character varying`, `citext`,
# `lseg`, `name`, `path`, `text`, `tsvector`. `upper`/`lower` answer **twelve** — the six string
# types and the **six ranges**, where they are the bounds.
#
# **This node answered ninety-nine of the hundred for `length`**, because every scalar function read
# its operand as `text`. Seventeen rows diverged and **thirteen were the worse direction** — a value
# where a real server raises:
#
#     length(daterange)   node 2020-01-02   -- the range's UPPER BOUND
#     length(json)        node 7            length(jsonb)   node 8
#     length(xml)         node 4            length(lquery)  node 3
#     length(int2vector)  node 3            length(oidvector) node 3
#     length(tsrange)     node 2020-01-02 00:00:00
#
# and four the other way: `bit`, `bytea`, `lseg`, `path` refused where 19beta1 answers.
#
# ## The geometric length, measured
#
#     length('[(0,0),(3,4)]'::lseg)        5        length('[(1,1),(1,1)]'::lseg)   0
#     length('[(0,0),(3,4)]'::path)        5        -- open, one segment
#     length('((0,0),(3,4))'::path)        10       -- **closed: the edge back counts**
#     length('[(0,0),(3,4),(3,0)]'::path)  9        -- 5 + 4
#     length('((0,0),(3,4),(3,0))'::path)  12       -- 5 + 4 + 3
#     length('[(0,0)]'::path)              0
#
# A `path`'s bracket says whether it is open, and the closing edge is counted at two points as
# well as at three.
#
# ## `bit_length`, measured 2026-09-10 and now built
#
# It was the one this file did not close: three overloads on 19beta1 and none on this node, which
# answered the **named** refusal `0A000 the function bit_length is not supported`.
#
# ### Which spellings it accepts — asked, not assumed
#
# `SELECT pg_typeof(bit_length(NULL::<type>))` over the same 100 distinct spellings, one
# `SAVEPOINT`/`ROLLBACK TO` per probe. **Eight answer**, every one of them `integer`:
#
#     "char"   bit   bytea   character   character varying   citext   name   text
#
# and `bit varying`, which the probe list does not carry (`pg19_varbit.txt:92` has it at 3 for
# `'101'::varbit`). The other 92 are `42883 function bit_length(<type>) does not exist`.
#
# **That is `octet_length`'s set, not `length`'s** — no `tsvector`, no `lseg`, no `path`.
#
# ### What it counts
#
#     bit_length('abc'::text)              24     octet_length 3    length 3
#     bit_length('éî'::text)               32     octet_length 4    length 2
#     bit_length(''::text)                  0
#     bit_length('abc'::varchar)           24
#     bit_length('abc'::citext)            24
#     bit_length('abc'::name)              24
#     bit_length('x'::"char")               8
#     bit_length('ab'::character(5))       16     octet_length 5    length 2
#     bit_length('1'::bit)                  1     octet_length 1    length 1
#     bit_length('101'::bit(3))             3     octet_length 1    length 3
#     bit_length('101010101'::varbit)       9     octet_length 2    length 9
#     bit_length('\x0102'::bytea)          16     octet_length 2    length 2
#     bit_length(''::bytea)                 0
#     bit_length(NULL::text)             NULL
#
# **`character(5)` is the row that matters.** `bit_length` has no `(character)` row in `pg_proc`
# where `octet_length` does, so a `bpchar` reaches it through the coercion to `text` — and that
# coercion **trims the trailing blanks**: 16, which is `'ab'` times eight, and not 40. It is the
# same rule `tests/bpchar_padding.rs` lists as "a text function trims", and it is why this node
# does *not* exempt `bit_length` from `read_as_text` the way it exempts `octet_length`.
#
# Built 2026-09-10; `tests/length_overloads.rs` holds both halves.
