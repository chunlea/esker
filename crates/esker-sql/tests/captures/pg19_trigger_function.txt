# A plpgsql trigger function and its `CREATE TRIGGER` — **and the answer to whether the schema load
# needs a plpgsql runtime** — as a real PostgreSQL 19beta1 answers them.
#
# **Statement 790 of `postgresql_specific_schema.rb`**, verbatim as `ActiveRecord` emits it: one
# message carrying a dollar-quoted `CREATE OR REPLACE FUNCTION … LANGUAGE plpgsql` and the
# `CREATE TRIGGER` that installs it. It refuses at `3f02889` as `CREATE OR is not supported`, which
# is also what statement **762** now refuses with — the two share this unit.
#
# ## Does the load fire it?  No. One test does.
#
# **The schema load only defines them.** `postgresql_specific_schema.rb:211-231` creates the table
# `id: false` and executes the block; it inserts nothing, and this capture confirms `count(*)` is
# **`0`** immediately after the whole statement runs. So the load needs a node that can store a
# dollar-quoted body and register a trigger — **not** one that can execute plpgsql.
#
# **Exactly one test fires it**: `test/cases/persistence_test.rb:1708`,
# `PkAutopopulatedByATriggerRecord.create`, guarded by
# `if supports_insert_returning? && !current_adapter?(:SQLite3Adapter)`, asserting `record.id` is
# not nil and `> 0`. That single test is the whole of the plpgsql *runtime* requirement in the
# suite, and it needs three things together: the trigger fires `BEFORE INSERT`, it assigns
# `NEW.id`, and `RETURNING` gives back the **trigger-modified** row.
#
# One qualification, because it decides how much is in scope: PostgreSQL **validates a plpgsql body
# at `CREATE` time** — a body missing a semicolon is `42601 syntax error at end of input` from the
# `CREATE FUNCTION` itself, not from a later call. The suite's body is valid, so a node that stores
# the text without parsing it loads the schema identically; validation is observable here but is
# not what the load requires.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The two `SELECT count(*)` lines at the end prove it left nothing behind — no function, no table.
# The `\gdesc` pass runs after the rollback, so statements naming the table or the function have an
# **empty** declared-types column; the `pg_typeof` line pins `"char"` for `prokind` and
# `provolatile`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`pg_get_triggerdef` normalises `EXECUTE PROCEDURE` to `EXECUTE FUNCTION`.** The trigger
#     created here with `EXECUTE PROCEDURE` prints back as `EXECUTE FUNCTION`. That matters beyond
#     this file: **statement 762's `INHERITS` block uses `EXECUTE PROCEDURE`** and statement 790
#     uses `EXECUTE FUNCTION` — two spellings of one clause, both of which have to parse, and only
#     one of which is ever printed.
#   * **The trigger overwrites an explicitly supplied value.** `INSERT … ("id") VALUES (99)
#     RETURNING "id"` returns **`4`**, not `99`: the function assigns `NEW.id` unconditionally, and
#     `RETURNING` reports the row *after* the `BEFORE` trigger. An implementation that evaluates
#     `RETURNING` against the submitted row returns `99` and passes nothing.
#   * **`DEFAULT VALUES` on a table whose only column is `NOT NULL` works only because the trigger
#     fills it.** Disable the trigger and the same statement is `23502 null value in column "id" …
#     violates not-null constraint`, `DETAIL: Failing row contains (null).` — which is the proof
#     that the value comes from the trigger and not from a default.
#   * **`tgenabled` is `O` when enabled and `D` when disabled** — a one-letter code, not a boolean —
#     and `tgtype` is the bitmask `7` for `BEFORE` + `ROW` + `INSERT`.
#   * **`prorettype` is `trigger`**, a real type, and **calling the function directly is `0A000
#     trigger functions can only be called as triggers`** — not `42883`.
#   * **The counter follows `MAX(id)`, not a sequence.** After rows `1,2,3`, an explicit `99` still
#     becomes `4`; after that row is updated to `50` and deleted, the next insert is `4` again.
#     Nothing is reserved and nothing is skipped.
#   * **`CREATE OR REPLACE FUNCTION` run twice is not an error** — the second one is a plain
#     success, no `42710` — while a second `CREATE TRIGGER` of the same name **is**
#     `42710 trigger "t_dup" for relation "…" already exists`. `OR REPLACE` exists for the function
#     and not for the trigger.
#   * **A missing trigger function is `42883 function nosuchfunction() does not exist`** at
#     `CREATE TRIGGER` time, and a missing language is `42704 language "nosuchlang" does not exist`.
#   * **`DROP FUNCTION` with a trigger still on it is `2BP01`**, naming the trigger and the table in
#     the DETAIL and suggesting `CASCADE` — the same dependency shape run 33 recorded for
#     `DROP SEQUENCE`. Dropping the trigger first makes the drop succeed.
#   * **`plpgsql` is present with `lanpltrusted = t` and no `CREATE EXTENSION`** — it is not one of
#     the extensions `postgresql_specific_schema.rb` enables.
