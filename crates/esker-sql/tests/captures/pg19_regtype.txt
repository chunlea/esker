# `'x'::regtype` and `oid::regtype`, as a real PostgreSQL 19beta1 answers them.
#
# NOT a type — a **cast**, and the one statement standing between this node and a number. At
# `ae0c8d5` tier 1's types are all in and `ActiveRecord` still cannot boot: rung 2 stops on
# `SELECT 'integer'::regtype::oid` and all 367 suite files that never load stop on
# `SELECT 'character varying(1024)'::regtype::oid`, both from
# `ConnectionAdapters::PostgreSQL::Quoting#lookup_cast_type`. ADR 0033 scoped this cast with the
# type surface — "neither moves the ladder alone" — and the types landed without it.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It creates nothing and drops nothing.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **A typmod is parsed, validated, and then thrown away.**
#     `'character varying(1024)'::regtype::oid` is **1043**, the same OID as the bare spelling,
#     and `'character varying(1024)'::regtype` *prints* `character varying` with no length. But it
#     is not ignored: `'character varying(0)'` is `22023 length for type varchar must be at least
#     1` and `10485761` is `cannot exceed 10485760`. An implementation that stripped `(...)` before
#     looking the name up would return the right OID for every input and the wrong answer for the
#     two that must fail. This is the exact shape `ActiveRecord` sends.
#   * **Quoting defeats the alias table.** `'integer'::regtype` is 23; `'"integer"'::regtype` is
#     `42704 type "integer" does not exist`. `integer` is a *grammar* alias resolved by the type
#     parser; `int4` is the `pg_type.typname`. Quote it and only the catalog is consulted — so
#     `'"int4"'` is 23 and `'"integer"'` is not a type at all. Same rule, second face:
#     `'pg_catalog.int4'` is 23 and `'pg_catalog.integer'` is `42704`, because a schema qualifier
#     also takes the catalog path.
#   * **Two SQLSTATEs, and the empty string picks the rarer one.** An unknown name is
#     `42704 type "nosuchtype" does not exist`; an unparseable one is `42601` — `''` is
#     `invalid type name ""` and `'integer(4)'` is `syntax error at or near "("`. `integer` takes
#     no typmod where `character varying` does, so which spelling may carry a number is part of
#     the alias table and not a property of typmods.
#   * **`float(p)` is the exception to "the typmod is discarded", and it is the one that would
#     silently return the wrong OID.** `'character varying(1024)'::regtype::oid` is 1043, the same
#     as bare — but `'float(24)'::regtype::oid` is **700** (`real`) where `'float'` and
#     `'float(53)'` are **701** (`double precision`). The number does not qualify a type here, it
#     *chooses* one: 1–24 bits is `real`, 25–53 is `double precision`, and outside that it is
#     `22023 precision for type float must be at least 1 bit` / `must be less than 54 bits`.
#     An implementation that stripped the typmod and looked up `float` would answer 701 for
#     `float(24)` and be wrong about the type a client is told.
#   * **The reverse direction never fails.** `999999::regtype` prints `999999` rather than raising
#     — an OID with no `pg_type` row renders as its own number. Only the *text* direction has an
#     error path.
#   * **`serial` is not a type here either.** `'serial'::regtype` is `42704`, which is the catalog
#     agreeing with ADR 0033: `serial` is an `integer` plus a default and it has no OID.
#   * **The canonical name is not the input.** `'time'::regtype` prints `time without time zone`
#     and `'timestamptz'::regtype` prints `timestamp with time zone`. `::regtype::text` is the
#     canonical spelling, not the one that was written.
#   * **Array dimensions are ignored and the internal name works.** `'integer[]'`, `'integer[][]'`,
#     `'integer[3]'` and `'_int4'` are all 1007, and `1007::regtype` prints back `integer[]`.
#   * **`timestamp(9)` is not an error anywhere.** `'timestamp(9)'::regtype` is 1114, and
#     `CREATE TABLE t (a timestamp(9))` *succeeds* with `WARNING: TIMESTAMP(9) precision reduced
#     to maximum allowed, 6` and stores `atttypmod` 6. Out-of-range precision clamps for
#     `timestamp` where out-of-range length raises for `varchar`. (The warning is not in the lines
#     below: this capture records `ERROR` and PostgreSQL's warnings are not part of the format.)
#   * **`numeric`'s bound message shouts.** `22023 NUMERIC precision 1001 must be between 1 and
#     1000` — upper-case type name, where `varchar`'s and `char`'s say `varchar` and `char` in
#     lower case. Three types, three vocabularies, in one SQLSTATE.
