# **A set operation's arms when one of them is an enum, an unknown literal, a domain or a range**
# — PostgreSQL 19beta1, 2026-09-11. Two `BEGIN … ROLLBACK` sessions, **a `SAVEPOINT` per probe**.
#
# Taken for `debts-v1.1.md` #75, #76 and #57's last shape, and it settled #81 as well. The
# savepoint per probe is the point of the shape: without it the first refusal aborts the
# transaction and every later statement answers `current transaction is aborted` instead of the
# thing being measured.
#
# **stdout and stderr interleave** in the raw output below — an `ERROR` line can appear one echo
# block later than the statement it belongs to. Each one quotes its own statement on the `LINE 1:`
# line, so the attribution is never in doubt; it is recorded here rather than tidied away.
#
# ## What an arm one clause down does (#76, closed)
#
#     SELECT m FROM t UNION SELECT 'sad'::mood                        sad ; ok
#     SELECT v FROM (SELECT m AS v FROM t UNION SELECT 'sad'::mood) s  sad ; ok   pg_typeof mood
#     WITH c AS (… UNION SELECT 'sad'::mood) SELECT v FROM c           sad ; ok   pg_typeof mood
#
# The nesting changes nothing: a set operation in a derived table or a `WITH` resolves its arms'
# casts exactly as one at the top level does, and the column is the enum in all three.
#
# ## What an arm with no type of its own does (#75, four rules)
#
#     SELECT 'lit' UNION ALL SELECT tt FROM u      lit ; a          pg_typeof  text
#     SELECT NULL  UNION ALL SELECT 1              NULL ; 1         pg_typeof  integer
#     SELECT NULL  UNION ALL SELECT NULL           NULL ; NULL      pg_typeof  text
#     SELECT 1     UNION ALL SELECT NULL           1 ; NULL
#     SELECT 1     UNION ALL SELECT 'abc'          22P02 invalid input syntax for type integer: "abc"
#
# An unknown literal takes the type of the arms that **have** one and is then read as it — so a
# literal that will not parse fails **as that type**, which is `22P02` about the value and not the
# `42804` about a pair of types. When every arm is unknown the column is `text`.
#
# ## The same rule with an enum on the other side (#81, open)
#
#     SELECT m FROM t UNION SELECT 'sad'           sad ; ok
#     SELECT m FROM t UNION SELECT NULL            ok ; NULL
#     SELECT m FROM t UNION SELECT 'nope'          22P02 invalid input value for enum mood: "nope"
#
# The third is the failure case of the same rule, one type over: the literal is read **as the
# enum**, so the complaint names the enum's own input function. This node reaches neither — it
# refuses the pair — which is #81.
#
# ## An enum beside another category (#57's last shape, closed)
#
#     SELECT m FROM t UNION SELECT 'sad'::text     UNION types mood and text cannot be matched
#     SELECT 'sad'::text UNION SELECT m FROM t     UNION types text and mood cannot be matched
#     SELECT m FROM t UNION SELECT 1::integer      UNION types mood and integer cannot be matched
#     SELECT m FROM t UNION SELECT 1::smallint     UNION types mood and smallint cannot be matched
#     SELECT v FROM (SELECT m AS v FROM t) q UNION SELECT 1::smallint
#                                                  UNION types mood and smallint cannot be matched
#
# Two categories, so the conversion is never tried and the `42846` two enums get is never reached.
# **The sentence names the enum**, not the `int2` it is stored as — and the `smallint` row is the
# sharp one, because that *is* an enum's storage here and this node answered the ordinals for it.
#
#     SELECT m FROM t UNION SELECT o FROM t        UNION could not convert type other_mood to mood
#     SELECT m FROM t UNION SELECT 'sad'::mood     sad ; ok
#     SELECT max(m) FROM t UNION SELECT 'sad'::mood  sad ; ok
#
# Two **different** enums are one category, so that one does reach the conversion and is `42846`
# with the later arm's type first. The same enum on both sides answers, and so does an enum that
# arrives through `max()` — an aggregate that keeps its argument's type is still that type.
#
# ## What the rule must not touch: a domain and a range
#
#     SELECT d FROM t UNION SELECT 2::integer      1 ; 2            pg_typeof  integer
#     SELECT d FROM t UNION SELECT 'a'::text       UNION types integer and text cannot be matched
#     SELECT r FROM t UNION SELECT '[2,3)'::int4range   [1,5) ; [2,3)
#     SELECT r FROM t UNION SELECT 'a'::text       UNION types int4range and text cannot be matched
#
# **A domain is its base type here and is never named**: `posint` does not appear in either
# sentence, and it unifies with `integer` rather than being refused against it. A range is its own
# type and was already named correctly. So the enum rule above has to be enum-only, and these four
# rows are what says so.
#
