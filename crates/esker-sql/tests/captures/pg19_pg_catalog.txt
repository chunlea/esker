# `pg_type` and `pg_range`, as a real PostgreSQL 19beta1 answers them -- the first slice of
# `pg_catalog` and the one `ActiveRecord` asks for before anything else. Four of its 36 boot
# statements read these two relations (`docs/bench/rails-scoreboard.md`), and rung 2 of the ladder
# stopped on `relation "pg_type" does not exist`.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# No fixture: both relations are built in.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# WHOSE TYPES DOES `pg_type` LIST? The predecessor left this open and said it wanted a capture
# rather than an argument (`docs/plans/phase-9-rails.md` §Unit 5, handover question 1). The
# capture is of `ActiveRecord` rather than of PostgreSQL, and it is in the adapter's own source:
#
#   * `add_pg_decoders` runs statement 4 and builds its decoders with
#     `result.filter_map { |row| construct_coder(row, coders_by_name[row["typname"]]) }` --
#     `construct_coder` returns `nil` for a name it has no coder for, so a **short answer is a
#     shorter map and not an error**;
#   * `TypeMapInitializer#run` (statements 7-9) partitions the rows it is given and registers each
#     partition. An empty partition registers nothing;
#   * a column whose OID is in no map is decoded as a string.
#
# So a short `pg_type` costs a client nothing it can see, **and this node never sends an OID that
# is not in it**: the six types it has are the six it can put in a `RowDescription`. Listing
# PostgreSQL's standard OIDs would be the opposite trade -- telling a client this server has
# `numeric` and `int4`, which it answers `0A000` for. The decision is therefore the literal
# meaning of the relation: `pg_type` lists the types **this** server has, with PostgreSQL's own
# OIDs for them, and `SELECT typname FROM pg_type WHERE typname = 'numeric'` is no rows here and
# one row there. That is the divergence, it is declared in `tests/pg_catalog.rs`, and it closes
# one type at a time as types arrive.
#
# TWO THINGS THE CAPTURE SETTLED THAT READING WOULD HAVE GOT WRONG:
#
#   * **`pg_range` has no `oid` column.** `SELECT oid FROM pg_range` is `42703`, and that is what
#     makes `LEFT JOIN pg_range AS r ON oid = rngtypid` legal with an unqualified `oid` -- there
#     is only one `oid` in scope. A `pg_range` given one would make `ActiveRecord`'s statement 7
#     ambiguous, which is `42702` and a query a real server takes.
#   * **DDL on a system catalog is `42501`, not `0A000`.** `DROP TABLE pg_type`, `ALTER TABLE` and
#     `CREATE INDEX` all answer `permission denied: "pg_type" is a system catalog`. DML is *not*
#     refused for a superuser -- the three write probes below run inside a rolled-back block for
#     exactly that reason, and deleting a row out of `pg_type` breaks the database.
