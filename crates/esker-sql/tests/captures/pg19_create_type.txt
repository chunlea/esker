# `CREATE TYPE` — `AS RANGE`, `AS (…)` composite and `AS ENUM` — as a real PostgreSQL 19beta1
# answers them.
#
# **Run 45 ranking row 3: 51 tests across 3 files**, and the three files want three different forms.
# Taken verbatim from the tests' own `setup`:
#
#   * `adapters/postgresql/range_test.rb:19` (46 tests) — **two statements in one `execute`**:
#     `CREATE TYPE floatrange AS RANGE ( subtype = float8, subtype_diff = float8mi );
#      CREATE TYPE stringrange AS RANGE ( subtype = varchar );`
#   * `adapters/postgresql/composite_test.rb:19` (4 tests) —
#     `CREATE TYPE full_address AS ( city VARCHAR(90), street VARCHAR(90) );`
#   * `adapters/postgresql/timestamp_test.rb:196` (1 test) —
#     `CREATE TYPE custom_time_format AS ENUM ('past', 'present', 'future');`
#
# So the row is not "enums": it is **ranges first**, by nine to one.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way.
#
# **The whole capture runs inside `BEGIN … ROLLBACK`**, error probes in `SAVEPOINT` / `ROLLBACK TO`.
# The `SELECT count(*)` at the end proves it left nothing behind and answers `0`. The `\gdesc` pass
# runs after the rollback, so statements naming these types have an **empty** declared-types column;
# the `pg_typeof` line pins `"char"` for `typtype` and `typcategory`.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **`typtype` and `typcategory` are different one-letter codes and both matter**: range is
#     `r`/`R`, composite `c`/`C`, enum `e`/`E`. A composite additionally has `typrelid <> 0` — it
#     owns a `pg_class` row, which is how its fields are stored; a range and an enum do not.
#   * **Creating a range type creates its array type too**: `typarray` is `floatrange[]`, with no
#     statement asking for it.
#   * **A bare decimal literal will not go into a `float8` range.**
#     `floatrange(1.0, 5.0) @> 3.0` is **`42883 operator does not exist: floatrange @> numeric`**
#     with the "add explicit type casts" HINT — because `3.0` is `numeric`, not `float8`. With
#     `3.0::float8` it answers `t`. The constructor accepts `1.0` happily; only the operator is
#     strict, so an implementation can pass the `CREATE` and the constructor and still fail here.
#   * **A custom range prints and behaves like the built-in ones**: `[1,5)`, half-open, with
#     `lower`, `upper`, `&&` and `isempty` all defined. `pg_range` carries `rngsubtype`
#     (`double precision`), `rngsubdiff` (`float8mi`) and an **empty** `rngcanonical` — the
#     `subtype_diff` the test supplies lands in `rngsubdiff`, and nothing fills `rngcanonical`.
#   * **A composite value quotes only the fields that need it**: `(Paris,Rue)` but
#     `("New York",Broadway)`. Both the `ROW('Paris','Rue')` constructor and the literal
#     `'("New York","Broadway")'` are accepted, and they round-trip to the same shape.
#   * **Field access needs the parentheses**: `(address).city`. And `format_type` of a composite
#     column is just `full_address` — no `(90)`, no schema qualification.
#   * **An enum with no labels is legal.** `CREATE TYPE emptyenum AS ENUM ()` succeeds and
#     `typtype` is `e`. A bad label is `22P02 invalid input value for enum custom_time_format:
#     "nope"` — `22P02`, the input-syntax class, not `42704`.
#   * **`enumsortorder` is 1, 2, 3 and is what ordering compares** — `'past' < 'future'` is `t`
#     because of declaration order, not alphabetical order.
#   * **`DROP TYPE` with a dependent column is `2BP01`**, DETAIL naming *the column and its table*
#     (`column address of table postgresql_composites depends on type full_address`), not the table
#     alone. Duplicate type is `42710`; an unknown subtype is `42704`.
