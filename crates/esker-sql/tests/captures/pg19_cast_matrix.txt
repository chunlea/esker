# **Every cast between two of the probe list's types** — PostgreSQL 19beta1, 2026-09-10,
# `127.0.0.1:55432`, one `BEGIN … ROLLBACK` with a `SAVEPOINT`/`ROLLBACK TO` per probe.
#
# Every **ordered pair** of the wire v3 probe list's 100 distinct type spellings — 9,900 casts —
# asked as `SELECT ($1::<source>::<target>) IS NOT NULL` with the source's own probe value bound.
# 2.8 seconds of oracle time, which is what makes the complete sweep cheaper than the estimate it
# replaces.
#
# ## What 19beta1 answers
#
#     ok        1,037      !42846    8,243      !22P02      522
#     !22007       40      !22023       14      !42601       11
#     !42P01        9      !42883        9
#
# `42846` is by far the common answer: **most pairs of types have no cast at all**, and a node that
# reads a value's text through the target's input function will answer where a real server refuses.
#
# ## What this node answered, before and after the literal-array guard
#
#                                  before    after
#     node answers, PG refuses        391       95     <- ADR 0031's worst class
#     node refuses, PG answers        121      121
#     both refuse, different code   3,501      293
#                                   -----     -----
#                                   4,013       509
#
# **3,504 rows closed and none regressed**, by one check. `parse::lower`'s array arm reads a
# literal array's *text* and hands it to the target's `array_in` — which is right for a pair that
# has a cast and wrong for a pair that does not — and it returns before the general `casts_to`
# guard below it. So `'{x}'::"char"[]::bytea[]` answered `{"\x78"}` while the **scalar**
# `'x'::"char"::bytea` and the same pair through a **column** both refused correctly.
#
# The sqlstate half is the same fix: a pair with no cast used to reach `array_in` and fail as the
# element reader's `22P02` — "invalid input syntax" for a conversion that does not exist — where a
# real server says `42846` before reading anything.
#
# ## What was left after the literal-array guard, and it was not one thing
#
#     95   node answers, PG refuses    — mostly `text ->` something the reader accepts too freely
#     121  node refuses, PG answers    — **not** 121 missing `pg_cast` rows; see the breakdown below
#     293  both refuse, different code
#
# ## RE-SWEPT 2026-09-10 after the element-wise array cast: 509 -> 353
#
# The node side was re-taken over the same 1,425 pairs the grading above names (the 509 divergent
# and the 916 that agreed), with each source's own probe value from `esker-coord/wire-v3-probes.txt`:
#
#                                     before   now agrees   still
#     node refuses, PG answers          121        **71**      50
#     node answers, PG refuses           95        **79**      16     <- ADR 0031's worst class
#     both refuse, different code       293          6        287
#                                      ----       -----     -----
#                                       509        156        353
#
# **One mechanism, and the "121 missing `pg_cast` rows" reading was wrong.** Grouped by the
# sqlstate the node gave, the 121 were: `22001` 34 (`<T>[] -> character[]`), `22P02` 34 (pairs
# whose scalar cast **exists**), `42846` 40 (the genuinely missing rows — F9's forty), `22026` 5,
# `42704` 4 (`<integer>[] -> regtype[]`), `22003` 4 (`regclass -> integer`, whose ids are 64-bit
# here). Only the 40 were about a missing row.
#
# The other families were **one defect**: an array's cast read each element's *text* through the
# target element's input function instead of applying the **element cast**. The scalar pair and
# the array pair disagreed, and all three routes in — a literal, an `ARRAY[…]` constructor and a
# **column** — shared it:
#
#     1.5::float8::integer            2       '{1.5,2.5}'::float8[]::integer[]      22P02
#     '2020-01-01'::date::character   2       '{2020-01-01}'::date[]::character[]   22001
#
# **It was not the literal-array arm**, which is where the previous unit's note pointed: a column
# of `float8[]` reached the same `22P02`. Three changes, each symmetric with something that
# already existed — `exec::cursor` casts element by element through the same function the scalar
# fallback uses, `parse::lower` stops folding an array cast that **has** a source type (no source
# type is the input function, a source type is a cast — `pg_cast`'s own boundary), and
# `value::truncate_to_typmod` gains the container arm `fit_to_typmod` already had.
#
# **Why the second class moved at all**: 79 of the 95 rows where this node *answered* and 19beta1
# refuses were the same mechanism seen from the other side — a pair with no element cast used to
# be read by `array_in`, which accepts what the element reader accepts.
#
# ## What the 357 are now, and they are four separate items plus one family
#
# **54 node refuses, PG answers** — by the sqlstate this node gives:
#
#     42846  40   `hstore -> json|jsonb` and `int2vector`/`oidvector` -> the arrays.
#                 **The genuinely missing `pg_cast` rows**, which is family F9's forty. A unit.
#     42704   4   `<integer>[] -> regtype[]`. `pg_cast` has **no** `text -> regtype` row either, so
#                 both spellings are I/O conversions and `regtypein` reads all digits as an oid —
#                 `'23'::regtype` is `integer` there and `42704 type "23" does not exist` here.
#                 The scalar has it too; four rows here and two spellings. A unit.
#     22003   4   `regclass -> integer|oid` and their arrays. This node's relation ids are 64-bit
#                 (ADR 0097) and a real server's oids are four bytes, so the overflow is a
#                 consequence of the id and not a cast defect. **Probably a declared divergence**
#                 rather than a fix, and it should be decided rather than carried.
#     22P02   5   `"char"[] -> integer[]` is the byte (`'1'::"char"::integer` is 49) and an element
#                 never reaches the arm that knows, because that arm asks the *operand's* declared
#                 type and an element's is the array's — one parameter away. The other four are
#                 `regproc -> oid` and three of the unreproducible rows below.
#     42601   1   `text -> hstore`, the fourth unreproducible row.
#
# **11 node answers, PG refuses** — the other direction of one small table: seven are
# `<something> -> oidvector`, where `casts_to` says yes and `pg_cast` has no row, and the rest are
# `regclass <-> regtype` and `bit -> oid`. A `casts_to` unit, and the smallest of the four.
#
# **292 both refuse with different codes** is a family of its own and not a cast defect: what is
# wrong there is the *sqlstate*, which is what a client branches on. It is the largest group left
# and the least urgent by ADR 0031.
#
# ## RE-SWEPT 2026-09-10 (evening) after the `42846 / ok` residue: 357 -> 31
#
# The node side re-taken over the **357 rows of the divergence list below**, in the same literal
# spelling the previous re-take used (`'<value>'::<source>::<target>`, each source's own probe
# value from `esker-coord/wire-v3-probes.txt`):
#
#     now agree                      **326**
#     node refuses, PG answers        **10**   <- was 54
#     node answers, PG refuses         **1**   <- was 11
#     both refuse, different code     **20**   <- was 292
#
# **The `42846 / ok` forty are closed, and they were four mechanisms rather than one missing
# table.** (1) `refused_cast`'s `stringy` was three names where PostgreSQL asks a *category*, so
# `interval|money|time|uuid -> name|citext` were refused — eight rows, and `typcategory` already
# said `S` for all five one module over. (2) `time -> interval` is a real `pg_cast` row the same
# table hid, and the arm beside it already carried the finding in words. (3) `hstore -> json|jsonb`
# are two rows the extension carries, added to `CASTS` with the conversion in
# `value::convert_without_text` — one arm for the fold, the column and the array element. (4) The
# twenty-five vector rows are **one rule**: a vector casts to every array its element casts to, so
# `casts_to` asks `casts_to(int2, T)` where it had two tuples, and three readers of the operand's
# text had to stop treating `1 2` as an array literal (`lower_array_cast`'s typmod'd elements,
# `lower_regclass_array`, and the evaluator's `regclass[]` arm, which sat above the vector one).
#
# **The four `42704` rows went with them**: `regtypein` reads all digits as an oid — `'23'::regtype`
# is `integer` — which is `regclassin`'s rule one type over, now `value::oid_spelled` for all three
# roads a `regtype` arrives by. It closed `<integer>[] -> regtype[]`, the vectors' last two rows,
# and a declared divergence in `tests/regtype.rs` whose reason had stated the rule.
#
# **What is left, and five of the eleven are this file's own bad rows.**
#
#     22003  4   `regclass -> integer|oid` and their arrays: ADR 0097's 64-bit ids against a
#                four-byte oid. **A ruling, not a fix** — it is the id and not the cast.
#     22P02  1   `"char"[] -> integer[]` is the byte, and an element never reaches the arm that
#                knows, because that arm asks the *operand's* declared type — one parameter away.
#     22P02  1   `regproc -> oid` over a literal.
#     ----   5   `text -> money|hstore|int2vector|oidvector` and `text -> lquery`: the rows below
#                whose value the list does not reproduce. Both servers agree on all five when
#                asked with the list's own value (`x`). **Re-take them.**
#
# The `both refuse, different code` group is 20 and is the sqlstate family, not a cast defect:
# seven are `22P02` where a real server says `22023`, six `22P02` where it says `42846`.
