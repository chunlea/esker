#
# Every **ordered pair** of the wire v3 probe list's 100 distinct type spellings — 9,900 casts —
# asked as `SELECT ($1::<source>::<target>) IS NOT NULL` with the source's own probe value bound.
# 2.8 seconds of oracle time, which is what makes the complete sweep cheaper than the estimate it
# replaces.
#
# ## What 19beta1 answers
#
#     ok        1,037      !42846    8,243      !22P02      522
#     !22007       40      !22023       14      !42601       11
#     !42P01        9      !42883        9
#
# `42846` is by far the common answer: **most pairs of types have no cast at all**, and a node that
# reads a value's text through the target's input function will answer where a real server refuses.
#
# ## What this node answered, before and after the literal-array guard
#
#                                  before    after
#     node answers, PG refuses        391       95     <- ADR 0031's worst class
#     node refuses, PG answers        121      121
#     both refuse, different code   3,501      293
#                                   -----     -----
#                                   4,013       509
#
# **3,504 rows closed and none regressed**, by one check. `parse::lower`'s array arm reads a
# literal array's *text* and hands it to the target's `array_in` — which is right for a pair that
# has a cast and wrong for a pair that does not — and it returns before the general `casts_to`
# guard below it. So `'{x}'::"char"[]::bytea[]` answered `{"\x78"}` while the **scalar**
# `'x'::"char"::bytea` and the same pair through a **column** both refused correctly.
#
# The sqlstate half is the same fix: a pair with no cast used to reach `array_in` and fail as the
# element reader's `22P02` — "invalid input syntax" for a conversion that does not exist — where a
# real server says `42846` before reading anything.
#
