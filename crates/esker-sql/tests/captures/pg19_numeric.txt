# `numeric(p, s)`, as a real PostgreSQL 19beta1 answers it — tier 2's hard half
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)'s roadmap: "numeric's text
# parity, because PostgreSQL prints the *declared* scale exactly and this is the type ADR 0031 has
# been refusing on those grounds since unit 0"). OID 1700, varlena, `typcategory` N.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table, dropping whatever a previous run left, so a replay of `cut -f1` is
# byte-identical. The table is deliberately *not* dropped at the end: `sesscap.py` asks `\gdesc`
# for the declared types after the session closes, and a dropped table makes that column empty.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **The scale is part of the value, and it is what ADR 0031 refused `avg(int8)` over.**
#     `1.0`, `1.00` and `1.000` are three different texts for one number and all three are stored
#     and printed as written. A declared scale forces it: `1.0::numeric(10,3)` prints `1.000` and
#     `1.5::numeric(10,2)` prints `1.50`. Any implementation that normalises trailing zeros is
#     wrong on the first row of this file.
#   * **Rounding is half away from zero, everywhere, and never banker's.** The discriminating case
#     is `1.245::numeric(10,2)`, which is **1.25** — half-to-even would give `1.24`. `round(2.5)`
#     is 3, `round(3.5)` is 4, `round(-2.5)` is -3, and `2.5::numeric::int` is 3. One rule for the
#     cast, the function and the assignment.
#   * **Arithmetic scale is computed, not inherited, and each operator has its own rule.**
#     `1.50 * 1.50` is `2.2500` — multiplication **adds** the scales. `1.5::numeric(10,2) +
#     1.5::numeric(10,2)` is `3.00`. Division picks a scale of its own: `1::numeric / 2` is
#     `0.50000000000000000000` (20 digits) while `6.0 / 2.0` is `3.0000000000000000` (16). And
#     `2 ^ 10` is `1024.0000000000000`, not `1024`.
#   * **`NaN` is a `numeric` value and it sorts as the largest one.** `'NaN' = 'NaN'` is **`t`**
#     and `'NaN' > 1` is **`t`** — the opposite of IEEE, and the opposite of what `float8` does.
#     `'NaN'::numeric / 0` is `NaN` where `1 / 0` is `22012 division by zero`.
#   * **`NaN` fits a `numeric(10,2)` and `Infinity` does not.** Both are values of the unqualified
#     type; only one survives a typmod, and the `22003` says which: "cannot hold an infinite
#     value" against "must round to an absolute value less than 10^1".
#   * **`NaN::int` is `0A000`, not `22003`.** `cannot convert NaN to integer` — a
#     feature-not-supported code from a cast, which is the one SQLSTATE nobody would predict here.
#   * **Negative scale is legal.** `numeric(10,-2)` is a real type: `12345.6789` stored in it is
#     `12300`, and `format_type(1700, 786434)` is `numeric(11,-2)`. Bounds are precision 1..1000
#     and scale **-1000..1000**, and both messages shout: `NUMERIC precision 1001 must be between
#     1 and 1000`.
#   * **The typmod is `((p << 16) | s) + 4`** — a third encoding, next to `varchar`'s length+4 and
#     `timestamp`'s bare precision. Measured: `format_type(1700, 655366)` is `numeric(10,2)`, and
#     655366 is `(10 << 16) | 2` plus 4. And `numeric(10)` is `numeric(10,0)`: a bare precision
#     means scale zero, not "no scale".
#   * **`0.1 + 0.2 = 0.3` is `t` here and `f` for `float8`.** That is the whole reason the type
#     exists, and it is one line of this file.
#   * **`numeric + float8` is `double precision`** — the exact type loses to the inexact one in
#     promotion, where `numeric + int4` stays `numeric`.
#   * **`22P03` is not in this file and cannot be.** It is `invalid binary representation`, which
#     only the extended protocol's binary format can produce; `psql` sends text. The on-wire shape
#     is recorded instead — `numeric_send(1.5)` is `\x000200000000000100011388` — so an
#     implementation of the binary path has the bytes to check against.
