# `date`, as a real PostgreSQL 19beta1 answers it — tier 2's first type
# ([ADR 0033](../../../../docs/adr/0033-tier-1-of-the-type-surface.md)'s roadmap, "Tier 2 — new
# physical types"). Four bytes, OID 1082, and the first tier-2 type because it is the one
# `ActiveRecord`'s `t.date` emits and the one with no fractional part to argue about.
#
# Captured in one session with `scratchpad/sesscap.py` and replayed the same way against one node.
# It builds its own table, dropping whatever a previous run left, so a replay of `cut -f1` is
# byte-identical. The table is deliberately *not* dropped at the end: `sesscap.py` asks `\gdesc`
# for the declared types after the session closes, and a dropped table makes that column empty.
#
#   statement <tab> types <tab> rows      the result, and the types `\gdesc` declared for it
#   statement <tab> <tab> -               a command with no result set, only a tag
#   statement <tab> !SQLSTATE message     PostgreSQL refused it; DETAIL and HINT follow
#
# THINGS REASONING WOULD GET WRONG
#
#   * **A `date` has no fixed text.** `DateStyle` decides it, and all four spellings of one value
#     are below: ISO `2020-01-02`, SQL `01/02/2020`, German `02.01.2020`, Postgres `01-02-2020`.
#     An implementation that hard-codes ISO is right only for the default. The *input* half of the
#     same setting is worse: `'01/02/2020'` is **2 January** under `MDY` and **1 February** under
#     `DMY` — one literal, two dates, no error either way.
#   * **`22008` has two messages and they are not interchangeable**, the same trap `int4`'s two
#     `22003`s set. Past the type's ends is `date out of range: "5874898-01-01"`; an impossible
#     *field* is `date/time field value out of range: "2020-02-30"`. And only the second kind
#     sometimes carries `HINT: Perhaps you need a different "DateStyle" setting.` — `2020-13-01`
#     gets the hint and `2020-02-30` does not, because a 13 could have been a day.
#   * **`date - date` is an `integer`, not an `interval`**, and **`date + interval` is a
#     `timestamp`, not a `date`**. Neither arithmetic result has the type of its operands, and
#     `date + numeric` does not exist at all — `1.5` is a `numeric`, so `d + 1.5` is `42883` where
#     `d + 1` is a date.
#   * **`extract` answers `numeric` and `date_part` answers `double precision`** for the same
#     question. Two functions, one meaning, two declared types.
#   * **A `date` is not a number.** `'2020-01-01'::date::int` is `42846 cannot cast type date to
#     integer` and so is the other direction. The Julian day is an implementation detail with no
#     cast to reach it.
#   * **There is no year zero.** `0000-01-01` is `22008` while `0001-01-01 BC` is a value, and
#     `4713-01-01 BC` is the bottom of the range — one year further back is out of range.
#   * **`infinity` absorbs arithmetic**: `'infinity'::date - 1` is `infinity`, not the day before.
#   * **`sum` and `avg` over a `date` do not exist** (`42883 function sum(date) does not exist`)
#     where `min`, `max` and `count` do. The aggregate set is not uniform across types.
#   * **The clock words are values, not literals to store.** `today`, `tomorrow`, `yesterday` and
#     `now` resolve at parse time, so no capture can pin them; what is pinned here is the
#     invariant they satisfy — `'tomorrow'::date - 'today'::date` is 1 on every day.
