# **Set operations: `UNION ALL`'s typing, and where an `ORDER BY` may stand** — PostgreSQL
# 19beta1, 2026-09-05. One `BEGIN … ROLLBACK`, a `SAVEPOINT` per probe.
#
# `with_test.rb` sends `WITH … AS (SELECT … UNION ALL (SELECT …) UNION ALL SELECT …) SELECT …`
# and a `WITH RECURSIVE` whose body is a `UNION ALL`.
#
# **The sentence that used to stand here has expired.** It said "nothing here is built: a set
# operation is `0A000` naming the operator (`parse::lower`)", which was true when this was
# captured and stopped being true when `UNION` landed. Today the parser lowers all three
# operators and the plan can say all three; the refusal that remains is one function in the
# executor, `exec::mod::set_arm_supported`, and it covers `INTERSECT` and `EXCEPT` only
# (`debts-v1.1.md` #105, whose plan page is `docs/plans/set-operators.md`). A recorded blocker
# is a dated hypothesis: this one decayed in eleven days and nobody came back to the line that
# depended on it.
#
# ## Cross-arm type unification
#
#     SELECT 1        UNION ALL SELECT 2.5           numeric      int + numeric
#     SELECT 1::int4  UNION ALL SELECT 2::int8       bigint       the wider integer
#     SELECT 'lit'    UNION ALL SELECT t FROM …      text         an unknown literal takes the
#                                                                 other arm's type
#     SELECT NULL     UNION ALL SELECT 1             integer      and so does a bare NULL
#     SELECT NULL     UNION ALL SELECT NULL          text         both unknown, so text
#
# **A literal that cannot be read as the resolved type fails as that type**, not as a mismatch:
#
#     SELECT 1 UNION ALL SELECT 'abc'
#         22P02 invalid input syntax for type integer: "abc"
#
# — the same rule `GREATEST(1, 'a')` follows. A **column** of the wrong type is the other error:
#
#     SELECT t FROM so_b UNION ALL SELECT i FROM so_b
#         UNION types text and integer cannot be matched
#     SELECT i FROM so_b UNION ALL SELECT t FROM so_b
#         UNION types integer and text cannot be matched      <- the names follow the arms' order
#
# And a different number of columns is the grammar's:
#
#     SELECT 1, 2 UNION ALL SELECT 3
#         42601 each UNION query must have the same number of columns
#
# ## The names come from the first arm, and only from it
#
#     SELECT 1 AS first_name UNION ALL SELECT 2 AS second_name     ->  column `first_name`
#     SELECT i FROM so_a UNION ALL SELECT n FROM so_a              ->  column `i`, type numeric
#
# The second is both rules at once: the **name** is the first arm's and the **type** is the
# unification, so a column can be called `i` and be a `numeric` because the other arm made it one.
#
# ## Arms concatenate in order, and three of them flatten
#
#     SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3               ->  1, 2, 3
#     SELECT i FROM so_a UNION ALL (SELECT i FROM so_a) UNION ALL SELECT 9
#                                                                 ->  1, 2, 1, 2, 9
#
# ## Where an `ORDER BY` or a `LIMIT` may stand — h1's question, measured
#
#     (SELECT 1) UNION ALL SELECT 2                    ok
#     SELECT 1 UNION ALL (SELECT 2)                    ok
#     (SELECT 1 ORDER BY 1) UNION ALL SELECT 2         ok      inside the parentheses
#     (SELECT 1 LIMIT 1) UNION ALL SELECT 2            ok      likewise
#     SELECT 1 UNION ALL SELECT 2 ORDER BY 1 DESC      2, 1    outside, over the whole set
#
#     SELECT 1 ORDER BY 1 UNION ALL SELECT 2           42601 syntax error at or near "UNION"
#     SELECT 1 LIMIT 1 UNION ALL SELECT 2              42601 syntax error at or near "UNION"
#
# **So the parentheses are the rule and not a style**: an arm may carry its own `ORDER BY` or
# `LIMIT` only inside them, and an unparenthesised one before `UNION` is a syntax error rather
# than a clause that binds to the set.
#
# ## What an outer `ORDER BY` may name
#
#     SELECT i AS c FROM so_b UNION ALL SELECT 2 ORDER BY c      ok, the output name
#     SELECT i    FROM so_b UNION ALL SELECT 2 ORDER BY 1 DESC   ok, the ordinal
#     SELECT i AS c FROM so_b UNION ALL SELECT 2 ORDER BY i      column "i" does not exist
#
# The last is the sharp one: **the underlying column is not visible**, only the set's output name.
#
#     SELECT 1 UNION ALL SELECT 2 LIMIT 1 OFFSET 1               ->  2
#
# ## Dedup, for the commit after (measured now so the two are one capture)
#
#     SELECT 1 UNION SELECT 1 UNION SELECT 2         ->  1, 2      duplicates collapse
#     SELECT NULL::int UNION SELECT NULL::int        ->  one row   NULL is equal to NULL here
#     SELECT 1 INTERSECT SELECT 1                    ->  1
#     SELECT 1 EXCEPT SELECT 2                       ->  1
#
# ## `WITH RECURSIVE`, measured for the commit that does not build it
#
#     WITH RECURSIVE t AS (SELECT 1 AS n) SELECT n FROM t                  ->  1
#
# **The keyword is about the bodies, not the list**: a `WITH RECURSIVE` whose body does not name
# itself is an ordinary `WITH` and answers. So the keyword alone is not a refusal.
#
#     WITH RECURSIVE t(n) AS (SELECT 1 UNION ALL SELECT n+1 FROM t WHERE n < 5) SELECT n FROM t
#         ->  1, 2, 3, 4, 5
#     WITH RECURSIVE t AS (
#       SELECT id, firm_id FROM co WHERE firm_id IS NULL
#       UNION ALL
#       SELECT c.id, c.firm_id FROM co c JOIN t ON c.firm_id = t.id
#     ) SELECT id FROM t ORDER BY id                                       ->  1, 2, 3, 4
#
# — the second is `with_test.rb`'s own statement, one table smaller.
#
#     WITH RECURSIVE t(n) AS (SELECT 1 UNION SELECT 1 FROM t) SELECT n FROM t   ->  1
#
# **The dedup is what terminates that one**: with `UNION` the second iteration produces a row the
# working table already has, so there is nothing to carry forward. With `UNION ALL` it would not
# terminate at all — and PostgreSQL answers it anyway when a `LIMIT` bounds the reading:
#
#     WITH RECURSIVE t(n) AS (SELECT 1 UNION ALL SELECT n FROM t) SELECT n FROM t LIMIT 3
#         ->  1, 1, 1
#
# That last row is the one a bounded implementation cannot reproduce. A fixpoint that materialises
# hits its iteration cap and must **raise** rather than loop; PostgreSQL streams the working table
# and the `LIMIT` stops it. Whichever cap is chosen, that statement is a declared divergence and
# not a bug in the cap.
