# **`jsonb` comparison and ordering** — PostgreSQL 19beta1, 2026-09-09.
# `ON_ERROR_ROLLBACK on`, one `BEGIN … ROLLBACK`, no fixture.
#
# The (b) direction of the no-equality census: PostgreSQL answers these and this node refuses them
# with `0A000`, because `jsonb` shares `text`'s representation and byte order is not `jsonb` order
# (ADR 0042). `crate::value::json` already parses and canonicalises into a `Json` with kinds, so
# what is missing is a comparison over that, not a new `Datum`.
#
# ## THINGS REASONING WOULD GET WRONG
#
#   * **The kind rank is `null < string < number < boolean < array < object`** — measured
#     pairwise, and it is *not* the order the values print in nor the order a reader guesses.
#   * **The empty array does not follow it.** `'[]' < 'null'` is true while `'[1]' > 'true'` is
#     true, and `'{}' > 'null'` — so `[]` sorts below every scalar and `[1]` does not. Any
#     implementation that ranks by kind and then compares within it is wrong on exactly this
#     value, and `[]` is not a rare one.
#
#     **The obvious explanation is false and was tested.** "A scalar is internally a one-element
#     array, so `[]` wins on length" accounts for every ordering cell above — and it predicts
#     `'[null]' = 'null'` and `'[1]' = '1'`, both of which are **false**. So the ordering behaves
#     that way and equality does not, and this capture records the measurements rather than a
#     mechanism. Implement against the cells; do not derive them.
#   * **Numbers compare as `numeric`, not as text**: `1.0 = 1.00` is true and `2 < 10` is true,
#     where a byte comparison says false and false.
#   * **Arrays compare by length before contents**, so `[2] < [1,1]`.
#   * **Objects compare by pair count before keys**, so `{"z":1} < {"a":1,"b":1}`.
#   * **Key order is not part of the value** — the canonical form already sorted them, which is
#     why `{"a":1,"b":2} = {"b":2,"a":1}`.
#
# ## The measurements
#
