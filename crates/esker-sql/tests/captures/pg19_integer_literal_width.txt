# **What width PostgreSQL calls an unsuffixed integer literal** — PostgreSQL 19beta1, 2026-09-11.
# Three `BEGIN … ROLLBACK` sessions, **a `SAVEPOINT` per probe**.
#
# Taken for `debts-v1.1.md` #73. The savepoint per probe is the shape, not a flourish: without it
# the first refusal aborts the transaction and every later statement answers `current transaction
# is aborted` instead of the thing being measured. **stdout and stderr interleave** in the raw
# output below, so an `ERROR` can print one echo block late; each quotes its own statement on its
# `LINE 1:` line.
#
# ## The ladder: a literal's type is the width its value needs
#
#     pg_typeof(1)                       integer
#     pg_typeof(-1)                      integer
#     pg_typeof(2147483647)              integer      the last int4
#     pg_typeof(-2147483648)             integer
#     pg_typeof(2147483648)              bigint       one past it
#     pg_typeof(3000000000)              bigint
#     pg_typeof(100000000000000000000)   numeric      past int8
#
#     SELECT 1 AS one         \gdesc     integer      and the RowDescription agrees
#     SELECT ARRAY[1,2] AS a  \gdesc     integer[]
#     pg_typeof(ARRAY[1,2,3])            integer[]
#     pg_typeof(ARRAY[1,3000000000])     bigint[]     the constructor takes the widest element
#
# ## A written cast wins over the value's width
#
#     INSERT INTO t VALUES (2, 1, 'sad')             …expression is of type integer
#     INSERT INTO t VALUES (2, 1::bigint, 'sad')     …expression is of type bigint
#     INSERT INTO t VALUES (2, 1::smallint, 'sad')   …expression is of type smallint
#     INSERT INTO t VALUES (2, 1::integer, 'sad')    …expression is of type integer
#     INSERT INTO t VALUES (2, 3000000000, 'sad')    …expression is of type bigint
#     INSERT INTO t VALUES (2, 1.5, 'sad')           …expression is of type numeric
#     INSERT INTO t VALUES (2, true, 'sad')          …expression is of type boolean
#
#     UPDATE t SET m = 1                             …expression is of type integer
#     UPDATE t SET m = 1::bigint                     …expression is of type bigint
#     UPDATE t SET m = 3000000000                    …expression is of type bigint
#
# **These two halves are the whole rule** and together they refute both easy fixes: naming every
# integer `integer` fails the `1::bigint` rows, and reading the width off the stored value fails
# them too. Only asking the **literal** — the width it was written as, falling back to the width
# its value needs — passes all of them.
#
# ## The same names appear wherever a type is reported, not only on assignment
#
#     SELECT m = 1 FROM t          operator does not exist: mood = integer
#     SELECT m + 1 FROM t          operator does not exist: mood + integer
#     INSERT INTO t (m) SELECT i   …expression is of type integer     (an `integer` column)
#     INSERT INTO t (m) SELECT s   …expression is of type smallint    (a `smallint` column)
#
# A **column** is named by its own declared type, which is the case an evaluated expression
# already gets right: the value's width there really is its type.
#
# ## And assignment still coerces
#
#     INSERT INTO t (i) VALUES (1)            ok, an integer column
#     INSERT INTO t (b) VALUES (1)            ok, a bigint column
#     INSERT INTO t (i) VALUES (3000000000)   integer out of range
#
# The literal's own type is not the column's: assigning narrows or widens, and only a value that
# will not fit is refused — **and it is refused as being out of range, not as a type mismatch**.
#
# ---- probe 1: the ladder, arrays, assignment, as sent
# \set ON_ERROR_STOP 0
# BEGIN;
# CREATE TYPE mood AS ENUM ('sad','ok');
